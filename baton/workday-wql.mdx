## Which Workday connector should I use?

C1 offers two Workday connectors: Workday and Workday Accounts. How you want to work with Workday in C1 will determine which one you should set up.

* **[Workday connector](/baton/workday)**: This connector is the best choice if you want to use Workday as a [directory](/product/admin/directory). You’ll also need it if you want to enable access requests for Workday role and group assignments. It syncs accounts, roles, and security groups. Configured with a custom report, it can also pull in the account owner’s organization, title, and manager.

* **[Workday Accounts connector](/baton/workday-wql)**: This connector utilizes the Workday Query Language (WQL), which allows it to pull a different data set than the Workday connector. Workday Accounts is the best choice if you want to review who has what kind of access to Workday in your organization, including security groups, organization roles, account type, and service center assignments. Organization role assignments can be granted and revoked. The capabilities table lists what this connector syncs and what it provisions.

| Service center  | <Icon icon="square-check" iconType="solid"  color="#c937ae"/>    |   | 

The connector provisions organization role assignments and user-based security group membership. For user-based security groups, it provisions direct assignments only.

The connector surfaces the following entitlements:

* **Security groups** and **user-based security groups**: a `Member` entitlement, granted to each account that belongs to the group. Role-based security groups are synced for review only. Their `Member` entitlement cannot be granted or revoked, and C1 does not offer that action. Workday derives those memberships from an organization role assignment, so grant and revoke the **Assigned** entitlement on the organization role.
* **Organizations**: one resource per active organization. The parent is the superior organization.
* **Assignable roles**: one resource per assignable role referenced by a role-based security group in the type filter.
* **Organization roles**: a scope binding for one assignable role on one organization, with an **Assigned** entitlement you can grant and revoke. See [Organization roles (opt-in)](#organization-roles-opt-in).
* **Service centers**: a `Representative` entitlement, granted to each account that represents the service center.
* **Account type**: `Implementer` and `Integration User` role assignments, granted to the matching accounts.

## Organization roles (opt-in)

An organization role assignment is a scope binding: one assignable role on one organization. The organization is the scope, and the role is the role side. The connector emits a binding only where a worker holds the role on that organization, and grants the **Assigned** entitlement to that worker.

Workday passes a role assignment down from an organization to the organizations below it. The connector keeps only holders Workday marks as **Assigned**, because those are the only ones it can revoke. A holder who has the role by inheritance or by default on a sub-organization is not a grant there. That access still appears in C1 through the role-based security groups the role feeds.

### Turn organization roles on

<Steps>
<Step>
Add the role-based security group types to the **Other security group types** list, for example `Role-Based Security Group (Unconstrained)` and `Role-Based Security Group (Constrained)`. The names are case-sensitive, and one wrong character matches nothing. Get the list right before the first sync: the connector refuses a run only when C1 names the resource types to sync, and C1 does not name them on the first sync of a deployment, or at all on some tenants. When it names them, an empty list stops the connector before it calls Workday, and a list whose security groups name no assignable role fails the assignable role and organization role syncs. When it does not, the three types sync with nothing in them, and C1 reads that as a deletion. The **Other security groups** list narrows the same set and can empty it the same way.
</Step>
<Step>
Enable **Organization**, **Assignable Role**, and **Organization Role** together under **Capabilities & configuration** > **Resource capabilities**. C1 leaves the three types off until you enable them, and a binding needs the other two: they are its role and its scope.
</Step>
<Step>
Give the integration system user the domain rows in [Create a new security group](#create-a-new-security-group) and the [Assign Roles business process permission](#allow-the-integration-system-user-to-start-assign-roles).
</Step>
</Steps>

<Note>
The same **Other security group types** list selects which security groups sync. A list that names only the role-based types drops every other security group type.
</Note>

### Grant and revoke

Grant assigns one worker to the role on the organization. Revoke removes that worker.

<Warning>
A Workday role can be restricted to a single assignment. On such a role, Assign Roles accepts a grant even when another worker already holds the role on that organization, removes that worker, and returns success. The connector therefore checks the current holder first and refuses the grant, naming the position that holds the role. Revoke the current assignment first, or transfer the role in Workday. The check needs Get on the Manage: Organization Roles domain. Without it, a grant on a single-assignment role fails with "The task submitted is not authorized".
</Warning>

<Note>
Workday requires the `Update_Later_Dated_Assignments` option on a removal, so a revoke also updates later-dated assignments. Review scheduled role changes in Workday before you revoke.
</Note>

If the Assign Roles business process definition has an approval step, the assignment stays pending and the grant does not complete. An assignable role can also restrict who is allowed to assign it; the integration system security group has to be allowed on that role. See the [Workday Assign Roles reference](https://community.workday.com/sites/default/files/file-hosting/productionapi/Staffing/v45.0/Assign_Roles.html) for the service's validation rules.

## Gather Workday credentials 

Configuring the connector requires you to pass in credentials generated in Workday. Gather these credentials before you move on. 

<Warning>
A user with the permission to create a new API client in Workday must perform this task.
</Warning>

### Look up your Workday REST API endpoint

<Steps>
<Step>
In Workday, use the search bar to look up "View API Clients". Make sure to select this name from the results, not the similarly named "Register API Client". 
</Step>
<Step>
Carefully copy and save the Workday REST API endpoint.  
</Step>
</Steps>

### Create a new Workday API client

<Steps>
<Step>
In Workday, use the search bar to look up "Register API Client for Integrations". Make sure to select this name from the results, not the similarly named "Register API Client". 
</Step>
<Step>
In the modal that appears, give the new API client a name, such as "C1 integration". 
</Step>
<Step>
In the **Scopes** box, select **Custom Objects** and add **System**, **Organizations and Roles**, and **Staffing**. System is required for the WQL API. Organizations and Roles is required for Get Organizations; without it, that call returns "not authorized". Staffing is required for Get Workers, Assign Roles, and Get Role Assignments For Role Assigners.
</Step>
<Step>
The newly created client's client ID and client secret are shown. Carefully copy and save these credentials. 

   **Do not** click **Done** at the bottom of the page yet.
</Step>
</Steps>

#### Create a refresh token

<Steps>
<Step>
Next, click the three dots icon next to the client name and navigate to **API Client** > **Manage Refresh Tokens for Integrations**. 
</Step>
<Step>
Select the Workday account you want to associate with the token and click **OK**. 
</Step>
<Step>
On the **Delete or Regenerate Refresh Token** page, scroll down and check the **Generate New Refresh Token** box. 
</Step>
<Step>
Click **OK**. 
</Step>
<Step>
Carefully copy and save the new refresh token. 
</Step>
</Steps>

#### Create a new security group

<Steps>
<Step>
Still in Workday, use the search bar to look up "Maintain Permissions for Security Group". 
</Step>
<Step>
In the **Maintain Permissions for Security Group** modal, make sure the **Maintain** button is selected. 
</Step>
<Step>
In the **Source Security Group** field, navigate to **By Type** > **Integration System Security Group**. 
</Step>
<Step>
Create a new security group. Give it a name, such as "C1 WQL integration security group". 
</Step>
<Step>
On the new group's **Domain Security Policy Permissions** tab, leave the **Select All** box checked. 
</Step>
<Step>
Click the **+** icon to create new rows, and fill them out as follows: 

| View/Modify Access | Domain Security Policy                    | Functional Areas | Purpose                                |
| :--- | :--- | :--- | :--- |
| View Only          | WQL for Workday Extend                    | System           | (Required) WQL API Access              |
| View Only          | Workday Accounts                          | System           | (Required) Accounts, Implementers      |
| View Only          | Worker Data: Public Worker Reports        | Staffing         | Worker name, email, manager, and job title |
| Get Only           | Worker Data: Public Worker Reports        | Staffing         | Whether an organization role was assigned |
| View Only          | Security Configuration                    | System           | Security Groups                        |
| View Only          | Security Administration                   | System           | Most recent sign-on, and the assignable role catalog |
| View Only          | Manage: Service Center                    | System           | Service Centers                        |
| Get and Put        | User-Based Security Group Administration  | System           | User-Based Security Group Provisioning |
| Get                | Manage: Organization Integration          | Organizations and Roles | Organization role sync, when enabled (Get Organizations) |
| Get                | Manage: Organization Roles                | Organizations and Roles | Organization role grants, to read the holder of a role restricted to a single assignment (Get Role Assignments For Role Assigners) |
</Step>
<Step>
Click **OK**.

   Worker Data needs both rows. **Maintain Permissions for Security Group** offers one access choice per domain, so add them from the domain: search for **Domain Security Policies for Functional Area**, choose **Staffing**, open **Worker Data: Public Worker Reports**, and choose **Edit Permissions**. **View Only** goes on **Report/Task Permissions**. **Get Only** goes on **Integration Permissions**.
</Step>
</Steps>

#### Allow the integration system user to start Assign Roles

Grant and revoke run the Assign Roles web service. That permission is a business process security policy, not a domain row in the table above.

<Steps>
<Step>
In Workday, search for "Edit Business Process Security Policy". Older tenants name this task "Maintain Business Process Security Policy".
</Step>
<Step>
Select the initiating action **Assign Roles (Web Service)**.
</Step>
<Step>
Add the integration system security group you created above, and click **OK**.
</Step>
</Steps>

Use that integration system security group. Adding the integration system user to a user-based security group can start an approval. While the approval is pending the group stays empty, and Assign Roles returns "not authorized".

#### Activate pending security policy changes

Activate after the domain rows and after the Assign Roles policy. Neither takes effect until you do. Before activation, Assign Roles returns "The task submitted is not authorized".

<Steps>
<Step>
Search for "Activate Pending Security Policy Changes". 
</Step>
<Step>
Add a comment about the change you're making and click **OK**. 
</Step>
<Step>
Review the changes. If everything looks good, click the **Confirm** checkbox, then click **OK**. 
</Step>
</Steps>

#### Assign the security group to the Workday account

<Steps>
<Step>
Still in Workday, use the search bar to look up "View Workday Account" and select the Workday account you used when generating the refresh token. 
</Step>
<Step>
Click the three dots icon next to the account name and navigate to **Security Profile** > **Assign Integration System Security Groups**. 
</Step>
<Step>
Select the security group you created and click **OK**. 
</Step>
</Steps>

### Optional: Look up security group types

If you want C1 to sync specific non-user-based security group types (such as `Role-Based Security Group (Constrained)` and `Integration System Security Group`), you'll need to gather the list of these types. 

Non-user-based security group types are defined and configured in Workday, and their exact names vary based on how your Workday instance is configured. Remember that security group type names are cases-sensitive. 

**That's it!** Next, move on to the connector configuration instructions. 

## Configure the Workday Accounts connector

<Warning>
To complete this task, you'll need:

- The **Connector Administrator** or **Super Administrator** role in C1
- Access to the set of Workday Accounts credentials generated by following the instructions above
</Warning>

<Tabs>
<Tab title="Cloud-hosted">

**Follow these instructions to use a built-in, no-code connector hosted by C1.**

<Steps>
   <Step>
   In C1, navigate to **Apps** > **Connectors** and click **Browse connectors**.
   </Step>
   <Step>
   Search for **Workday Accounts** and click **Add**. 
   </Step>
   <Step>
   Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).

      If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
   </Step>
   <Step>
   Set the connector's **Name** and, optionally, a **Description**.
   </Step>
   <Step>
   Click the pencil icon next to **Owners** to choose who can configure and manage this connector.

   Make sure any user who you select as a connector owner has either the Connector Admin or Super Admin user role in C1, as this is required to manage the connector.
   </Step>
   <Step>
   Click **Add**. The connector is created and its configuration page opens.
   </Step>
   <Step>
   Find the **Settings** area of the page and click **Edit**.
   </Step>
   <Step>
   Enter the endpoint you looked up in the **Workday REST API endpoint** field. 
   </Step>
   <Step>
   Enter the **Client ID**, **Client secret**, and **Refresh token** in the relevant fields.
   </Step>
   <Step>
   **Optional.** If desired, click the checkbox to **Sync service centers**. 
   </Step>
   <Step>
   **Optional.** If desired, click the checkbox to **Sync user-based security groups**. 

      * If you select this option, you may enter an optional list of the user-based security groups that you want to sync in the **User-based security groups (optional)** field. 
   </Step>
   <Step>
   **Optional.** Enter the list of (non-user-based) security group types you want to sync in the **Other security group types (optional)** field. The names are case-sensitive. Organization roles need the role-based types included in that list, for example `Role-Based Security Group (Unconstrained)` and `Role-Based Security Group (Constrained)`. A list that names only those two stops syncing every other security group type.
   </Step>
   <Step>
   **Optional.** Enter the list of (non-user-based) security groups you want to sync in the **Other security groups (optional)** field. Remember that security group names are case-sensitive.  
   </Step>
   <Step>
   **Optional.** If desired, click the checkbox to **Include effective membership for security groups**. This option is off by default.

      * Grants include members who inherit access, for example through included groups or role defaulting, in addition to direct members. When this option is off, only direct members are synced. The option does not apply to service centers.
      * This option optimizes listing security group grants for large tenants with long-running security group queries.
      * When this option is on, users must be synced in the same sync as the security groups.
      * The connector can revoke only user-based security group grants, and a revoke removes only the direct assignment. Inherited access is not removed and is synced again.
   </Step>
   <Step>
   Click **Save**.
   </Step>
   <Step>
   **Optional.** To sync organization roles, open **Capabilities & configuration**, click **Edit**, and enable **Organization**, **Assignable Role**, and **Organization Role** together. See [Organization roles (opt-in)](#organization-roles-opt-in).
   </Step>
   <Step>
   The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
   </Step>
</Steps>

**That's it!** Your Workday Accounts connector is now pulling access data into C1.

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your Workday Accounts connector deployment:

#### Secrets configuration

```yaml expandable
# baton-workday-wql-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-workday-wql-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>
  
  # Workday credentials
  BATON_WORKDAY_REST_API_ENDPOINT: <Workday REST API endpoint>
  BATON_WORKDAY_CLIENT_ID: <Workday API client ID>
  BATON_WORKDAY_CLIENT_SECRET: <Workday API client secret>
  BATON_WORKDAY_REFRESH_TOKEN: <Workday API client refresh token>

  # Optional: include if you want to sync resource IDs
  BATON_SYNC_RESOURCES: <List of the resource IDs to sync>

  # Optional: include if you want to sync service centers
  BATON_SYNC_SERVICE_CENTERS: "true"

  # Optional: include if you want to sync user-based security groups (default is true)
  BATON_SYNC_USER_BASED_SECURITY_GROUPS: "true"

  # Optional: include if you want to limit the synced user-based security groups to the types listed here
  BATON_USER_BASED_SECURITY_GROUP_FILTER: <List of user-based security group types to sync>

  # Optional: include if you want to limit the synced security groups to the groups listed here
  BATON_SECURITY_GROUP_FILTER: <List of the names of other security groups to sync>

  # Optional: include if you want to limit the synced security group types to the types listed here; add the role-based types to sync organization roles
  BATON_SECURITY_GROUP_TYPE_FILTER: <types you already sync>,Role-Based Security Group (Unconstrained),Role-Based Security Group (Constrained)

  # Optional: include if you want to limit the sync to the resource types listed here; leaving it unset syncs every type
  # BATON_SYNC_RESOURCE_TYPES: user,account_type,service_center,user_based_security_group,security_group,organization,assignable_role,organization_role

  # Optional: include to add inherited members to security group grants and to optimize listing them for large tenants;
  # users must be synced in the same sync; a revoke removes only a direct assignment (default is false)
  BATON_INCLUDE_EFFECTIVE_SECURITY_GROUP_MEMBERSHIP: "true"

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: "true"
```

Run `--help` to see all available configuration flags and environment variables.

#### Deployment configuration

```yaml expandable
# baton-workday-wql.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: baton-workday-wql
  labels:
    app: baton-workday-wql
spec:
  selector:
    matchLabels:
      app: baton-workday-wql
  template:
    metadata:
      labels:
        app: baton-workday-wql
        baton: "true"
        baton-app: workday-wql
    spec:
      containers:
      - name: baton-workday-wql
        image: public.ecr.aws/conductorone/baton-workday-wql:latest
        imagePullPolicy: IfNotPresent
        env:
        - name: BATON_HOST_ID
          value: baton-workday-wql
        envFrom:
        - secretRef:
            name: baton-workday-wql-secrets
```

### Step 3: Deploy the connector

<Steps>
<Step>
Create a namespace in which to run C1 connectors (if desired), then apply the secret config and deployment config files. 
</Step>
<Step>
Check that the connector data uploaded correctly. In C1, click **Apps**. On the **Applications** tab, locate and click the name of the application you added the Workday Accounts connector to. Workday Accounts data should be found on the **Entitlements** and **Accounts** tabs.
</Step>
</Steps>


**That's it!** Your Workday Accounts connector is now pulling access data into C1.
