C1 provides identity governance and just-in-time provisioning for Descope. Integrate your Descope project with C1 to run user access reviews (UARs), enable just-in-time access requests, and automatically provision and deprovision access.

The Descope connector reads identity and access data from a Descope project (https://www.descope.com) through the Descope Management API.

## Capabilities

| Resource | Sync | Provision |
|-|-|-|
| Users | <Icon icon="square-check" iconType="solid" color="#c937ae"/> | |
| Tenants | <Icon icon="square-check" iconType="solid" color="#c937ae"/> | <Icon icon="square-check" iconType="solid" color="#c937ae"/> |
| Roles | <Icon icon="square-check" iconType="solid" color="#c937ae"/> | <Icon icon="square-check" iconType="solid" color="#c937ae"/> |
| Permissions | <Icon icon="square-check" iconType="solid" color="#c937ae"/> | |

- **Users**: Synced from `/v2/mgmt/user/search`. The stable ID is the Descope `userId`.
- **Tenants**: Synced from `/v1/mgmt/tenant/search`. Each tenant has a `member` entitlement that C1 can grant to and revoke from users.
- **Roles**: Synced from `/v1/mgmt/role/all`, including both project-level and tenant-scoped roles. Each role has an `assigned` entitlement that C1 can grant to and revoke from users.
- **Permissions**: Synced from `/v1/mgmt/permission/all`. Each permission has a `granted` entitlement that shows which roles confer the permission. This is read-only. Manage permission-to-role assignments by editing roles in Descope.

The connector does not create or delete Descope user accounts, and it does not provide connector actions.

## Gather Descope credentials

<Warning>
To configure the Descope connector, you need to be a project admin in Descope. The management key needs read access to users, tenants, roles, and permissions, plus user-management write access for provisioning (role assignment and tenant membership). A project-scoped management key with the project admin role covers all of these.
</Warning>

<Steps>
  <Step>
    Log in to the Descope console as a project admin.
  </Step>

  <Step>
    Find your **Project ID** under **Project** > **Settings** > **Project ID**. It starts with `P`.
  </Step>

  <Step>
    Create a **Management Key** under **Company** > **Management Keys**, scoped to the project you want to connect. Copy the key. Descope shows it only once.
  </Step>

  <Step>
    Decide on the **Base URL**. Use `https://api.descope.com` unless you are on a non-default Descope deployment.
  </Step>

  <Step>
    Optional: To limit the sync to specific tenants, find the tenant IDs in the Descope console under **Tenants**. They start with `T`.
  </Step>
</Steps>

The connector authenticates with a bearer token of the form `ProjectID:ManagementKey`.

That's it! Next, configure the connector in C1.

## Configure the Descope connector

<Warning>
To complete this task, you need the **Connector Administrator** or **Super Administrator** role in C1. You also need the Descope **Project ID**, **Management Key**, and **Base URL** from the previous section.
</Warning>

<Tabs>
  <Tab title="Cloud-hosted">
    Follow these instructions to use a built-in, no-code connector hosted by C1.

    <Steps>
      <Step>
        In C1, navigate to **Integrations** > **Connectors** and click **Add connector**.
      </Step>

      <Step>
        Search for **Descope** and click **Add**.
      </Step>

      <Step>
        Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).

        If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
      </Step>

      <Step>
        Set the connector's **Name** and, optionally, a **Description**.
      </Step>

      <Step>
        Click the pencil icon next to **Owners** to choose who can configure and manage this connector.
      </Step>

      <Step>
        Click **Add**. The connector is created and its configuration page opens.
      </Step>

      <Step>
        Find the **Settings** area of the page and click **Edit**.
      </Step>

      <Step>
        Enter the required configuration:

        - **Project ID**: Your Descope Project ID. It starts with `P`.
        - **Management Key**: The management key you created. C1 stores it as a secret.
        - **Base URL**: The Descope API base URL, for example `https://api.descope.com`. Do not include a trailing slash or path.
        - **Tenant IDs**: Optional. Leave empty to sync every tenant in the project. See [Tenant IDs filter](#tenant-ids-filter).
      </Step>

      <Step>
        Click **Save**.
      </Step>

      <Step>
        The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
      </Step>
    </Steps>

    **Done.** Your Descope connector is now pulling access data into C1.
  </Tab>

  <Tab title="Self-hosted">

    - [Download center](https://dist.conductorone.com/ConductorOne/baton-descope)
    - [GitHub repository](https://github.com/conductorone/baton-descope)

    <Steps>

        In C1, navigate to **Integrations** > **Connectors** and click **Add connector**.
      </Step>

      <Step>
        Search for **Baton** and click **Add**.
      </Step>

      <Step>
        Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).
      </Step>

      <Step>
        Set the connector's **Name** and, optionally, a **Description**, then click the pencil icon next to **Owners** to choose who can configure and manage this connector.
      </Step>

      <Step>
        Click **Add**. The connector is created and its configuration page opens.
      </Step>

      <Step>
        In the **Settings** area, click **Edit**, then click **Rotate** to generate a new Client ID and Client Secret. Store these values securely for your deployment.
      </Step>

        Store the C1 credentials and the Descope credentials in a Kubernetes Secret and expose them to the connector with `envFrom`:

        ```yaml
        apiVersion: v1
        kind: Secret
        metadata:
          name: baton-descope-secrets
        stringData:
          BATON_CLIENT_ID: <C1 client ID>
          BATON_CLIENT_SECRET: <C1 client secret>
          BATON_PROJECT_ID: <Descope Project ID>
          BATON_MANAGEMENT_KEY: <Descope Management Key>
          BATON_BASE_URL: https://api.descope.com
          # Optional. Comma-separated Descope tenant IDs to sync.
          # BATON_TENANT_IDS: <tenant ID>,<tenant ID>
        ```
      </Step>

      <Step>
        Deploy the connector using the public ECR image:

        ```yaml
        apiVersion: apps/v1
        kind: Deployment
        metadata:
          name: baton-descope
        spec:
          replicas: 1
          selector:
            matchLabels:
              app: baton-descope
          template:
            metadata:
              labels:
                app: baton-descope
            spec:
              containers:
                - name: baton-descope
                  image: public.ecr.aws/conductorone/baton-descope:latest
                  envFrom:
                    - secretRef:
                        name: baton-descope-secrets
                  env:
                    - name: BATON_HOST_ID
                      value: baton-descope
        ```
      </Step>
    </Steps>

    **Done.** Your Descope connector is now pulling access data into C1.
  </Tab>
</Tabs>

## Tenant IDs filter

By default the connector syncs every tenant in the project. When you set **Tenant IDs**, only these tenants are synced: their tenant resources, their memberships, the assignments of roles scoped to them, and the tenant-scoped roles themselves. Project-level roles and every user still sync, because the role catalogue is read in one project-wide call and the user directory is not filtered.

The connector checks on every sync that each ID in this field is a tenant in the project. A configured ID that the search does not return **fails that whole sync**, including users, roles, and permissions, not just that tenant. The error names the ID, so a tenant that was deleted in Descope stops syncing until you remove its ID from this field.

An ID that does not exist, or that carries whitespace from a comma-separated value, would otherwise drop that tenant's resources and membership grants from every sync without an error, because the listing simply returns fewer tenants. Find the IDs in the Descope console under **Tenants** (they start with `T`).

## Sync behavior

- Paginates `/v2/mgmt/user/search` via the request-body `offset`/`limit`
  fields (page size 100), terminating on the response `total`.
- Lists tenants, roles, and permissions in single unpaginated calls.
- Lists tenants through `POST /v1/mgmt/tenant/search`. With **Tenant IDs**
  unset the request carries an empty payload, which Descope documents as
  returning every tenant. With the field set the request filters by
  `tenantIds`, so the response — and the memory it occupies — is bounded by
  the configured tenants instead of by the project's tenant count. Without
  that bound, a project that auto-provisions a tenant per end-user can return
  a tenant listing large enough to exhaust the connector's memory.
- Fails validation when a configured **Tenant IDs** value is not returned by
  that search. Descope answers an unmatched `tenantIds` filter with a normal
  empty result, so without the check a wrong ID would just sync less.
- Scopes tenant-scoped roles, resources and walks together. A role scoped to a
  tenant that **Tenant IDs** excludes is not emitted as a role resource (so its
  tenant id does not reach C1 in the role display name or the
  `tenant_id` profile), and its member walk is skipped. Project-level roles
  (`tenant_id` empty) are never filtered. The permission → role grants below are
  derived from the same role catalogue, so they are filtered the same way — a
  grant never names a role resource that was not emitted.
- Reads the role catalogue itself in one project-wide call per sync, cached for
  the session; the scope filter above is applied to what it emits, not to what
  it fetches.
- Does **not** filter the user directory: users are project-level in
  Descope, and a user can belong to a tenant that is not synced without
  being scoped to one. Every user is emitted, whoever its tenants are.
- Refuses to grant access outside the sync scope. A project previously
  synced without **Tenant IDs** still holds C1 entitlements for
  every tenant, so a grant request can name an excluded tenant; the
  connector fails that grant with an actionable error instead of writing it.
  Revokes are not guarded, so legacy out-of-scope grants can be cleared.
- Resolves tenant and role grants with a server-side filtered
  `/v2/mgmt/user/search` per resource — `tenantIds` for tenant membership,
  `tenantRoleNames` for tenant-scoped roles, and `roleNames` for project-level
  roles — so no full user directory is cached in the session store.
- Reports tenant membership as direct membership only, via
  `includeSubTenants: false`. A user's `userTenants[]` lists only the tenants
  they belong to directly, so members of a child tenant are not reported
  against its parent.
- Re-checks project-level role holders against the user's project `roleNames`.
  The `roleNames` filter matches a role name at any scope, so a user holding
  the role only inside a tenant would otherwise be reported as holding the
  project-level role of the same name.
- Resolves permission grants from the inline `permissionNames` on the role
  list (cached once per sync; the role list is small and bounded).
- Treats HTTP 429 and 5xx as transient and retries with exponential back-off.
- Caps concurrency at `maxParallelFetches: 6`.

## Provisioning behavior

- Every grant and revoke first resolves the principal's login via
  `GET /v1/mgmt/user?userId=…`, because the mutation endpoints below take a
  `loginId` while user resources are keyed on the stable `userId`.
- **Role assignment** (`role` → `assigned`): grants and revokes project-level
  and tenant-scoped roles via `/v1/mgmt/user/update/role/add` and
  `/remove` (tenant-scoped roles include the `tenantId`).
- **Tenant membership** (`tenant` → `member`): adds and removes users via
  `/v1/mgmt/user/update/tenant/add` and `/remove`.
- Permission → role grants are read-only; manage them by editing roles in
  Descope.
