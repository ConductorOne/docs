The NetSuite connector supports [automatic account provisioning](/product/admin/account-provisioning).

This connector does not support account deprovisioning. You must deprovision accounts directly in NetSuite.

## Account provisioning

The NetSuite connector supports creating new employee accounts directly from C1. When configuring an account provisioning policy, you can map the following fields.

### Required fields

| Field | Description |
| :--- | :--- |
| `email` | The employee's email address. Used as the login identifier in NetSuite. |
| `firstName` | The employee's first name. |
| `lastName` | The employee's last name. |

### Optional fields

| Field | Description | Default |
| :--- | :--- | :--- |
| `subsidiary` | Name or internal ID of the NetSuite subsidiary to assign to the employee. | None |
| `entityId` | Custom entity ID for the employee record. If omitted, NetSuite auto-generates one. | Auto-generated |
| `roleID` | Internal ID of the NetSuite role to assign to the employee at creation time. | Employee Center |
| `giveAccess` | Whether the employee should have login access to NetSuite (`true` or `false`). | `true` |
| `skipDefaultRole` | When `true`, skips assigning the default Employee Center role if no `roleID` is provided. Use this when the role will be assigned separately via a grant step. | `false` |

### Role assignment and login access

`giveAccess` controls whether the employee can log into NetSuite. `skipDefaultRole` controls whether the connector assigns the Employee Center role when no `roleID` is provided.

**If `roleID` is provided**, the specified role is always assigned. `skipDefaultRole` is ignored. Login access is determined by `giveAccess`.

**If `roleID` is not provided, `skipDefaultRole` is `false`** (default), **and `giveAccess` is `true`** (default), the connector assigns the Employee Center role automatically. This requires the Employee Center role to exist and be assignable in your NetSuite tenant.

**If `roleID` is not provided and `skipDefaultRole` is `true`**, no role is included in the create request.

**If `roleID` is not provided and `giveAccess` is `false`**, no role is included in the create request regardless of `skipDefaultRole`.

<Note>
To add `giveAccess` or `skipDefaultRole` to your mapping, click **Add mapping** in the **Optional mappings** section of the provisioning policy configuration.
</Note>

<Warning>
**Administrator roles cannot be granted or revoked via the connector.** NetSuite's API does not allow modifications to employee records that have the Administrator role assigned, regardless of the permissions granted to the integration. Attempting to grant or revoke the Administrator role through C1 will result in an error. To assign or remove the Administrator role, make the change directly in NetSuite.
</Warning>

## Login Access

The connector surfaces whether an employee can sign in to NetSuite as a dedicated **Login Access** entitlement. Employees who have login access receive a grant on this entitlement.

<Note>
Login Access only controls whether an employee can sign in. It does not assign or remove roles. Use role grants to control what an employee can do once they can log in.
</Note>

<Warning>
**Granting a role also turns on login access and emails the employee.** When C1 grants a NetSuite role, the connector sets **Login Access** (`giveAccess`) to `true` on the employee and asks NetSuite to send the employee a notification email (`sendEmail`). An employee who had no login access can sign in to NetSuite after any role grant. To remove sign-in, revoke the **Login Access** entitlement separately.
</Warning>

### Revoking the last role

NetSuite does not allow removing the last role from an employee while `giveAccess` is `true`. If you attempt to do so, the API returns an error.

By default, the connector does not override this restriction. To allow the connector to automatically set `giveAccess = false` before revoking an employee's last role, enable the `revoke-access-with-last-role` flag.

<Warning>
When this flag is enabled, revoking an employee's last role will also remove their login access. Only enable it if that is the intended behavior for your deprovisioning policy.
</Warning>

## Role permissions

The connector can optionally sync the granular **permissions** that NetSuite roles confer, with their access level (View, Create, Edit, Full), read from NetSuite's `rolepermissions` data. This lets reviewers see exactly what a role grants — not just the role name — during a user access review.

When enabled, each distinct NetSuite permission (for example *Sales Order* or *Custom Lists*) is synced once as a **Permission** resource, with one entitlement per access level: **View**, **Create**, **Edit**, and **Full**. Every role that confers a permission is granted the entitlement matching its access level, and users who hold the role show **derived access** to that permission level, attributed to the role that confers it. A user holding two roles that confer the same permission at different levels shows both, each attributed to its role.

Because a NetSuite permission cannot be granted or revoked on its own, this derived access is **revocable only at the role** — reviewing and revoking happens at the role level, exactly as NetSuite enforces it.

The connector syncs **access levels only**. NetSuite role-level restrictions (employee, subsidiary, and department/class/location restrictions) are not represented — a permission whose scope is limited by a role restriction displays at its base access level.

<Note>
Permission syncing is **off by default**. Enable the **Permissions** resource type when configuring the connector's sync or an access review campaign. The connector syncs every permission assigned to at least one role (typically a few hundred resources), so enable it when reviewers need permission-level visibility.
</Note>

<Tip>
This uses the **Setup - Bulk Manage Roles** permission already listed in the integration role setup below. If that permission is missing, the connector fails the sync with a clear error rather than silently omitting permission data.
</Tip>

## Gather NetSuite credentials 

Configuring the connector requires you to pass in credentials generated in NetSuite. Gather these credentials before you move on. 

The connector supports two authentication methods:

- **Token-Based Authentication (TBA)**: a consumer key and secret plus a token key and secret.
- **OAuth 2.0 client credentials (machine to machine)**: a client ID, a certificate ID, and a private key. Use this method if your organization requires OAuth 2.0.

The account ID, integration, and role steps apply to both methods. Then follow either **Generate a token key and token secret** (TBA) or **Set up OAuth 2.0 client credentials**.

<Warning>
A user with an **Administrator** role in NetSuite must perform this task.
</Warning>

<Tip>
**Before you begin:** Make sure you have enabled the following features for your NetSuite instance:

- Token-Based Authentication (TBA) or OAuth 2.0, depending on the authentication method you choose
- REST Web Services
- Suite Analytics Workbook

You'll find directions for enabling features in the [NetSuite documentation](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_N232138.html#Enabling-Features).
</Tip>

### Locate your NetSuite Account ID

<Steps>
<Step>
In NetSuite, navigate to **Setup** > **Company** > **Company Information**.
</Step>
<Step>
Find the **ACCOUNT ID** field on the page. Make a note of your account ID. We'll use it in Step 5.
</Step>
</Steps>

### Generate a consumer key and consumer secret

<Steps>
<Step>
In NetSuite, navigate to **Setup** > **Integrations** > **Manage Integrations**. Click **New** to create a new integration.
</Step>
<Step>
Give the new integration a name, such as "C1".
</Step>
<Step>
On the **Authentication** tab, select the authentication method:

- For TBA, check the box for **TOKEN-BASED AUTHENTICATION**.
- For OAuth 2.0 client credentials, check the box for **CLIENT CREDENTIALS (MACHINE TO MACHINE) GRANT** and, under **Scope**, check **REST WEB SERVICES**.

<Tip>
Make sure **OAuth 2.0 Authorization Code Grant** is unchecked on the Authentication tab. NetSuite may enable this by default, which requires a Redirect URI that is not needed for the C1 connector. The C1 NetSuite connector doesn't use the authorization code grant.
</Tip>
</Step>
<Step>
Click **Save**. The new integration is created, and its credentials are shown: the consumer key and consumer secret for TBA, or the client ID and client secret for OAuth 2.0 client credentials.
</Step>
<Step>
Make a careful note of these credentials (they won't be shown again). The OAuth 2.0 client credentials method only needs the client ID.
</Step>
</Steps> 

### Create a NetSuite role and add it to a user

<Steps>
<Step>
Still in NetSuite, navigate to **Setup** > **Users/Roles** > **Manage Roles**. Click **New** to create a new role.
</Step>
<Step>
Give the new role a name, such as "C1 integration".
</Step>
<Step>
Assign the following permissions to the role:

   - Setup - REST Web Services
   - Setup - Log in using Access Tokens (TBA only)
   - Setup - Log in using OAuth 2.0 Access Tokens (OAuth 2.0 client credentials only)
   - Setup - Bulk Manage Roles
   - Reports- Suite Analytics Workbook
   - Lists - Employee Record
   - Lists - Employees

   <Tip>
   **Why are these permissions needed?** The integration uses these permissions to read and query SuiteQL tables containing information on roles and employees.
   </Tip>
</Step>
<Step>
Click **Save**.
</Step>
<Step>
Next, assign the new role to a user. You might want to create a new user for this purpose rather than assigning the role to an existing user. Navigate to **Lists** > **Employees** > **Employees**, then search for the employee by email.
</Step>
<Step>
Click **Edit** next to the name of the employee you want to assign a role to.
</Step>
<Step>
Click the **Access** subtab.
</Step>
<Step>
In the **Role** field, select a role for this employee.
</Step>
<Step>
Click **Add**.
</Step>
<Step>
Click **Save**.
</Step>
</Steps>

### Generate a token key and token secret

<Steps>
<Step>
In NetSuite, navigate to **Setup** > **Users/Roles** > **Access Tokens**. Click **New** to create a new token.
</Step>
<Step>
Select the application (integration), role, and user you created in the previous steps, and give the token a name.
</Step>
<Step>
Click **Save**. The new token is created, and its key and secret are shown.
</Step>
<Step>
Make a careful note of these credentials (they won't be shown again).
</Step>
</Steps> 

### Set up OAuth 2.0 client credentials

Skip this section if you're using TBA.

<Steps>
<Step>
On your computer, generate a certificate and private key. NetSuite accepts RSA keys of 3072 or 4096 bits, or EC keys on P-256, P-384, or P-521, and certificates valid for up to two years. For example:

```bash
openssl req -new -x509 -newkey rsa:4096 -keyout private.pem -sigopt rsa_padding_mode:pss -sha256 -sigopt rsa_pss_saltlen:64 -out public.pem -nodes -days 365
```

Keep `private.pem` secret. You'll paste its full contents into C1.
</Step>
<Step>
In NetSuite, navigate to **Setup** > **Integration** > **Manage Authentication** > **OAuth 2.0 Client Credentials (M2M) Setup**. Click **Create New**. This page requires the **OAuth 2.0 Authorized Applications Management** permission, which the Administrator role has.
</Step>
<Step>
Select the user (entity), the C1 integration role, and the application (integration) you created in the previous steps, and upload `public.pem`.

<Warning>
**Don't map the certificate to the Administrator role.** NetSuite blocks REST web services over OAuth 2.0 for any role that has the **OAuth 2.0 Authorized Applications Management** permission, so the connector fails to authenticate. Map it to the C1 integration role.
</Warning>
</Step>
<Step>
Click **Save**. Make a note of the **Certificate ID** shown for the new mapping.
</Step>
</Steps>

<Warning>
**Syncs stop when the certificate expires.** NetSuite rejects the connector once the uploaded certificate expires or is revoked. Before that happens, create a new mapping with a new certificate and update the certificate ID and private key in C1.
</Warning>

<Note>
**Sandbox refreshes clear the setup.** NetSuite doesn't copy the OAuth 2.0 client credentials setup to sandbox or Release Preview accounts, and a sandbox refresh removes it. Repeat this section in each account you connect.
</Note>

**Done.** Next, move on to the connector configuration instructions. 

## Configure the NetSuite connector

<Warning>
To complete this task, you'll need:

- The **Connector Administrator** or **Super Administrator** role in C1
- Access to the set of NetSuite credentials generated by following the instructions above
</Warning>

<Tabs>
<Tab title="Cloud-hosted">
**Follow these instructions to use a built-in, no-code connector hosted by C1.**

<Steps>
<Step>
In C1, navigate to **Apps** > **Connectors** and click **Add connector**.
</Step>
<Step>
Search for **NetSuite** and click **Add**.
</Step>
<Step>
Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).

   If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
</Step>
<Step>
Set the connector's **Name** and, optionally, a **Description**.
</Step>
<Step>
Click the pencil icon next to **Owners** to choose who can configure and manage this connector.
</Step>
<Step>
Click **Add**. The connector is created and its configuration page opens.
</Step>
<Step>
Find the **Settings** area of the page and click **Edit**.
</Step>
<Step>
In the **Account ID** field, enter your NetSuite account ID as shown under **Setup** > **Company** > **Company Information** (for example, `1234567`, or `1234567_SB1` for a sandbox). Don't enter the domain (`1234567-sb1.suitetalk.api.netsuite.com`): the connector rejects account IDs that contain dashes.
</Step>
<Step>
Select the authentication method you set up and enter its credentials:

- **Token-Based Authentication**: enter the **Consumer key**, **Consumer secret**, **Token key**, and **Token secret** you generated.
- **OAuth 2.0 Client Credentials**: enter the integration's client ID in **OAuth 2.0 Client ID**, the **OAuth 2.0 Certificate ID**, and the full contents of `private.pem` in **OAuth 2.0 Private Key**.
</Step>
<Step>
(Optional) In the **Custom Employee Fields** field, enter a comma-separated list of custom employee field IDs to include in the sync (e.g. `custentity_zone,custentity_cost_center`). See [Custom Fields](#custom-fields) for details.
</Step>
<Step>
Click **Save**.
</Step>
<Step>
The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
</Step>
</Steps>

**Done.** Your NetSuite connector is now pulling access data into C1.

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your NetSuite connector deployment:

#### Secrets configuration

```yaml expandable
# baton-netsuite-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-netsuite-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>
  
  # NetSuite credentials
  BATON_ACCOUNT_ID: <NetSuite account ID>
  BATON_CONSUMER_KEY: <NetSuite consumer key>
  BATON_CONSUMER_SECRET: <NetSuite consumer secret>
  BATON_TOKEN_KEY: <NetSuite token key>
  BATON_TOKEN_SECRET: <NetSuite token secret>

  # Or, for OAuth 2.0 client credentials, replace the four TBA values above with:
  # BATON_AUTH_METHOD: oauth2-client-credentials
  # BATON_NETSUITE_OAUTH2_CLIENT_ID: <NetSuite integration client ID>
  # BATON_NETSUITE_OAUTH2_CERTIFICATE_ID: <Certificate ID from the M2M mapping>
  # BATON_NETSUITE_OAUTH2_PRIVATE_KEY: |
  #   -----BEGIN PRIVATE KEY-----
  #   <contents of private.pem>
  #   -----END PRIVATE KEY-----

  # Optional: comma-separated custom employee field IDs
  # BATON_CUSTOM_EMPLOYEE_FIELDS: custentity_zone,custentity_cost_center

  # Optional: set to true to allow revoking the last role even when the employee has login access
  # BATON_REVOKE_ACCESS_WITH_LAST_ROLE: true

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: true
```

See the connector's README or run `--help` to see all available configuration flags and environment variables.

#### Deployment configuration

```yaml expandable
# baton-netsuite.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: baton-netsuite
  labels:
    app: baton-netsuite
spec:
  selector:
    matchLabels:
      app: baton-netsuite
  template:
    metadata:
      labels:
        app: baton-netsuite
        baton: true
        baton-app: netsuite
    spec:
      containers:
      - name: baton-netsuite
        image: public.ecr.aws/conductorone/baton-netsuite:latest
        imagePullPolicy: IfNotPresent
        env:
        - name: BATON_HOST_ID
          value: baton-netsuite
        envFrom:
        - secretRef:
            name: baton-netsuite-secrets
```

</Steps>

**Done.** Your NetSuite connector is now pulling access data into C1.

## Custom Fields

The NetSuite connector supports syncing custom employee fields. Custom field values are added to the user profile attributes in C1, making them available for access reviews and reporting.

### Finding custom field IDs

Custom field IDs can be found in NetSuite under **Customization** > **Lists, Records, & Fields** > **Entity Fields**. The field ID is shown in the **ID** column (e.g. `custentity_zone`).

### Permissions for custom fields

Each custom field in NetSuite has its own field-level access controls, separate from the base employee record permissions. The connector's role must have at least **View-level access** to each custom field being synced.

Field access is configured per-field in NetSuite:

1. Navigate to **Customization** > **Lists, Records, & Fields** > **Entity Fields**.
2. Click on the custom field.
3. Go to the **Access** subtab.
4. Ensure the connector's role has **View**, **Run**, or **Edit** access.

<Tip>
The connector validates access to each custom field at startup. If a field is not accessible, the connector will report a clear error message indicating which field could not be accessed.
</Tip>
