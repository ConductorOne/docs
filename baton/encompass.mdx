## Capabilities

| Resource | Sync | Provision |
| :--- | :--- | :--- |
| Account | <Icon icon="square-check" iconType="solid"  color="#c937ae"/> | <Icon icon="square-check" iconType="solid"  color="#c937ae"/> |
| Group | <Icon icon="square-check" iconType="solid"  color="#c937ae"/> | <Icon icon="square-check" iconType="solid"  color="#c937ae"/> |
| Organization | <Icon icon="square-check" iconType="solid"  color="#c937ae"/> | |
| Persona | <Icon icon="square-check" iconType="solid"  color="#c937ae"/> | <Icon icon="square-check" iconType="solid"  color="#c937ae"/> |

**Additional functionality:**

<Icon icon="square-check" iconType="solid"  color="#c937ae"/> Supports [automatic account provisioning and deprovisioning](/product/admin/account-provisioning)

<Icon icon="square-check" iconType="solid"  color="#c937ae"/> When a new account is created by C1, the account's password will be sent to a [vault](/product/admin/vaults)

**Notes:**

- The connector syncs Encompass internal users and personas. It does not sync external users or loan roles.
- The connector syncs organizations read-only. C1 shows each organization under its parent organization, with a single member entitlement for the users placed in the organization and, inherited, the users of its child organizations.
- An organization that is a member of a group makes its users members of that group. At the **Current** level, only the users placed directly in the organization become members. At the **Recursive** level, the users of its child organizations become members too.
- C1 shows a group membership that comes from an organization as inherited from that organization, and only when the Organization resource type is synced.
- C1 offers **Revoke** on a group membership inherited from an organization. The revoke task completes, but Encompass does not change and the membership returns on the next sync. To remove an inherited membership, remove the user from that organization, or the organization from the group, in Encompass Admin.
- C1 does not revoke organization memberships. When a revoke, such as **Revoke all access**, includes an organization membership, C1 creates a manual task for it. Complete it by removing the user from the organization in Encompass Admin.
- Encompass requires at least one persona per user, so revoking the last persona of a user fails. To replace it, assign the new persona first, then revoke the old one.
- To create an account, C1 asks for a first name, last name, email, username, working folder, organization and persona. **Organization** takes the ID of an Encompass organization (`0` is the root organization), and **Personas** takes the ID of a single persona. **Job Title** and **Employee ID** are optional.
- The connector generates a random password of 8 to 50 characters for each new account.
- Creating an account for a username that already exists in Encompass returns the existing account instead of creating a new one.
- Deprovisioning an account deletes the user from Encompass. It does not disable the user.

## Gather Encompass configuration information

Configuring the connector requires you to pass in information from Encompass. Gather these configuration details before you move on.

Here's the information you'll need:

- Base URL
- Client ID
- Client Secret
- Password
- Username, in the format `user_name@encompass:instance_id`

<Warning>
The Encompass user needs the **Super Administrator** or **Administrator** persona and must belong to the root organization. Encompass returns only the users of the caller's organization and its child organizations, so a user outside the root organization syncs only part of your users. If no users come back, the sync fails with `the users list is empty although the configured user is itself a user; check that it belongs to the root organization`.

The connector requests the `lp` (Lending Platform) scope, so the API key and the user need access to it.
</Warning>

See the Encompass docs for information on how to acquire credentials: [View the documentation](https://developer.icemortgagetechnology.com/developer-connect/docs/authentication#resource-owner-password-credentials)

## Configure the Encompass connector

<Warning>
To complete this task, you'll need:

- The **Connector Administrator** or **Super Administrator** role in C1
- Access to the set of Encompass configuration information gathered by following the instructions above
</Warning>

<Tabs>
<Tab title="Cloud-hosted">
**Follow these instructions to use a built-in, no-code connector hosted by C1.**

<Steps>
  <Step>
  In C1, navigate to **Apps** > **Connectors** and click **Browse connectors**.
  </Step>
  <Step>
  Search for **Encompass** and click **Add**.
  </Step>
  <Step>
  Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).

  If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
  </Step>
  <Step>
  Set the connector's **Name** and, optionally, a **Description**.
  </Step>
  <Step>
  Click the pencil icon next to **Owners** to choose who can configure and manage this connector.

  Make sure any user who you select as a connector owner has either the Connector Admin or Super Admin user role in C1, as this is required to manage the connector.
  </Step>
  <Step>
  Click **Add**. The connector is created and its configuration page opens.
  </Step>
  <Step>
  Find the **Settings** area of the page and click **Edit**.
  </Step>
  <Step>
  Enter the configuration information from the previous section.
  </Step>
  <Step>
  Click **Save**.
  </Step>
  <Step>
  The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
  </Step>
</Steps>

**Done.** Your Encompass connector is now pulling access data into C1.

</Tab>
<Tab title="Self-hosted">
**Follow these instructions to use the Encompass connector, hosted and run in your own environment.**

When running in service mode on Kubernetes, a self-hosted connector maintains an ongoing connection with C1, automatically syncing and uploading data at regular intervals. This data is immediately available in the C1 UI for access reviews and access requests.

* [Official connector registry](https://dist.conductorone.com/ConductorOne/baton-encompass): For stable binaries (Windows/Linux/macOS) and container images.

### Step 1: Set up a new Encompass connector

<Steps>
  <Step>
  In C1, navigate to **Apps** > **Connectors** and click **Browse connectors**.
  </Step>
  <Step>
  Search for **Baton** and click **Add**.
  </Step>
  <Step>
  Choose where to add the connector: **Create a new app**, or **Add to an existing app** (then select the app).

  If you're creating a new app, choose whether to link it to an application discovered from your identity provider: select **Yes** and pick the IdP application, or **No** to continue with just the connector.
  </Step>
  <Step>
  Set the connector's **Name** and, optionally, a **Description**.
  </Step>
  <Step>
  Click the pencil icon next to **Owners** to choose who can configure and manage this connector.

  Make sure any user who you select as a connector owner has either the Connector Admin or Super Admin user role in C1, as this is required to manage the connector.
  </Step>
  <Step>
  Click **Add**. The connector is created and its configuration page opens.
  </Step>
  <Step>
  In the **Settings** area of the page, click **Edit**.
  </Step>
  <Step>
  Click **Rotate** to generate a new Client ID and Secret.

  Carefully copy and save these credentials. We'll use them in Step 2.
  </Step>
</Steps>

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your Encompass connector deployment:

#### Secrets configuration

```yaml expandable
# baton-encompass-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-encompass-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>

  # Encompass config
  BATON_ENCOMPASS_BASE_URL: <The base URL of the Encompass instance. This should include the protocol (https://).>
  BATON_ENCOMPASS_CLIENT_ID: <The client ID of the Encompass instance.>
  BATON_ENCOMPASS_CLIENT_SECRET: <The client secret of the Encompass instance.>
  BATON_ENCOMPASS_PASSWORD: <The password of the Encompass user.>
  BATON_ENCOMPASS_USERNAME: <The fully qualified Encompass username, in the format user_name@encompass:instance_id (for example user1@encompass:BE1111234).>

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: "true"
```

Run `--help` to see all available configuration flags and environment variables.

#### Deployment configuration

```yaml expandable
# baton-encompass.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: baton-encompass
  labels:
    app: baton-encompass
spec:
  selector:
    matchLabels:
      app: baton-encompass
  template:
    metadata:
      labels:
        app: baton-encompass
        baton: "true"
        baton-app: encompass
    spec:
      containers:
      - name: baton-encompass
        image: public.ecr.aws/conductorone/baton-encompass:latest
        imagePullPolicy: IfNotPresent
        env:
        - name: BATON_HOST_ID
          value: baton-encompass
        envFrom:
        - secretRef:
            name: baton-encompass-secrets
```

### Step 3: Deploy the connector

<Steps>
  <Step>
  Create a namespace in which to run C1 connectors (if desired), then apply the secret config and deployment config files.
  </Step>
  <Step>
  Check that the connector data uploaded correctly. In C1, click **Apps**. On the **Applications** tab, locate and click the name of the application you added the Encompass connector to. Encompass data should be found on the **Entitlements** and **Accounts** tabs.
  </Step>
</Steps>

**Done.** Your Encompass connector is now pulling access data into C1.
