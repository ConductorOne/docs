| Accounts | <Icon icon="square-check" iconType="solid" color="#65DE23"/> | |
| Organizations | <Icon icon="square-check" iconType="solid" color="#65DE23"/> | |
| Roles | <Icon icon="square-check" iconType="solid" color="#65DE23"/> | <Icon icon="square-check" iconType="solid" color="#65DE23"/> |

{/* AUTO-GENERATED:END - capabilities */}

**Notes:**

- Accounts are synced from WorkOS's User Management (AuthKit) API. WorkOS Directory Sync users and groups (mirrored from Okta, Microsoft Entra, Google Workspace, or another IdP) are intentionally not synced — those identities belong to your customers' end-users, not your workforce. Manage upstream IdP identities through that IdP's own ConductorOne connector.
- Roles are scoped to an organization. Each WorkOS organization defines its own set of roles, and a user holds at most one role per organization.
- Provisioning is at the role level. Granting a role places the user in the organization with that role; revoking a role removes the user from the organization. See [Understanding roles in WorkOS](#understanding-roles-in-workos) for the full model.

## Understanding roles in WorkOS

WorkOS bundles "in the organization" with "has this role" into a single concept: an **Organization Membership**. Every membership inseparably carries exactly one role. There is no "in the org but role-less" state.

The connector models this directly:

- A WorkOS **Organization** is a container in ConductorOne — it has no entitlements of its own and exists only to parent its roles.
- A WorkOS **Role** is the unit of access. Granting a role to a user creates (or updates) their organization membership.
- **Revoking a role removes the user from the organization entirely.** WorkOS has no API to demote a role without choosing a replacement, so the only correct revoke is a full membership deactivation. To restore the user with a different role, grant the new role.

This is a deliberate consequence of WorkOS's data model, not a connector limitation.

## Gather WorkOS credentials

<Warning>
To configure the WorkOS connector, you need administrator access to the WorkOS Dashboard for the environment (staging or production) you want to integrate.
</Warning>

<Steps>
  <Step>
    Sign in to the [WorkOS Dashboard](https://dashboard.workos.com) and select the environment you want to connect (staging or production).

    <Tip>
    Each WorkOS environment has its own API keys. The connector targets a single environment. If you want both staging and production in ConductorOne, set up two connectors with two different keys.
    </Tip>
  </Step>

  <Step>
    Create a secret API key:

    1. Navigate to **API Keys** in the left sidebar.
    2. Click **Create Key**.
    3. Enter a name: `ConductorOne`.
    4. Click **Create Key**.
    5. Copy the key, which begins with `sk_`, and save it securely. You won't be able to retrieve it again after closing the dialog.

    <Warning>
    The secret API key grants full access to all WorkOS resources in the selected environment, including the ability to create, update, and deactivate organization memberships. ConductorOne uses this access to provision and deprovision role assignments. **If you do not want ConductorOne to perform these tasks, do not create this key.**
    </Warning>
  </Step>
</Steps>

For more information, see the [WorkOS API authentication docs](https://workos.com/docs/reference/authentication).

## Configure the WorkOS connector

<Tabs>
  <Tab title="Cloud-hosted">
    Follow these instructions to use a built-in, no-code connector hosted by ConductorOne.

    <Steps>
      <Step>
        In ConductorOne, navigate to **Integrations** > **Connectors** and click **Add connector**.
      </Step>

      <Step>
        Search for **WorkOS** and click **Add**.
      </Step>

      <Step>
        Choose how to set up the new WorkOS connector:

        - Add the connector to a currently unmanaged app (select from the list of apps that were discovered in your identity, SSO, or federation provider that aren't yet managed with ConductorOne)
        - Add the connector to a managed app (select from the list of existing managed apps)
        - Create a new managed app
      </Step>

      <Step>
        Set the owner for this connector. You can manage the connector yourself, or choose someone else from the list of ConductorOne users. Setting multiple owners is allowed.

        If you choose someone else, ConductorOne will notify the new connector owner by email that their help is needed to complete the setup process.
      </Step>

      <Step>
        Click **Next**.
      </Step>

      <Step>
        Find the **Settings** area of the page and click **Edit**.
      </Step>

{/* AUTO-GENERATED:START - config-params
     Generated from config_schema.json. Do not edit manually. */}

      <Step>
        Paste the credentials into the relevant fields:

        - **API Key**: The WorkOS secret API key you created (starts with `sk_`)
      </Step>

{/* AUTO-GENERATED:END - config-params */}

      <Step>
        Click **Save**.
      </Step>

      <Step>
        The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
      </Step>
    </Steps>

    **That's it!** Your WorkOS connector is now pulling access data into ConductorOne.
  </Tab>

  <Tab title="Self-hosted">
    Follow these instructions to use the [WorkOS](https://github.com/ConductorOne/baton-workos) connector, hosted and run in your own environment.

    When running in service mode on Kubernetes, a self-hosted connector maintains an ongoing connection with ConductorOne, automatically syncing and uploading data at regular intervals. This data is immediately available in the ConductorOne UI for access reviews and access requests.

### Resources

    * [Official download center](https://dist.conductorone.com/ConductorOne/baton-workos): For stable binaries (Windows/Linux/macOS) and container images.

    * [GitHub repository](https://github.com/conductorone/baton-workos): Access the source code, report issues, or contribute to the project.

    ### Step 1: Set up a new WorkOS connector

    <Steps>
      <Step>
        In ConductorOne, navigate to **Integrations** > **Connectors** > **Add connector**.
      </Step>

      <Step>
        Search for **Baton** and click **Add**.
      </Step>

      <Step>
        Choose how to set up the new WorkOS connector:

        - Add the connector to a currently unmanaged app (select from the list of apps that were discovered in your identity, SSO, or federation provider that aren't yet managed with ConductorOne)
        - Add the connector to a managed app (select from the list of existing managed apps)
        - Create a new managed app
      </Step>

      <Step>
        Set the owner for this connector. You can manage the connector yourself, or choose someone else from the list of ConductorOne users. Setting multiple owners is allowed.

        If you choose someone else, ConductorOne will notify the new connector owner by email that their help is needed to complete the setup process.
      </Step>

      <Step>
        Click **Next**.
      </Step>

      <Step>
        In the **Settings** area of the page, click **Edit**.
      </Step>

      <Step>
        Click **Rotate** to generate a new Client ID and Secret.

        Carefully copy and save these credentials. We'll use them in Step 2.
      </Step>
    </Steps>

    ### Step 2: Create Kubernetes configuration files

    Create two Kubernetes manifest files for your WorkOS connector deployment:

    #### Secrets configuration

    ```yaml expandable
    # baton-workos-secrets.yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: baton-workos-secrets
    type: Opaque
    stringData:
      # ConductorOne credentials
      BATON_CLIENT_ID: <ConductorOne client ID>
      BATON_CLIENT_SECRET: <ConductorOne client secret>

      # WorkOS credentials
      BATON_API_KEY: <Your WorkOS secret API key>

      # Optional: include if you want ConductorOne to provision access using this connector
      BATON_PROVISIONING: true
    ```

    See the connector's README or run `--help` to see all available configuration flags and environment variables.

    #### Deployment configuration

    ```yaml expandable
    # baton-workos.yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: baton-workos
      labels:
        app: baton-workos
    spec:
      selector:
        matchLabels:
          app: baton-workos
      template:
        metadata:
          labels:
            app: baton-workos
            baton: "true"
            baton-app: workos
        spec:
          containers:
          - name: baton-workos
            image: ghcr.io/conductorone/baton-workos:latest
            imagePullPolicy: IfNotPresent
            env:
            - name: BATON_HOST_ID
              value: baton-workos
            envFrom:
            - secretRef:
                name: baton-workos-secrets
    ```

    ### Step 3: Deploy the connector

    <Steps>
      <Step>
        Create a namespace in which to run ConductorOne connectors (if desired), then apply the secret config and deployment config files.
      </Step>

      <Step>
        Check that the connector data uploaded correctly. In ConductorOne, click **Applications**. On the **Managed apps** tab, locate and click the name of the application you added the WorkOS connector to. WorkOS data should be found on the **Entitlements** and **Accounts** tabs.
      </Step>
    </Steps>

    **That's it!** Your WorkOS connector is now pulling access data into ConductorOne.
  </Tab>
</Tabs>
