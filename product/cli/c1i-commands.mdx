## Overview

c1i interacts with the C1 API to manage identities, apps, access, policies, automations, MCP servers, and more.

List and search commands output NDJSON, one JSON object per line. Most other commands output pretty JSON, but some delete and action commands, such as `apps delete` and `tasks approve`, print a one-line confirmation instead. See [Output conventions](/product/cli/c1i#output-conventions) for `auth`, `docs`, and `api` output.

| Command | Description |

| [`roles`](#roles) | List and inspect IAM roles (find role IDs for `auth login --scoped-role`). |
| [`users`](#users) | Search, list, and get C1 users. |

## Global flags

Every command accepts these flags.

| Flag | Description |
| :--- | :--- |
| `--url string` | C1 tenant URL; https required. Precedence: `--url`, `C1I_URL`, then `~/.c1i.yaml`. |
| `--fields string` | Comma-separated JSON fields to keep in read output (dot-paths). Prefer it over `jq` for simple projection. |
| `--max-retries int` | Retries for transient API failures (429/5xx); 0 disables (default 4). |
| `--error-format string` | Error output format: `text` or `json` (default `text`). |
| `--dry-run` | Preview C1 REST mutations (method, path, body) without sending them. `mcp gateway call` and `auth login` reject it (exit 2). |
| `--debug` | Trace HTTP requests (method, URL, status, timing) to stderr. |
| `-h`, `--help` | Help for any command. |

Each global flag also reads a `C1I_*` environment variable: `C1I_URL`, `C1I_FIELDS`, `C1I_MAX_RETRIES`, `C1I_ERROR_FORMAT`, `C1I_DRY_RUN`, and `C1I_DEBUG`.

| [`c1i docs guide`](#docs-guide) | Print an embedded, task-oriented runbook for a common workflow. |
| [`c1i docs agents`](#docs-agents) (alias `skill`) | Print agent-facing conventions: output contracts, exit codes, and pagination. |

### `docs endpoints`

Optionally filter by a pattern.

**Usage:**

```bash
c1i docs endpoints [--filter <pattern>]
```

| Flag | Description |
| :--- | :--- |
| `--filter string` | Filter endpoints by pattern. |

### `docs guide`

Print an embedded, task-oriented runbook: a numbered sequence of c1i commands for a common end-to-end workflow. Run it with no argument to list the available guide names and their purposes. Guides are static content in the c1i binary, so unlike `docs search` and `docs page` they make no network call.

**Usage:**

```bash
c1i docs guide [name]
```

**Example:**

```bash
c1i docs guide register-mcp-server
```

### `docs agents`

Print a short, agent-facing document covering the conventions that `--help` text can't: getting the tenant right, output contracts, exit codes, pagination, and when to prefer a first-class command over `c1i api`. It doesn't list every command or flag; run `c1i --help`, `c1i <group> --help`, or `c1i <group> <command> --help` for those.

The output opens with a YAML front-matter block (name, description, version, and required binaries) that some agent harnesses parse automatically, followed by plain Markdown. `skill` remains an alias for backward compatibility, so `c1i docs skill` still works.

| Flag | Description |
| :--- | :--- |
| `-o`, `--output string` | Write to a file instead of stdout. |

**Examples:**

```bash
# Print the agent doc to stdout
c1i docs agents

# Write directly to a file for Claude Code
c1i docs agents -o .claude/skills/c1i/SKILL.md

# Write as a Cursor project rule
c1i docs agents -o .cursor/rules/c1i.md
```

For step-by-step setup instructions for Claude Code, Cursor, and other agents, see [Use c1i with AI agents](/product/cli/c1i-agent-skills).

<Callout icon="globe" color="#c937ae" iconType="regular">These examples use `conductor.one`. If your organization is on the EU data residency instance, substitute `c1eu.ai` in URLs, client IDs, and hostnames.</Callout>

## Auth

Log in, check which identity and credential c1i is using, and mint access tokens.

c1i reads credentials from `C1I_CLIENT_ID` and `C1I_CLIENT_SECRET`, then the OS keyring, then a `0600` file, and caches each access token it mints until it's close to expiry; see [Credential storage](/product/cli/c1i#credential-storage). `auth token` and `mcp gateway` always mint a fresh token. A cached token the server rejects (clock skew, or a revocation) is dropped and re-minted automatically, once.

| Command | Description |
| :--- | :--- |
| [`c1i auth login`](#auth-login) | Authenticate via browser or API credentials. |
| `c1i auth logout` | Remove stored c1i credentials for the current URL from both the OS keyring and the file fallback. Environment variables (`C1I_CLIENT_ID`, `C1I_CLIENT_SECRET`) are not affected. |
| `c1i auth status` | Check whether valid C1 credentials are stored and working. Reports which source (environment, keyring, or file) served the active credentials. |
| [`c1i auth whoami`](#auth-whoami) | Show the authenticated principal's identity, roles, permissions, and feature flags. |
| [`c1i auth token`](#auth-token) | Print a short-lived OAuth2 bearer token for driving raw API calls yourself. |

### `auth login`

Authenticate to C1. Opens a browser for OAuth device flow authorization, or accepts credentials directly.

| Flag | Description |
| :--- | :--- |
| `--client-id string` | C1 API client ID (skips browser login). |
| `--client-secret string` | C1 API client secret (skips browser login). |
| `--choose-roles` | Choose the browser-login credential's roles from a menu after approval (needs a terminal). `--choose-roles=false` skips the role question. |
| `--scoped-role stringArray` | Restrict the browser-login credential to a role, by name (such as `basic-user`) or ID (repeatable). |

A browser login creates a credential with all of your roles; see [Limit the credential to specific roles](/product/cli/c1i#limit-the-credential-to-specific-roles). `--scoped-role` takes a role name or a role ID from [`c1i roles list`](#roles). A name that matches no role you can scope to exits with code 2 before c1i creates your credential. An unknown role ID exits with code 4. `--choose-roles` and `--scoped-role` can't be combined, and neither works with `--client-id` and `--client-secret`. `auth login` rejects `--dry-run` (exit 2), because it can't preview creating a credential.

### `auth whoami`

Show the authenticated principal: principal ID, user ID (a service principal might carry only the principal ID), counts of roles, permissions, and tenant feature flags, and display name and email when the user lookup succeeds. Useful for agents and scripts that need to confirm identity before making other API calls.

| Flag | Description |
| :--- | :--- |
| `-v`, `--verbose` | Include full roles, permissions, and features arrays. |

By default, `whoami` returns a compact summary. `--verbose` replaces that summary with the raw introspect payload, which includes the full role, permission, and feature lists but not the summary's counts, `displayName`, or `email`.

Both modes add two keys that c1i resolves itself: `tenant`, the base URL this invocation targets, and `tenantSource`, where it came from (`flag`, `env`, or `config`). They appear only after your credentials are proven against that tenant, so check them before a write:

```bash
c1i auth whoami --fields tenant
```

### `auth token`

Mint and print a short-lived OAuth2 bearer token from your stored credentials, for driving raw API calls yourself (for example, with `curl`). A new token is minted on each invocation — it is not written to disk.

| Flag | Description |
| :--- | :--- |
| `--json` | Print a JSON object with `access_token`, `token_type`, and `expires_at` (RFC3339) instead of just the access token. |

By default only the access token is printed (newline-terminated), so it composes directly into another command:

```bash
curl -H "Authorization: Bearer $(c1i auth token)" \
  https://your-tenant.conductor.one/api/v1/apps
```

The token is audience-scoped to the C1 API host.

## Apps

Create, inspect, and delete applications, and manage their owners.

| Command | Description |
| :--- | :--- |
| `c1i apps list` | List applications. [Paginates](#pagination-and-limits). |
| `c1i apps get <app-id>` | Get a single app by ID. |
| [`c1i apps create`](#apps-create) | Create a new app. |
| `c1i apps delete <app-id>` | Soft-delete an app by ID. The app is marked deleted and drops out of normal listings, but the record is retained for audit. |
| [`c1i apps owners`](#apps-owners) | List an app's owners. |
| [`c1i apps add-owner`](#apps-add-owner) | Add one owner to an app. |
| [`c1i apps remove-owner`](#apps-remove-owner) | Remove one owner from an app. |
| [`c1i apps set-owners`](#apps-set-owners) | Set the owners of an app, replacing the full owner list. |

### `apps create`

Create a new app — a plain, unmanaged container you can register MCP servers under. Only `--display-name` is required; app owners are managed separately via `set-owners`, not at create time.

**Usage:**

```bash
c1i apps create --display-name <name> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--display-name string` | Display name for the new app. (Required.) |
| `--description string` | Description for the new app. |

The created app is returned as pretty JSON under an `app` key.

**Example:**

```bash
APP_ID=$(c1i apps create --display-name "Google Workspace" | jq -r .app.id)
```

### `apps owners`

[Paginates](#pagination-and-limits).

**Usage:**

```bash
c1i apps owners <app-id> [flags]
```

Use this to verify an owner change. Owner provisioning is asynchronous, so a change can take roughly 45 to 150 seconds to appear. Most apps already have at least one owner, because `apps create` assigns its caller as an owner. A well-formed app ID that doesn't exist returns zero rows and exits `0`, not `4`.

### `apps add-owner`

Add one user as an app owner without changing the rest of the owner list. Unlike `set-owners`, it can't drop an owner that someone else added in the meantime.

**Usage:**

```bash
c1i apps add-owner <user-id> --app-id <app-id>
```

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Application ID to add the owner to. (Required.) |

Owner changes are provisioned asynchronously; verify with `c1i apps owners <app-id>`. Honors `--dry-run`.

### `apps remove-owner`

Remove one user as an app owner without changing the rest of the owner list. The creator that `apps create` assigned can remain an owner, so check `c1i apps owners <app-id>` first if that matters.

**Usage:**

```bash
c1i apps remove-owner <user-id> --app-id <app-id>
```

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Application ID to remove the owner from. (Required.) |

Owner changes are provisioned asynchronously; verify with `c1i apps owners <app-id>`. Honors `--dry-run`.

### `apps set-owners`

Set the complete list of owners for an app, replacing any existing owners.

**Usage:**

```bash
c1i apps set-owners <app-id> --user-id <user-id> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--user-id stringArray` | C1 user ID to set as owner (repeatable; replaces the full owner list). (Required.) |
| `--wait` | Block and poll until every requested owner appears, or `--wait-timeout` elapses. |
| `--wait-timeout duration` | Max time to wait with `--wait` (default `4m0s`). |

Owner changes are provisioned asynchronously — this command returns as soon as the request is accepted, but the new owners can take up to a few minutes to actually appear. Pass `--wait` to block until they do.

**Example:**

```bash
c1i apps set-owners app_abc123 --user-id user_1 --user-id user_2 --wait
```

| Command | Description |

| `--query string` | Search query. |

**Usage:**

```bash

```

| Flag | Description |

### `entitlements create`

Create an app entitlement, plus the app resource type and resource it points at, as up to three requests in order. Pass `--resource-type-id` to reuse an existing resource type, and `--resource-id` to reuse an existing resource. Outputs pretty JSON under `appEntitlementView`.

**Usage:**

```bash
c1i entitlements create --app-id <app-id> --display-name <name> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Application ID to create the entitlement on. (Required.) |
| `--display-name string` | Display name for the new entitlement; also names the resource type and resource that c1i creates. (Required.) |
| `--description string` | Description for the new entitlement. |
| `--alias string` | Alias for the new entitlement; exact-match queryable. |
| `--slug string` | Slug for the new entitlement, such as `member`. |
| `--duration-grant string` | Maximum grant duration as a protobuf duration in seconds, such as `3600s`; omit for standing access. `1h` is refused. |
| `--owner-id stringArray` | C1 user ID to own the new entitlement (repeatable). |
| `--resource-type string` | Kind of resource type to create: `ROLE`, `GROUP`, `LICENSE`, `PROJECT`, `CATALOG`, `CUSTOM`, `VAULT`, or `PROFILE_TYPE` (default `CUSTOM`). |
| `--resource-type-display-name string` | Display name for the resource type this command creates (default: `--display-name`). |
| `--resource-type-id string` | Existing app resource type to reuse instead of creating one. |
| `--resource-display-name string` | Display name for the resource this command creates (default: `--display-name`). |
| `--resource-id string` | Existing app resource to reuse instead of creating one; requires `--resource-type-id`. |

Passing `--resource-type` or `--resource-type-display-name` together with `--resource-type-id` is a usage error (exit 2), as is `--resource-id` without `--resource-type-id`. Only the `CUSTOM` resource type can repeat on one app, so reuse an existing type with `--resource-type-id` for any other kind.

There is no rollback. If a later request fails, the objects that earlier ones created still exist; the error names them and the flags that reuse them. `--dry-run` previews every request in the sequence. Owner provisioning is asynchronous.

**Example:**

```bash
c1i entitlements create --app-id "$APP_ID" \
  --display-name "Payroll admin" --resource-type-display-name "Payroll role" \
  --slug member --alias payroll_admin
```

### `entitlements proxy-bindings`

A proxy binding is a visibility and tracking link from a source entitlement to a destination entitlement — it does not grant access or configure delegated provisioning. The public REST API has no list endpoint for proxy bindings; the C1 Console discovers them through an internal search service that isn't part of the public API.

| Command | Description |
| :--- | :--- |
| [`c1i entitlements proxy-bindings get`](#entitlements-proxy-bindings-get) | Get an entitlement proxy binding. |
| [`c1i entitlements proxy-bindings create`](#entitlements-proxy-bindings-create) | Create an entitlement proxy binding. |
| [`c1i entitlements proxy-bindings delete`](#entitlements-proxy-bindings-delete) | Delete an entitlement proxy binding. |

Each subcommand takes the same four flags to identify the binding:

| Flag | Description |
| :--- | :--- |
| `--source-app-id string` | Application ID of the source entitlement. (Required.) |
| `--source-entitlement-id string` | Source entitlement ID. (Required.) |
| `--destination-app-id string` | Application ID of the destination entitlement. (Required.) |
| `--destination-entitlement-id string` | Destination entitlement ID. (Required.) |

### `entitlements proxy-bindings get`

**Usage:**

```bash
c1i entitlements proxy-bindings get --source-app-id <app-id> \
  --source-entitlement-id <entitlement-id> --destination-app-id <app-id> \
  --destination-entitlement-id <entitlement-id>
```

### `entitlements proxy-bindings create`

**Usage:**

```bash
c1i entitlements proxy-bindings create --source-app-id <app-id> \
  --source-entitlement-id <entitlement-id> --destination-app-id <app-id> \
```

## Grants

Query access grants: the bindings between accounts or users and entitlements. Answers "who has access to what".

### `grants list`

Search and list grants. At least one filter is required. [Paginates](#pagination-and-limits).

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Filter to grants in this application. |
| `--entitlement-id string` | Filter to grants of this entitlement (requires `--app-id`). |
| `--user-id string` | Filter to grants held by this C1 identity user. |
| `--app-user-id string` | Filter to grants held by this app account (app user). |
| `--wait` | Block and poll every page until the same grants come back `--wait-stable` times in a row, or `--wait-timeout` elapses. |
| `--wait-stable int` | Consecutive identical reads that `--wait` requires before printing (minimum 2; default 3). |
| `--wait-min int` | Minimum matching grants that `--wait` requires before it can settle (0 = an empty result can settle). |
| `--wait-timeout duration` | Maximum time to wait with `--wait` (default `4m0s`). |

Grant provisioning is asynchronous, so a read taken right after a grant or revoke can catch the set mid-change. With `--wait`, c1i re-reads every page of the match every 5 seconds, regardless of `--limit`, and prints the settled set; progress goes to stderr, so stdout stays pure NDJSON. An empty result is stable: if you are waiting for a grant you just made, pass `--wait-min 1` so the wait holds out for it instead of settling on zero rows.

**Examples:**

```bash
# Who holds an entitlement?
c1i grants list --app-id <app-id> --entitlement-id <entitlement-id>

# What does a C1 identity have across apps?
c1i grants list --user-id <user-id>
```

### `tasks approve`

Approve an access request task.

**Usage:**

```bash
c1i tasks approve <task-id> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--comment string` | Comment to include with the approval. |
| `--policy-step-id string` | Policy step to approve (defaults to the task's current step). |

If you omit `--policy-step-id`, c1i fetches and uses the task's currently executing step. If it can't determine the step, the command errors and asks you to pass `--policy-step-id`.

### `tasks deny`

Deny an access request task.

**Usage:**

```bash

```

| Flag | Description |
| :--- | :--- |
| `--comment string` | Comment to include with the denial. |
| `--policy-step-id string` | Policy step to deny (defaults to the task's current step). |

Unlike `approve`, `deny` doesn't require a step: if c1i can't determine the current step, it sends the denial without one.

### `tasks comment`

**Usage:**


## Policies

Manage policies — the objects that describe how C1 processes a task (an access request, a certification, a provisioning action): who approves it, what happens on escalation or timeout, and how the underlying resource gets provisioned.

| Command | Description |
| :--- | :--- |
| [`c1i policies list`](#policies-list) | List all policies. |
| [`c1i policies search`](#policies-search) | Search policies by display name, description, type, or deletion state. |
| [`c1i policies get`](#policies-get) | Get a single policy by ID. |
| [`c1i policies create`](#policies-create) | Create a new policy. |
| [`c1i policies update`](#policies-update) | Update a policy. |
| [`c1i policies delete`](#policies-delete) | Soft-delete a policy by ID. |
| [`c1i policies validate-cel`](#policies-validate-cel) | Check a CEL condition for compile errors. |

<Warning>
Creating or updating a policy with an empty (or missing) steps list succeeds with no validation error, and silently produces a deny-everything policy. The `create` and `update` commands refuse to send a request with empty or missing steps unless you pass `--allow-deny-all` to confirm that's what you want.
</Warning>

A policy's shape is deeply nested: `policySteps` holds an ordered list of steps, each one of seven types (approval, provision, accept, reject, wait, form, action), and an approval step's approver is itself one of several kinds (users, manager, group, app owners, self, entitlement owners, expression, webhook, resource owners, agent). You can read back all seven types, but `create` and `update` refuse two of them client-side with exit code 2, before sending a request: `a "provision" step is never allowed in a policy body — it's read-only and server-computed` and `an "action" step is not supported by create/update yet`. Modeling the nested structure as flags would be unusable, so `create` and `update` take the nested pieces from a JSON file (or `-` for stdin), while flat top-level fields (display name, description, policy type) stay as flags.

### `policies list`

List every policy in the tenant, auto-paginating through the full result. [Paginates](#pagination-and-limits).

Unlike most list commands, this takes no query filter at all — only pagination. Use `search` for filtering.

Rows carry `step_kinds` (the kind of each step in the policy's baseline sequence) and `baseline_policy_id`, which together identify a tenant's auto-approval policy without matching on its display name. Search rows carry the same keys.

### `policies search`

Search policies by a fuzzy query (display name + description), an exact display-name match, one or more policy types, or include soft-deleted policies. [Paginates](#pagination-and-limits); `--page-size` defaults to 25.

| Flag | Description |
| :--- | :--- |
| `--query string` | Fuzzy search on display name and description. |
| `--display-name string` | Exact-ish (case-insensitive) display name match. |
| `--policy-type stringArray` | Filter by policy type, such as `grant`, `revoke`, or `certify` (repeatable). |
| `--include-deleted` | Include soft-deleted policies. This is the only listing command that can find one. |
| `--exclude-policy-id stringArray` | Policy ID to exclude from results (repeatable). |

**Usage:**

```bash

```

Unlike `list` and the default `search`, `get` returns a soft-deleted policy too (with `deletedAt` populated) rather than filtering it out.

### `policies validate-cel`

Check a CEL expression for compile errors, without creating or updating anything. Useful for testing a rule's `condition` before using it in `create` or `update`.

**Usage:**

```bash
c1i policies validate-cel <condition>
```

**Example:**

```bash
c1i policies validate-cel 'subject.role == "admin"'
```

Exits `0` for a valid condition, `2` for an invalid one — so `c1i policies validate-cel '<cond>' && ...` only continues past a condition that compiles.

<Note>
This validates the CEL environment rules run in (`subject`, `account`, `entitlement`, `task`) — not the same environment an approval step's `expression` approver runs in. An expression that's valid in one may not compile in the other.
</Note>

### `export events`

Export C1 system log events, in OCSF format, as an NDJSON stream with one event per line. c1i auto-paginates through the full result set. Redirect the output to a file to archive events or ship them to an external system. [Paginates](#pagination-and-limits).

| `--sort string` | Chronological order: `asc` (oldest first) or `desc` (default `asc`). |


## Upgrade

Check for and install a newer c1i release. The command is aliased as `update`.

c1i follows a release channel from the C1 distribution center (`dist.conductorone.com`); see [Upgrade c1i](/product/cli/c1i#upgrade-c1i). Before it replaces a standalone binary, it verifies the release manifest's Sigstore signature (signed by the release workflow run for that c1i tag) and the download's SHA-256 from that manifest. For a Homebrew, `go install`, or container install, `upgrade` prints that method's upgrade command and exits 0 without replacing anything.

| Flag | Description |
| :--- | :--- |
| `--channel string` | Release channel: `stable`, `latest`, or `preview` (default `stable`). |
| `--check` | Print a JSON report of whether a newer release is available; change nothing. |
| `-y`, `--yes` | Skip the confirmation prompt. Required when stdin is not a terminal. |

`--check` prints one JSON object with these keys:

| Key | Description |
| :--- | :--- |
| `current` | The version you run. |
| `latest` | The newest version on the channel. |
| `channel` | The release channel checked. |
| `update_available` | `true` when a newer release exists. |
| `install_method` | How c1i was installed: `standalone`, `homebrew`, `go-install`, `container`, `system`, or `windows`. |
| `upgrade_command` | The command that upgrades this install. Present only for a Homebrew, `go install`, or container install. |

Windows and system installs print a hint but no `upgrade_command`.

With the global `--dry-run` flag, `upgrade` fetches and verifies the release (index, manifest, signature, and TUF root) and checks that the install directory is writable. It then prints what it would download and replace. It takes no lock, doesn't prompt, and installs nothing.

`upgrade` treats the distribution center as a system beyond C1. A distribution center `404`, `429`, or `5xx` exits `4`, `5`, or `6`, and a same-path redirect loop exits `6`. Any other `4xx`, a refused redirect, a non-JSON `200`, or a TUF, signature, or checksum failure exits `8`.

## Service principals

## MCP servers

Register, configure, and inspect the MCP servers under a C1 app. C1 models an MCP server as a connector under an app, so you address one with `--app-id` plus its connector ID. Hosted servers run inside C1 from a catalog entry; external servers point at a third-party MCP URL. C1 seals auth secrets server-side, so reads only return `*_configured` booleans.

After you register a server, its tools start in the pending-review state. Approve them with [`c1i mcp tools approve`](#mcp-tools) before the gateway proxies calls to them.

| [`c1i mcp servers search`](#mcp-servers-search) | Search MCP servers within an app, with per-server tool counts. |
| [`c1i mcp servers register`](#mcp-servers-register) | Register a new hosted or external MCP server under an existing app. |

### `mcp servers register`

For a hosted server, browse [`catalog list`](#mcp-servers-catalog-list) and pass an entry's ID with `--catalog-id`. For an external server, pass `--server-url`.

**Usage:**

```bash
c1i mcp servers register --app-id <app-id> --type <hosted|external> \
  --display-name <name> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Application ID to register under. (Required unless `--print-config-template`.) |
| `--type string` | Server type: `hosted` or `external`. (Required unless `--print-config-template`.) |
| `--display-name string` | Display name. (Required unless `--print-config-template`.) |
| `--description string` | Description. |
| `--catalog-id string` | Catalog entry ID (hosted). |
| `--source-app-id string` | Source app ID for connector-backed hosted servers. |
| `--config-field stringArray` | Extra config field as `key=value` (hosted, repeatable). |
| `--server-url string` | External MCP server URL (external). |
| `--transport string` | Transport: `streamable-http` or `sse` (external). |
| `--auth string` | Auth method: `none`, `bearer-token`, `custom-header`, or `basic-auth`. OAuth2, AWS, and Google auth go through the `--*-config-file` flags. |
| `--bearer-token string` | Bearer token value (with `--auth bearer-token`). |
| `--header-name string` | Custom header name (with `--auth custom-header`). |
| `--header-value string` | Custom header value (with `--auth custom-header`). |
| `--basic-auth-username string` | Basic-auth username (with `--auth basic-auth`). |
| `--basic-auth-password string` | Basic-auth password (with `--auth basic-auth`). |
| `--hosted-config-file string` | Full `hostedConfig` JSON (file, or `-` for stdin). |
| `--external-config-file string` | Full `externalConfig` JSON (file, or `-` for stdin). |
| `--print-config-template` | Print a ready-to-edit config skeleton for the `--auth` method (use with `--auth` and `--type`) instead of registering. |
| `--token-sharing string` | Token sharing: `shared` or `per-user`. |
| `--data-sensitivity string` | Data sensitivity: `public`, `internal`, `confidential`, or `restricted`. |
| `--tool-prefix string` | Prefix for exposed tool names. |
| `--require-tool-approval` | Per-server override for tool auto-approval (omit to leave unset). |
| `--user-id stringArray` | Integration owner user ID (repeatable). |

The `per-user` token-sharing mode works only with OAuth2 (authorization-code or passthrough), bearer-token, custom-header, and basic-auth methods. `register` requires `--app-id`; registering under a new managed app isn't reachable over REST.

**Examples:**

```bash
# Print an OAuth2 config skeleton to edit
c1i mcp servers register --print-config-template --auth oauth2 --type hosted

# Register an external server with a bearer token
c1i mcp servers register --app-id <app-id> --type external \
  --display-name "Example MCP" --server-url https://mcp.example.com/v1 \
  --auth bearer-token --bearer-token <token>
```

### `mcp servers delete`

This stops the connector, removes it from the tenant's MCP catalog, and revokes any per-user OAuth credentials issued against it. The connector record is retained for audit.

### `mcp tools approve`

Approve MCP tools by setting each tool's state to approved, which lets the MCP gateway proxy calls to them. Pass one or more tool IDs. The API has no batch approve, so c1i sends each ID as its own request and prints a confirmation line for each. If one fails, c1i still attempts the rest and exits non-zero.

**Usage:**

```bash
c1i mcp tools approve <tool-id>... --app-id <app-id> \
  --connector-id <connector-id> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--state string` | Target state: `pending`, `approved`, or `disabled` (default `approved`). |

**Example:**

```bash
# Approve every pending read-only tool on a connector
c1i mcp tools approve $(c1i mcp tools search --app-id <app-id> --connector-id <connector-id> \
  --classification read --state pending --fields id | jq -r .id) \
  --app-id <app-id> --connector-id <connector-id>
```

### `mcp tools delete`

The tool stays in the database for audit but is hidden from listings and unbound from any toolsets. Tools move to the removed state on their own during sync when they disappear from the upstream server; to block a tool without deleting it, use `c1i mcp tools approve --state disabled`.

**Usage:**

```bash
c1i mcp tools delete <tool-id> --app-id <app-id> --connector-id <connector-id>
```

### `mcp tools history`

Outputs NDJSON, one record per historical version. Each record carries the full tool snapshot at that point and the change-history envelope (actor, change kind, creation time, trace ID, system log event ID, and annotations). [Paginates](#pagination-and-limits); `--page-size` accepts up to 200.

**Usage:**

```bash
c1i mcp tools history <tool-id> --app-id <app-id> \
  --connector-id <connector-id> [flags]
```

## MCP classifiers

Manage the AI-governance classifier surfaces used with the MCP gateway (formerly called guardrails in c1i's user-facing CLI).

A classifier is a reusable, ordered rule cascade evaluated first-match-wins. Bind a classifier to an enforcement surface with `bindings create`; rules may reference tool gates. Templates instantiate curated classifiers (and their dependent gates) into a tenant-owned, editable classifier. The singleton `policy` surface — the tenant's one agent classifier policy — is separate from named classifiers.

`create` and `update` take JSON objects through `--body-file` (or `-` for stdin), preserving nested CEL rules, hooks, gates, and template parameters without a lossy flag translation. Updates require an explicit `--update-mask` as a safeguard — including `rules` in the mask replaces the entire ordered cascade.

| Command | Description |
| :--- | :--- |
| `c1i mcp classifiers list` | List classifiers. [Paginates](#pagination-and-limits). |
| `c1i mcp classifiers get <classifier-id>` | Get a classifier by ID. |
| [`c1i mcp classifiers create`](#mcp-classifiers-create) | Create a classifier from JSON. |
| [`c1i mcp classifiers update`](#mcp-classifiers-update) | Update selected classifier fields from a JSON object. |
| `c1i mcp classifiers delete <classifier-id>` | Delete a classifier. |
| `c1i mcp classifiers bindings list` | List classifier bindings. [Paginates](#pagination-and-limits). |
| [`c1i mcp classifiers bindings create`](#mcp-classifiers-bindings-create) | Bind a classifier to an enforcement surface. |
| `c1i mcp classifiers bindings delete <binding-id>` | Delete a classifier binding. |
| [`c1i mcp classifiers templates list`](#mcp-classifiers-templates-list) | List classifier templates. |
| [`c1i mcp classifiers templates get`](#mcp-classifiers-templates-get) | Get a classifier template revision. |
| [`c1i mcp classifiers templates instantiate`](#mcp-classifiers-templates-instantiate) | Instantiate a template into a tenant-owned, editable classifier. |
| [`c1i mcp classifiers templates add-rule`](#mcp-classifiers-templates-add-rule) | Insert one rule from a template into a classifier. |

## API

Make raw C1 API requests. This is an escape hatch for accessing any API endpoint not covered by the built-in commands.

**Usage:**

```bash
c1i api --path <path> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--path string` | API endpoint path. (Required.) |
| `--method string` | HTTP method: `GET`, `POST`, `PUT`, `PATCH`, or `DELETE`. (Default: `GET`, or `POST` if a body is set.) |
| `--body string` | JSON request body (implies `POST`). |
| `--body-file string` | Read the JSON request body from a file (`-` for stdin); mutually exclusive with `--body`. |
| `--allow-delete-body` | Allow `--body` or `--body-file` with `--method DELETE`. Some endpoints, such as remove-membership, require a body on `DELETE`; without this flag c1i refuses the request. |
| `--header stringArray` | Extra request header as `key=value` (repeatable). |
| `--query stringArray` | Query parameter as `key=value` (repeatable). |
| `--paginate` | Automatically follow pagination to fetch all pages, and output results as NDJSON. |
| `--list-key string` | Force the response field name to drain as the list (default: the first array-valued field, such as `list`, `automationExecutions`, or `automations`). |
| `--limit int` | With `--paginate`, cap the total number of NDJSON rows emitted (0 = unlimited). Errors if used without `--paginate`. |

**Examples:**

```bash
# GET request
c1i api --path /api/v1/apps

# POST request — passing --body switches the method to POST automatically
c1i api --path /api/v1/search/tasks --body '{"taskStates":["TASK_STATE_OPEN"]}'

# Paginate through results as NDJSON
c1i api --path /api/v1/apps --paginate

# Paginate a POST search endpoint
c1i api --path /api/v1/search/tasks --body '{"taskStates":["TASK_STATE_OPEN"]}' --paginate
```

If you call a POST-only endpoint with GET (for example a `/search/*` path with no `--body`), c1i prints a one-line hint suggesting `--body` or `--method=POST` so you can recover without consulting the schema.

<Note>
c1i sends `--body` to the API verbatim — it does not wrap or reshape the payload. If the endpoint's schema nests fields under a top-level key (for example, `POST /api/v1/iam/personal_clients/{id}` expects `{"client": {"displayName": "...", "scopedRoles": ["..."]}, "updateMask": "displayName,scopedRoles"}`), your `--body` must include that wrapper. Use `c1i docs endpoint <path>` to see the exact request shape before calling.
</Note>

## Pagination and limits

Commands marked "Paginates" (and `c1i api --paginate`) auto-paginate by default — they keep fetching pages until the cursor is empty, so you don't have to manage tokens manually.

Each of those commands takes three flags that control how much data flows:

| Flag | Effect |
| :--- | :--- |
| `--page-size N` | Rows to request per API page (max 100). The server may return more than asked, so use `--limit` for an exact count. Default is 50. `policies search` defaults to 25. The history commands (`mcp tools history`, `mcp bindings history`) accept up to 200. |
| `--page-token TOKEN` | Resume from a specific cursor. When set, c1i fetches a single page and exits — auto-pagination is disabled. |
| `--limit N` | Cap the *total* number of results emitted across all pages (0 = unlimited). Auto-pagination stops fetching new pages once the cap is reached, and c1i tightens the per-call request size when `--limit` is smaller than `--page-size` so it doesn't over-fetch. |

**Examples:**

```bash
# Peek at the first 5 users without fetching everyone
c1i users list --limit 5

# Cap a wide query — useful for cost control or quick previews
c1i tasks list --state open --limit 25

# --limit also works with the raw api command, but only with --paginate
c1i api --path /api/v1/search/tasks --body '{"taskStates":["TASK_STATE_OPEN"]}' --paginate --limit 10
```

`c1i api --path X --limit N` without `--paginate` errors immediately — the non-paginated path returns a single response, so there's nothing to cap.

## Completion

Generate a shell completion script. Output is the script itself, which you can write to a file or `source` directly. Supported shells are bash, zsh, fish, and PowerShell.

**Usage:**

```bash
c1i completion <shell>
```

**Examples:**

```bash
# bash
c1i completion bash > /etc/bash_completion.d/c1i

# zsh
c1i completion zsh > "${fpath[1]}/_c1i"

# fish
c1i completion fish > ~/.config/fish/completions/c1i.fish

# PowerShell
c1i completion powershell > $PROFILE
```

| Flag | Description |
| :--- | :--- |
| `--no-descriptions` | Disable completion descriptions. |

For shell-specific install steps, run `c1i completion <shell> --help`.
