## Overview of c1i commands

Use this reference to find the command, flags, and output format for any c1i task, from managing identities, apps, and access to policies, automations, and MCP servers.

List and search commands output NDJSON, one JSON object per line. Other commands output formatted JSON. An absent string field in a list row is `null`, not `""`. Mutation commands, such as `apps create`, `requests create grant`, and `tasks approve`, print the API's response unwrapped the same way the matching `get` command unwraps it, so you read an ID with `.id` rather than `.app.id`. Deletes and other empty responses print `{}`; exit `0` means success. A few responses carry a different ID path, such as `.connectorId` for an MCP server. See [Output conventions](/product/cli/c1i#output-conventions) for `auth`, `docs`, and `api` output.

## Common workflows

| Goal | Start with |
| :--- | :--- |
| Request access and wait for the new grant | [`requests create grant`](#requests-create-grant) with `--wait`; re-read the task with [`requests get`](#requests-list). |
| Approve or deny a request | [`tasks list`](#tasks-list), [`tasks get`](#tasks-get), then [`tasks approve`](#tasks-approve) or [`tasks deny`](#tasks-deny). |
| Grant a manually managed entitlement directly | [`grants add`](#grants-add). This skips request policy and approval. |
| Register and govern an MCP server | [`mcp servers register`](#mcp-servers-register) with `--wait`, [`mcp tools approve`](#mcp-tools-approve), then [`mcp toolsets`](#mcp-toolsets). |
| Promote a connector-discovered app | [`apps managed-state`](#apps-managed-state) after finding the resource type with [`apps resource-types list`](#apps-resource-types-list). |
| Explore C1 docs and API schemas without credentials | [`docs`](#docs): `docs search`, `docs endpoints`, `docs endpoint`, and `docs page`. |

## Global flags

Every command accepts these flags.

| Flag | Description |
| :--- | :--- |
| `--url string` | C1 tenant URL; https required. Precedence: `--url`, `C1I_URL`, then `~/.c1i.yaml`. |
| `--fields string` | Comma-separated JSON fields to keep in read output (dot-paths). Prefer it over `jq` for simple projection. On a mutation command it's a usage error (exit 2), because mutation output is never projected. |
| `--max-retries int` | Retries for transient API failures (429/5xx); 0 disables (default 4). |
| `--error-format string` | Stderr format: `text` or `json` (default `text`). With `json`, every stderr line is one JSON object (NDJSON). See [Errors and exit codes](#errors-and-exit-codes). |
| `--dry-run` | Preview C1 REST mutations (method, URL, body) without sending them. See [Dry run](#dry-run). `mcp gateway call`, `auth login`, and `auth logout` reject it (exit 2). |
| `--debug` | Trace HTTP requests (method, URL, status, timing) to stderr. |
| `-h`, `--help` | Help for any command. |

Each global flag also reads a `C1I_*` environment variable: `C1I_URL`, `C1I_FIELDS`, `C1I_MAX_RETRIES`, `C1I_ERROR_FORMAT`, `C1I_DRY_RUN`, and `C1I_DEBUG`. A flag on the command line overrides its variable. A non-empty `C1I_DRY_RUN`, `C1I_DEBUG`, `C1I_MAX_RETRIES`, or `C1I_ERROR_FORMAT` value that doesn't parse exits with code 2 before any request, as does a negative `--max-retries`.

## Dry run

`--dry-run` (or `C1I_DRY_RUN=1`) previews a C1 REST mutation and sends nothing. The preview is one JSON object on stdout with two keys, `dryRun` and `requests`. `requests` lists each request in send order, with its `method`, full `url`, and the `body` as sent (omitted when the request has no body). A notice on stderr, `dry run: nothing was sent`, accompanies every preview.

```json
{
  "dryRun": true,
  "requests": [
    {
      "method": "POST",
      "url": "https://example.conductor.one/api/v1/task/grant",
      "body": {
        "appEntitlementId": "E1",
        "appId": "A1",
        "identityUserId": "U1"
      }
    }
  ]
}
```

- Credential fields appear as `[redacted]`: fields whose names end in `token`, `secret`, `password`, `signature`, or `apikey`, header values, a URL's username or password, and secret-named URL parameters. A body that isn't JSON prints as `"[redacted: not JSON]"`.
- A preview needs a configured URL (exit 2 without one), and an empty, `.`, or `..` ID is refused with exit 2, as it is for a real request. A preview needs no credentials unless c1i must look something up: a task's current policy step, a hosted MCP server's catalog ID, the caller for `requests create`, or a referenced user, policy, or app account checked before sending. Those checks run on a preview too, so the preview needs the matching read access.
- A preview has no `id`. If an inherited `C1I_DRY_RUN=1` turns a script's writes into previews, `jq -r .id` prints `null` and the script carries on. Extract IDs with `jq -er`, which fails on a preview.
- `upgrade --dry-run` follows the same JSON preview shape: `dryRun`, `requests`, and an `upgrade` object with the `--check` fields. `upgrade --fields` is a usage error unless you pass `--check`.

## Errors and exit codes

On failure, c1i writes an error to stderr and exits with a code you can branch on.

| Code | Meaning |
| :--- | :--- |
| `0` | Success. |
| `1` | Unclassified error, or a failed write to stdout (such as a full disk). On a mutation, the change was already applied, so verify before you retry. |
| `2` | Usage error: bad flags or arguments, a blank flag or ID, an empty, `.`, or `..` ID, a malformed `--update-mask` or `--body-file` key, a refused redirect, a non-approval `tasks skip-step`, or an API `4xx` other than `401`, `403`, `404`, `408`, `429`, and `499`. |
| `3` | Not authenticated, or the API returned `401` or `403`. A `400`, `401`, or `403` from the token endpoint also exits `3`. |
| `4` | The API returned `404`, or a referenced id was not found by a pre-send check. |
| `5` | The API returned `429`. Back off and retry. |
| `6` | C1 failed: a `5xx`, a redirect chain that never settled, a `200` response whose body isn't JSON (including an unusable token response), or a list command whose pagination cursor stopped advancing. |
| `7` | `mcp gateway call` completed, but the tool reported an error. |
| `8` | A system beyond C1 failed: an unreachable upstream connector or gateway, an unreachable external MCP server, a protocol-level gateway error, or any failure of the documentation site for `docs search` and `docs page`, whatever the HTTP status. |

A token-endpoint failure follows the same classification as other responses: `400`/`401`/`403` exits `3`, `404` exits `4`, `408` exits `1`, `429` exits `5`, and a `5xx` or unusable `200` exits `6`. An unreachable token endpoint is a transport failure (exit `1`), not bad credentials.

Several writes look up referenced users or policies before sending. An unknown referenced id exits `4`; a policy that exists but is deleted or of the wrong type exits `2`. The same checks run under `--dry-run`, so a preview can need the corresponding read access.

With `--error-format json`, stderr is NDJSON: each line is one object with an `error`, `notice`, `progress`, or `debug` key. Select errors with `jq 'select(.error)'`. API errors include `status`, `method`, `path`, and `body`.

An error from a command that writes also carries `"applied"`: `false` when nothing reached the server, `true` when the change was applied, and `"unknown"` when the request may have reached the server, including when a retry then failed. `mcp tools approve` adds an error object for each failed ID and a summary object with `notAttempted`. A batch can exit non-zero after it applied some changes.

## Docs

Explore C1 API documentation and schemas. These commands don't require authentication.

| Command | Description |
| :--- | :--- |
| `c1i docs search <query>` | Search C1 documentation by keyword. |
| `c1i docs page <path>` | Fetch a full documentation page by path. A leading slash or a full documentation URL is also accepted. |
| `c1i docs endpoints [--filter <pattern>]` | List all available API endpoints, optionally only those matching a pattern. |
| `c1i docs endpoint <path>` | Show the full request and response schema for a specific API endpoint. |
| `c1i docs openapi` | Dump the raw OpenAPI spec in YAML format. |
| [`c1i docs guide`](#docs-guide) | Print an embedded, task-oriented runbook for a common workflow. |
| [`c1i docs agents`](#docs-agents) (alias `skill`) | Print agent-facing conventions: output contracts, exit codes, and pagination. |
| [`c1i docs readme`](#docs-readme-and-docs-changelog) | Print the README embedded in the c1i binary: the full reference. |
| [`c1i docs changelog`](#docs-readme-and-docs-changelog) | Print the CHANGELOG embedded in the c1i binary, including migration notes under "Upgrading from" headings. |

`docs endpoints`, `docs endpoint`, and `docs openapi` read the public spec at `https://www.c1.ai/api/openapi.yaml`, which includes the MCP, service principal, and access review operations. c1i caches the spec for 24 hours at `~/.c1i/cache/api-openapi.yaml`. If a fetch fails, c1i serves the stale cache and prints a one-line warning on stderr. Each refresh deletes other files in `~/.c1i/cache/`, so keep your own files elsewhere.

`docs search` and `docs page` exit with code 8 when the documentation site fails, whatever the cause: an unreachable site, a non-200 response, an unparseable body, or a redirect loop. With no cached spec to fall back on, a redirect loop on `docs openapi`, `docs endpoints`, or `docs endpoint` also exits 8.

### `docs guide`

Print an embedded, task-oriented runbook: a numbered sequence of c1i commands for a common end-to-end workflow. Run it with no argument to list the available guide names and their purposes. Guides are static content in the c1i binary, so unlike `docs search` and `docs page` they make no network call.

**Usage:**

```bash
c1i docs guide [name]
```

### `docs agents`

Print a concise, agent-facing document covering the conventions that `--help` text can't: getting the tenant right, output contracts, exit codes, pagination, and when to prefer a first-class command over `c1i api`. It doesn't list every command or flag; run `c1i --help`, `c1i <group> --help`, or `c1i <group> <command> --help` for those.

The output opens with a YAML front-matter block (name, description, version, and required binaries) that some agent harnesses parse automatically, followed by plain Markdown. `skill` remains an alias for backward compatibility, so `c1i docs skill` still works.

| Flag | Description |
| :--- | :--- |
| `-o`, `--output string` | Write to a file instead of stdout. |

**Examples:**

```bash
# Write directly to a file for Claude Code
c1i docs agents -o .claude/skills/c1i/SKILL.md

# Write as a Cursor project rule
c1i docs agents -o .cursor/rules/c1i.md
```

For step-by-step setup instructions for Claude Code, Cursor, and other agents, see [Use c1i with AI agents](/product/cli/c1i-agent-skills).

### `docs readme` and `docs changelog`

Print the README or CHANGELOG embedded in the c1i binary, unmodified. They make no network call and need no credentials. Release archives ship only the binary, so these are how an installed c1i reads its own full reference. `docs agents` stays the concise guide for agents; the README is the full reference.

Relative links in the printed text don't resolve. A notice on stderr gives the version-pinned GitHub URL that renders the Markdown.

| Flag | Description |
| :--- | :--- |
| `-o`, `--output string` | Write to a file instead of stdout. `-` means stdout. |

<Callout icon="globe" color="#c937ae" iconType="regular">These examples use `conductor.one`. If your organization is on the EU data residency instance, substitute `c1eu.ai` in URLs, client IDs, and hostnames.</Callout>

## Auth

Log in, check which identity and credential c1i is using, and mint access tokens.

c1i reads credentials from `C1I_CLIENT_ID` and `C1I_CLIENT_SECRET`, then the OS keyring, then a `0600` file, and caches each access token it mints until it's close to expiry; see [Credential storage](/product/cli/c1i#credential-storage). `auth token` and `mcp gateway` always mint a fresh token. A cached token the server rejects (clock skew, or a revocation) is dropped and re-minted automatically, once.

| Command | Description |
| :--- | :--- |
| [`c1i auth login`](#auth-login) | Authenticate via browser or API credentials. |
| `c1i auth logout` | Remove stored c1i credentials for the current URL from both the OS keyring and the file fallback. Environment variables (`C1I_CLIENT_ID`, `C1I_CLIENT_SECRET`) are not affected. Rejects `--dry-run` and `C1I_DRY_RUN` (exit `2`): a delete cannot be previewed. |
| `c1i auth status` | Check whether valid C1 credentials are stored and working. Reports which source (environment, keyring, or file) served the active credentials. |
| [`c1i auth whoami`](#auth-whoami) | Show the authenticated principal's identity, roles, permissions, and feature flags. |
| [`c1i auth token`](#auth-token) | Print a short-lived OAuth2 bearer token for driving raw API calls yourself. |

### `auth login`

Opens a browser for OAuth device flow authorization, or accepts credentials directly.

| Flag | Description |
| :--- | :--- |
| `--client-id string` | C1 API client ID (skips browser login). |
| `--client-secret string` | C1 API client secret (skips browser login). |
| `--choose-roles` | Choose the browser-login credential's roles from a menu after approval (needs a terminal). `--choose-roles=false` skips the role question. |
| `--scoped-role stringArray` | Restrict the browser-login credential to a role, by name (such as `basic-user`) or ID (repeatable). |

A browser login creates a credential with all of your roles; see [Limit the credential to specific roles](/product/cli/c1i#limit-the-credential-to-specific-roles). `--scoped-role` takes a role name or a role ID from [`c1i roles list`](#roles). A name that matches no role you can scope to exits with code 2 before c1i creates your credential. An unknown role ID exits with code 4. `--choose-roles` and `--scoped-role` can't be combined, and neither works with `--client-id` and `--client-secret`. `auth login` rejects `--dry-run` (exit 2), because it can't preview creating a credential.

### `auth whoami`

Show the authenticated principal: principal ID, user ID (a service principal might carry only the principal ID), counts of roles, permissions, and tenant feature flags, and display name and email when the user lookup succeeds.

| Flag | Description |
| :--- | :--- |
| `-v`, `--verbose` | Include full roles, permissions, and features arrays. |

By default, `whoami` returns a compact summary. `--verbose` replaces that summary with the raw introspect payload, which includes the full role, permission, and feature lists but not the summary's counts, `displayName`, or `email`.

Both modes add two keys that c1i resolves itself: `tenant`, the base URL this invocation targets, and `tenantSource`, where it came from (`flag`, `env`, or `config`). They appear only after your credentials are proven against that tenant, so check them before a write:

```bash
c1i auth whoami --fields tenant
```

### `auth token`

c1i mints a new token from your stored credentials on each invocation and doesn't write it to disk.

| Flag | Description |
| :--- | :--- |
| `--json` | Print a JSON object with `access_token`, `token_type`, and `expires_at` (RFC3339) instead of just the access token. |

By default only the access token is printed (newline-terminated), so it composes directly into another command:

```bash
curl -H "Authorization: Bearer $(c1i auth token)" \
  https://your-tenant.conductor.one/api/v1/apps
```

The token is audience-scoped to the C1 API host.

[Paginates](#pagination-and-limits).

| Flag | Description |
| :--- | :--- |
| `--query string` | Search query. |
| `--email string` | Filter by email address. |
| `--status string` | Filter by status: `enabled`, `disabled`, or `deleted`. |

## Apps

Create, inspect, update, and delete applications, manage their owners, and promote apps a connector discovered.

| Command | Description |
| :--- | :--- |
| `c1i apps list` | List applications. [Paginates](#pagination-and-limits). |
| `c1i apps get <app-id>` | Get a single app by ID. |
| [`c1i apps create`](#apps-create) | Create a new app. |
| [`c1i apps update`](#apps-update) | Update an app's name, description, policies, or identity matching. |
| `c1i apps delete <app-id>` | Soft-delete an app by ID. The app is marked deleted and drops out of `apps list`, but `apps get` still returns it with `deletedAt` set. Prints `{}`. |
| [`c1i apps owners`](#apps-owners) | List an app's owners. |
| [`c1i apps add-owner`](#apps-add-owner) | Add one owner to an app. |
| [`c1i apps remove-owner`](#apps-remove-owner) | Remove one owner from an app. |
| [`c1i apps set-owners`](#apps-set-owners) | Set the owners of an app, replacing the full owner list. |
| [`c1i apps managed-state`](#apps-managed-state) | Inspect and promote apps a connector discovered. |
| [`c1i apps resource-types list`](#apps-resource-types-list) | List an app's resource types, including the connector's discovered-app type. |

### `apps create`

Create a new app — a plain, unmanaged container you can register MCP servers under. Only `--display-name` is required. C1 assigns the caller as an owner of the new app; manage owners afterward with `add-owner`, `remove-owner`, or `set-owners`.

**Usage:**

```bash
c1i apps create --display-name <name> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--display-name string` | Display name for the new app. Can't be blank. (Required.) |
| `--description string` | Description for the new app. |
| `--grant-policy-id string` | Grant policy ID to bind; must exist and be a grant policy. Omit for the server's default. |
| `--revoke-policy-id string` | Revoke policy ID to bind; must exist and be a revoke policy. Omit for the server's default. |
| `--certify-policy-id string` | Certify policy ID to bind; must exist and be a certify policy. |
| `--identity-matching string` | How app users are matched to C1 users: `strict`, `display-name`, or `custom`. |

Before sending, c1i checks each policy ID. An ID that doesn't exist exits with code 4; one that is deleted or of the wrong type exits with code 2. Nothing is sent. `--dry-run` runs the same check. An empty policy ID is a usage error.

The created app is returned as formatted JSON, unwrapped like `apps get`, so the app's ID is `.id`.

**Example:**

```bash
APP_ID=$(c1i apps create --display-name "Google Workspace" | jq -er .id)
```

### `apps update`

Update an app's display name, description, policies, or identity matching. c1i builds the update mask from the flags you pass: an omitted flag is left alone, and an explicit empty value is a change.

**Usage:**

```bash
c1i apps update <app-id> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--display-name string` | New display name. Can't be blank. |
| `--description string` | New description. Pass an empty value to clear it. |
| `--grant-policy-id string` | Grant policy ID to bind; must exist and be a grant policy. |
| `--revoke-policy-id string` | Revoke policy ID to bind; must exist and be a revoke policy. |
| `--certify-policy-id string` | Certify policy ID to bind; must exist and be a certify policy. |
| `--unbind-policy stringArray` | Unbind a policy: `grant`, `revoke`, or `certify` (repeatable). |
| `--identity-matching string` | How app users are matched to C1 users: `strict`, `display-name`, or `custom`. |
| `--app-user-mapper-file string` | JSON object that replaces the app's whole user mapper (file, or `-` for stdin). |

Each policy ID is checked before anything is sent, as for `apps create`. An empty policy ID is a usage error rather than an unbind, so pass `--unbind-policy` to remove a policy. You can't set and unbind the same kind in one call.

`--app-user-mapper-file` takes an object such as `{"mappingCases":[{"userKeyCel":"subject.email","appUserKeyCel":"account.email"}]}`. `userKeyCel` runs against the C1 user as `subject`, and `appUserKeyCel` runs against the app user as `account`. `mappingCases` must be non-empty, and the API offers no way to remove a mapper.

The updated app is returned as formatted JSON, unwrapped like `apps get`.

### `apps owners`

[Paginates](#pagination-and-limits).

**Usage:**

```bash
c1i apps owners <app-id> [flags]
```

Use this to verify an owner change. Owner changes are applied asynchronously and can take several minutes to appear. Most apps already have at least one owner, because `apps create` assigns its caller as an owner. A well-formed app ID that doesn't exist returns zero rows and exits `0`, not `4`.

### `apps add-owner`

Add one user as an app owner without changing the rest of the owner list. Unlike `set-owners`, it can't drop an owner that someone else added in the meantime.

**Usage:**

```bash
c1i apps add-owner <app-id> --user-id <user-id>
```

| Flag | Description |
| :--- | :--- |
| `--user-id string` | C1 user ID to add as owner. One per call; use `set-owners` for several. (Required.) |

An unknown app or user ID exits with code 4; c1i looks up the `--user-id` before sending, including under `--dry-run`. Owner changes are applied asynchronously; verify with `c1i apps owners <app-id>`. Prints `{}`; exit `0` means success.

### `apps remove-owner`

Remove one user as an app owner without changing the rest of the owner list. The creator that `apps create` assigned can remain an owner, so check `c1i apps owners <app-id>` first if that matters.

**Usage:**

```bash
c1i apps remove-owner <app-id> --user-id <user-id>
```

| Flag | Description |
| :--- | :--- |
| `--user-id string` | C1 user ID to remove as owner. One per call; use `set-owners` for several. (Required.) |

An unknown app ID exits with code 4. Owner changes are applied asynchronously; verify with `c1i apps owners <app-id>`. Prints `{}`; exit `0` means success.

### `apps set-owners`

**Usage:**

```bash
c1i apps set-owners <app-id> --user-id <user-id> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--user-id stringArray` | C1 user ID to set as owner (repeatable; replaces the full owner list). (Required.) |
| `--wait` | Block and poll until the owner set equals the requested owners, or `--wait-timeout` elapses. A timeout exits with code 1, though the write was accepted. |
| `--wait-timeout duration` | Max time to wait with `--wait` (default `4m0s`). |

Before it sends the request, c1i looks up each distinct `--user-id`. An unknown user exits with code 4, naming the ID, and nothing is sent. The lookup needs user-read access, so a credential without it exits with code 3. `--dry-run` runs the same lookups. c1i sends a repeated `--user-id` once.

Owner changes are applied asynchronously, so the command returns once the request is accepted and new owners can take several minutes to appear. Pass `--wait` to block until the owner set equals the request, including removals. `--wait` progress goes to stderr, and the command prints the API's JSON response on stdout.

**Example:**

```bash
c1i apps set-owners app_abc123 --user-id user_1 --user-id user_2 --wait
```

### `entitlements create`

Create an app entitlement, plus the app resource type and resource it points at, as up to three requests in order. Pass `--resource-type-id` to reuse an existing resource type, and `--resource-id` to reuse an existing resource. Outputs the created entitlement as formatted JSON, unwrapped like `entitlements get`, so its ID is `.id`. The output echoes `appResourceTypeId` and `appResourceId` and expands both objects.

**Usage:**

```bash
c1i entitlements create --app-id <app-id> --display-name <name> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Application ID to create the entitlement on. (Required.) |
| `--display-name string` | Display name for the new entitlement; also names the resource type and resource that c1i creates. Can't be blank. (Required.) |
| `--description string` | Description for the new entitlement. |
| `--alias string` | Alias for the new entitlement; exact-match queryable. |
| `--slug string` | Slug for the new entitlement, such as `member`. |
| `--duration-grant string` | Maximum grant duration, as a whole-number Go duration such as `8h` or a protobuf duration such as `3600s`; c1i sends it in seconds. Omit for standing access. A sign, decimal, or leading zero (`-1h`, `1.5h`, `01h`) exits with code 2. |
| `--owner-id stringArray` | C1 user ID to own the new entitlement (repeatable). |
| `--grant-policy-id string` | Grant policy ID to bind; must exist and be a grant policy. |
| `--revoke-policy-id string` | Revoke policy ID to bind; must exist and be a revoke policy. |
| `--certify-policy-id string` | Certify policy ID to bind; must exist and be a certify policy. |
| `--emergency-grant-policy-id string` | Emergency grant policy ID to bind; must exist and be a grant policy. |
| `--resource-type string` | Kind of resource type to create: `ROLE`, `GROUP`, `LICENSE`, `PROJECT`, `CATALOG`, `CUSTOM`, `VAULT`, or `PROFILE_TYPE` (default `CUSTOM`). |
| `--resource-type-display-name string` | Display name for the resource type this command creates (default: `--display-name`). |
| `--resource-type-id string` | Existing app resource type to reuse instead of creating one. |
| `--resource-display-name string` | Display name for the resource this command creates (default: `--display-name`). |
| `--resource-id string` | Existing app resource to reuse instead of creating one; requires `--resource-type-id`. |

Passing `--resource-type` or `--resource-type-display-name` together with `--resource-type-id` is a usage error (exit 2), as is `--resource-id` without `--resource-type-id`. Only the `CUSTOM` resource type can repeat on one app, so reuse an existing type with `--resource-type-id` for any other kind.

Before the first request, c1i checks each policy ID and each `--owner-id`. An unknown policy or user exits with code 4 and creates nothing; a policy that is deleted or of the wrong type exits with code 2. The owner check reads the user, so a credential without user-read access exits with code 3. c1i sends a repeated `--owner-id` once. `--dry-run` runs the same checks.

There is no rollback. If a later request fails, the objects that earlier ones created still exist; the error names them and the flags that reuse them. `--dry-run` previews every request in the sequence, and where an ID exists only after an earlier request, the preview shows `NEW_APP_RESOURCE_TYPE_ID` or `NEW_APP_RESOURCE_ID` in its place. Owner changes are applied asynchronously.

**Example:**

```bash

```

## Grants

Query access grants — the bindings between accounts or users and entitlements — to answer "who has access to what", or add users directly to a manually managed entitlement.

### `grants list`

Search and list grants. At least one filter is required. [Paginates](#pagination-and-limits).

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Filter to grants in this application. |
| `--entitlement-id string` | Filter to grants of this entitlement (requires `--app-id`). |
| `--user-id string` | Filter to grants held by this C1 identity user. |
| `--app-user-id string` | Filter to grants held by this app account (app user). |
| `--wait` | Block and poll every page until the same grants come back `--wait-stable` times in a row, or `--wait-timeout` elapses. |
| `--wait-stable int` | Consecutive identical reads that `--wait` requires before printing (minimum 2; default 3). |
| `--wait-min int` | Minimum matching grants that `--wait` requires before it can settle (0 = an empty result can settle). |
| `--wait-timeout duration` | Maximum time to wait with `--wait` (default `4m0s`). |

Grant provisioning is asynchronous, so a read taken right after a grant or revoke can catch the set mid-change. With `--wait`, c1i re-reads every page of the match every 5 seconds, regardless of `--limit`, and prints the settled set; progress goes to stderr, so stdout stays pure NDJSON. An empty result is stable: if you are waiting for a grant you just made, pass `--wait-min 1` so the wait holds out for it instead of settling on zero rows.

**Example:**

```bash
# Who holds an entitlement?
c1i grants list --app-id <app-id> --entitlement-id <entitlement-id>
```

### `grants add`

Grant users a manually managed entitlement directly. This bypasses the entitlement's grant policy and approval, so no access-request task is created. For a policy-respecting request, use [`requests create grant`](#requests-create-grant) instead.

**Usage:**

```bash
c1i grants add --app-id <app-id> \
  --entitlement-id <entitlement-id> --user-id <user-id> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--app-id string` | Application ID the entitlement belongs to. (Required.) |
| `--entitlement-id string` | Entitlement ID to grant. (Required.) |
| `--user-id stringArray` | C1 user ID to grant (repeatable; one request carries every id). (Required.) |
| `--wait` | Block and poll until every accepted user holds the entitlement, or `--wait-timeout` elapses. A timeout exits `1`, though the write was accepted. |
| `--wait-timeout duration` | Maximum time to wait with `--wait` (default `4m0s`). |

c1i looks up each `--user-id` before sending, including under `--dry-run`; an unknown user exits `4` and nothing is sent. A repeated `--user-id` is sent once. Adding a user who already holds the entitlement exits `0`. The server's `failedUsersErrorMap` is printed when present, each rejected user is named, and the command exits `1`; `--wait` then waits only for the users that were accepted.

There is no `grants remove`. Direct removal (`remove-membership`) rejects a manually managed entitlement; remove access through [`requests create revoke`](#requests-create-revoke).

## Policies

Manage policies — the objects that describe how C1 processes a task (an access request, a certification, a provisioning action): who approves it, what happens on escalation or timeout, and how the underlying resource gets provisioned.

| Command | Description |
| :--- | :--- |
| [`c1i policies list`](#policies-list) | List all policies. |
| [`c1i policies search`](#policies-search) | Search policies by display name, description, type, or deletion state. |
| [`c1i policies get`](#policies-get) | Get a single policy by ID. |
| [`c1i policies create`](#policies-create) | Create a new policy. |
| [`c1i policies update`](#policies-update) | Update a policy. |
| [`c1i policies delete`](#policies-delete) | Soft-delete a policy by ID. |
| [`c1i policies validate-cel`](#policies-validate-cel) | Check a CEL condition for compile errors. |

<Warning>
Creating or updating a policy with an empty (or missing) steps list succeeds with no validation error, and silently produces a deny-everything policy. The `create` and `update` commands refuse to send a request with empty or missing steps unless you pass `--allow-deny-all` to confirm that's what you want.
</Warning>

A policy's shape is deeply nested: `policySteps` holds an ordered list of steps, each one of seven types (approval, provision, accept, reject, wait, form, action), and an approval step's approver is itself one of several kinds (users, manager, group, app owners, self, entitlement owners, expression, webhook, resource owners, agent). You can read back all seven types, but `create` and `update` refuse two of them client-side with exit code 2, before sending a request: `a "provision" step is never allowed in a policy body — it's read-only and server-computed` and `an "action" step is not supported by create/update yet`. Modeling the nested structure as flags would be unusable, so `create` and `update` take the nested pieces from a JSON file (or `-` for stdin), while flat top-level fields (display name, description, policy type) stay as flags.

### `policies list`

[Paginates](#pagination-and-limits).

Unlike most list commands, this takes no query filter at all — only pagination. Use `search` for filtering.

Rows carry `step_kinds` (the kind of each step in the policy's baseline sequence) and `baseline_policy_id`, which together identify a tenant's auto-approval policy without matching on its display name. Search rows carry the same keys.

| `--policy-type stringArray` | Filter by policy type, such as `grant`, `revoke`, or `certify` (repeatable). |
| `--include-deleted` | Include soft-deleted policies. This is the only listing command that can find one. |
| `--exclude-policy-id stringArray` | Policy ID to exclude from results (repeatable). |

Unlike `list` and the default `search`, `get` returns a soft-deleted policy too (with `deletedAt` populated) rather than filtering it out.


### `policies validate-cel`

It creates and updates nothing, so you can test a rule's `condition` before using it in `create` or `update`.

**Usage:**

```bash
c1i policies validate-cel <condition>
```

**Example:**

```bash
c1i policies validate-cel 'subject.role == "admin"'
```

Exits `0` for a valid condition, `2` for an invalid one — so `c1i policies validate-cel '<cond>' && ...` only continues past a condition that compiles.

<Note>
This validates the CEL environment rules run in (`subject`, `account`, `entitlement`, `task`) — not the same environment an approval step's `expression` approver runs in. An expression that's valid in one may not compile in the other.
</Note>

## Upgrade

Check for and install a newer c1i release. The command is aliased as `update`.

**Usage:**

```bash
c1i upgrade [--channel <stable|latest|preview>] [--check] [-y]
```

c1i follows a release channel from the C1 distribution center (`dist.conductorone.com`); see [Upgrade c1i](/product/cli/c1i#upgrade-c1i). Before it replaces a standalone binary, it verifies the release manifest's Sigstore signature (signed by the release workflow run for that c1i tag) and the download's SHA-256 from that manifest. For a Homebrew, `go install`, or container install, `upgrade` prints that method's upgrade command and exits 0 without replacing anything.

| Flag | Description |
| :--- | :--- |
| `--channel string` | Release channel: `stable`, `latest`, or `preview` (default `stable`). |
| `--check` | Print a JSON report of whether a newer release is available; change nothing. |
| `-y`, `--yes` | Skip the confirmation prompt. Required when stdin is not a terminal. |

`--check` prints one JSON object with these keys:

| Key | Description |
| :--- | :--- |
| `current` | The version you run. |
| `latest` | The newest version on the channel. |
| `channel` | The release channel checked. |
| `update_available` | `true` when a newer release exists. |
| `install_method` | How c1i was installed: `standalone`, `homebrew`, `go-install`, `container`, `system`, or `windows`. |
| `upgrade_command` | The command that upgrades this install. Present only for a Homebrew, `go install`, or container install. |

Windows and system installs print a hint but no `upgrade_command`.

With the global `--dry-run` flag, `upgrade` fetches and verifies the release (index, manifest, signature, and TUF root) and checks that the install directory is writable. It prints one JSON object on stdout: `dryRun`, `requests` for the download it would make (`[]` when no download is needed), and an `upgrade` object with the `--check` fields; for a standalone update it also includes `asset_url`, `sha256`, and `destination`. It takes no lock, doesn't prompt, and installs nothing. `--fields` is a usage error unless you pass `--check`.

`upgrade` treats the distribution center as a system beyond C1. A distribution center `404`, `429`, or `5xx` exits `4`, `5`, or `6`, and a same-path redirect loop exits `6`. Any other `4xx`, a refused redirect, a non-JSON `200`, or a TUF, signature, or checksum failure exits `8`.

**Usage:**

### `mcp tools approve`

Approve MCP tools by setting each tool's state to approved, which lets the MCP gateway proxy calls to them. Pass one or more tool IDs. The API has no batch approve, so c1i sends each ID as its own request and prints one compact JSON line for each applied tool, with its `.id` and `.state`. If one fails, c1i still attempts the rest and exits non-zero with the first failure's code, while the IDs before it stay approved. A failed write to stdout stops the batch with exit code 1. With `--error-format json`, each failed ID gets its own error object, and a summary lists the IDs c1i never sent in `notAttempted`.

**Usage:**

```bash

  --connector-id <connector-id> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--state string` | Target state: `pending`, `approved`, or `disabled` (default `approved`). |

**Example:**

```bash
# Approve every pending read-only tool on a connector
c1i mcp tools approve $(c1i mcp tools search --app-id <app-id> --connector-id <connector-id> \
  --classification read --state pending --fields id | jq -r .id) \
  --app-id <app-id> --connector-id <connector-id>
```

## MCP classifiers

Templates instantiate curated classifiers (and their dependent gates) into a tenant-owned, editable classifier. The singleton `policy` surface — the tenant's one agent classifier policy — is separate from named classifiers.

`create` and `update` take JSON objects through `--body-file` (or `-` for stdin), preserving nested CEL rules, hooks, gates, and template parameters without a lossy flag translation. Updates require an explicit `--update-mask` as a safeguard — including `rules` in the mask replaces the entire ordered cascade.

## API

Make raw C1 API requests. This is an escape hatch for accessing any API endpoint not covered by the built-in commands.

**Usage:**

```bash
c1i api --path <path> [flags]
```

| Flag | Description |
| :--- | :--- |
| `--path string` | API endpoint path. (Required.) |
| `--method string` | HTTP method: `GET`, `POST`, `PUT`, `PATCH`, or `DELETE`. (Default: `GET`, or `POST` if a body is set.) |
| `--body string` | JSON request body (implies `POST`). |
| `--body-file string` | Read the JSON request body from a file (`-` for stdin); mutually exclusive with `--body`. |
| `--allow-delete-body` | Allow `--body` or `--body-file` with `--method DELETE`. Some endpoints, such as remove-membership, require a body on `DELETE`; without this flag c1i refuses the request. |
| `--header stringArray` | Extra request header as `key=value` (repeatable). |
| `--query stringArray` | Query parameter as `key=value` (repeatable). |
| `--paginate` | Automatically follow pagination to fetch all pages, and output results as NDJSON. |
| `--list-key string` | Force the response field name to drain as the list (default: the first array-valued field, such as `list`, `automationExecutions`, or `automations`). A misspelled key exits with code 2, and the error names the page's array fields. |
| `--limit int` | With `--paginate`, cap the total number of NDJSON rows emitted (0 = unlimited). Errors if used without `--paginate`. |

**Examples:**

```bash
# POST request — passing --body switches the method to POST automatically
c1i api --path /api/v1/search/tasks --body '{"taskStates":["TASK_STATE_OPEN"]}'

# Paginate a POST search endpoint
c1i api --path /api/v1/search/tasks --body '{"taskStates":["TASK_STATE_OPEN"]}' --paginate
```

If you call a POST-only endpoint with GET (for example a `/search/*` path with no `--body`), c1i prints a one-line hint suggesting `--body` or `--method=POST` so you can recover without consulting the schema.

<Note>
c1i sends `--body` to the API verbatim — it does not wrap or reshape the payload. If the endpoint's schema nests fields under a top-level key (for example, `POST /api/v1/iam/personal_clients/{id}` expects `{"client": {"displayName": "...", "scopedRoles": ["..."]}, "updateMask": "displayName,scopedRoles"}`), your `--body` must include that wrapper. Use `c1i docs endpoint <path>` to see the exact request shape before calling.
</Note>

## Pagination and limits

Commands marked "Paginates" (and `c1i api --paginate`) auto-paginate by default — they keep fetching pages until the cursor is empty, so you don't have to manage tokens manually.

Each of those commands takes three flags that control how much data flows:

| Flag | Effect |
| :--- | :--- |
| `--page-size N` | Rows to request per API page (max 100). The server may return more than asked, so use `--limit` for an exact count. Default is 50. `policies search` defaults to 25. The history commands (`mcp tools history`, `mcp bindings history`) accept up to 200. |
| `--page-token TOKEN` | Resume from a specific cursor. When set, c1i fetches a single page and exits — auto-pagination is disabled. |
| `--limit N` | Cap the *total* number of results emitted across all pages (0 = unlimited). Auto-pagination stops fetching new pages once the cap is reached, and c1i tightens the per-call request size when `--limit` is smaller than `--page-size` so it doesn't over-fetch. |

**Examples:**

```bash
# Peek at the first 5 users without fetching everyone
c1i users list --limit 5

# Cap a wide query — useful for cost control or quick previews
c1i tasks list --state open --limit 25
```

A blank `--page-token` (empty, whitespace-only, or invisible-only) exits with code 2. Without that check, an unset shell variable would turn off auto-pagination and return only the first page.

If a server's pagination cursor stops advancing, c1i doesn't loop forever. A cursor counts as stuck when `nextPageToken` repeats, when two or more pages in a row (25 or more rows in all) hold only rows c1i has already seen, or after 100 empty pages in a row. c1i keeps the rows it already printed, warns on stderr that results are INCOMPLETE, and exits with code 6. A list page that is HTML, an array, empty, or truncated also exits with code 6.

`c1i api --path X --limit N` without `--paginate` errors immediately — the non-paginated path returns a single response, so there's nothing to cap.

## Completion

Generate a shell completion script. Output is the script itself, which you can write to a file or `source` directly. Supported shells are bash, zsh, fish, and PowerShell.

**Usage:**

```bash
c1i completion <shell>
```

**Examples:**

```bash
# bash
c1i completion bash > ~/.local/share/bash-completion/completions/c1i

# zsh
c1i completion zsh > "${fpath[1]}/_c1i"

# fish
c1i completion fish > ~/.config/fish/completions/c1i.fish

# PowerShell (current session; add the line to your $PROFILE to keep it)
c1i completion powershell | Out-String | Invoke-Expression
```

| Flag | Description |
| :--- | :--- |
| `--no-descriptions` | Disable completion descriptions. |

For shell-specific install steps, run `c1i completion <shell> --help`.
