## What are C1 groups? 

<Frame><img src="/images/product/assets/c1-groups.png" alt="A screenshot of the C1 app showing a sample C1 group."/></Frame>

C1 groups are collections of C1 users that you create and use within C1. These groups are resources in [the C1 app](/product/admin/c1-for-c1). 

## What can I do with a C1 group? 

Key uses for these special groups include: 

* **Organizing employees without creating custom IdP groups.** C1 groups make it easy to create groups of employees who share key profile attributes or combinations of access. 

* **Specifying who is granted an access profile.** An access profile can be requestable by, or automatically assigned to, a C1 group. 

* **Assigning a group as reviewer on a policy step.** A C1 group can be set as a policy step reviewer. 

## What kind of groups should I make? 

When considering what groups to make, think about how you want to organize your employees for access management, access profile, and policy reviews. Groups provide a flexible way to do so without needing to manage complex groups in your identity provider. 

Here are some ideas for groups you might create in C1:

* **Department or team-based groups:** For example, "Marketing Team", "Engineering Department", "Sales". This helps organize employees and manage access relevant to those teams.

* **Role-based groups:** For example, "Software Engineers", "Data Analysts", "Project Managers". This is useful for assigning access based on job function.

* **Location-based groups:** For example, "Portland Office", "London Team". Useful if access varies by location.

* **Project-based groups:** For temporary teams working on specific projects, like "Spruce Mongoose Team".

* **Reviewer groups:** Groups specifically created to be used as reviewers in policies. For example, "Security Reviewers", "Legal Reviewers".

## Create a new C1 group 

Create a C1 group by setting a rule for membership. C1 will dynamically add or remove members from the group based on their adherence to the rule. 

<Steps>
<Step>
Navigate to **Identities** > **Dynamic groups** and click **Create group**.
</Step>
<Step>
Give your new group a name and add a description. Click **Create group**.
</Step>
<Step>
In the **Membership automation** section of the page, click **Edit**.
</Step>
<Step>
Choose how to form your membership rule:

   - Use the **Basic** condition builder to construct a rule from a combination of entitlements and [profile attributes](/product/admin/attributes) (see note below on which profile attributes are supported), with the option to add **and** and **or** statements to refine the rule.
   <Tip>
   **Supported attributes in the basic condition builder** The value input field in the basic condition builder currently only supports string values. Certain attributes are stored as enums (fixed lists of values) or arrays (multiple values), which cannot be correctly parsed when entered as a simple string in the basic builder. If you use these attributes in the basic builder, the system will treat the input as a literal string, and the policy or membership rule may not behave as expected.

   The following attributes are not supported in the basic condition builder:

   - Additional Employee ID
   - Additional Username
   - Additional Email
   - Directory Status
   - Manager Email

   If you need to use any of the attributes listed above, you must compose a CEL expression in the **Expression** field.
   </Tip>
   - Use the **Expression** field to to compose a [CEL expression](/product/admin/expressions) that describes the membership rule.
</Step>
<Step>
Click **Preview** to check the syntax of your membership rule.<br/><br/>
Note that not all users who match the membership rule will be shown immediately when you click **Preview**.
</Step>
<Step>
**Optional.** In the **Excluded users** field, add the names of any users who should be excluded from this group, even if they match the membership rule.
</Step>
<Step>
When you're satisfied, click **Save**. The **Membership rule** section syncs and updates the list of matching users.

Depending on the number of users in your C1 installation, syncing might take some time. When syncing is complete, the **Syncing** label will be replaced by a **Last sync** timestamp.
</Step>
</Steps>


**Done.** Your C1 group is now ready for use elsewhere in the app. The group will re-sync every hour to check which C1 users match the rule you set, and will add or remove group members accordingly. 

## Create a group from an existing entitlement

If a group already exists in your identity provider or another app, such as an Okta or Microsoft Entra ID group, you can use its membership as the starting point for a C1 group instead of rebuilding it by hand. C1 analyzes who holds the source entitlement and proposes a membership rule that covers as many of those people as it can, plus exact lists of the individual people the rule needs added or removed. You review the proposal and create an ordinary C1 group from it. This is called adoption.

Use this when you want to move a provider group's membership into C1, for example to use the group as an access profile audience or a policy reviewer group without maintaining it in the provider.

### Before you start

- **You must have the System Owner role.** Other roles don't see the adoption options.
- **Your tenant must support manual membership reasons.** C1 groups created this way hold some members individually, which requires this capability. If it isn't enabled, the **Use an existing entitlement** option is unavailable and C1 tells you why.
- **The source needs a completed full sync.** For a source backed by a connector, such as an Okta or Entra ID group, the connector's latest sync must be a successful full sync, and C1 must have finished processing it. If a sync is running, partial, or failed, analysis stops and tells you to wait for or run a full sync.
- **The source must represent membership.** A source can be an app's access entitlement, an entitlement synced from a connector, an entitlement you manage in C1, or a C1 role. An entitlement that combines multiple connectors, or that represents exclusion, owner, or admin access, can't be used.
- **You must be able to read the source entitlement.**

### Start from the Dynamic groups page

<Steps>
<Step>
Navigate to **Identities** > **Dynamic groups** and click **Create group**.
</Step>
<Step>
Under **Creation method**, choose **Use an existing entitlement** and click **Continue**. (**Start from scratch** creates a group as described in [Create a new C1 group](#create-a-new-c1-group).)
</Step>
<Step>
Under **Source**, select the app and then the entitlement to use as the starting point. Click **Analyze**.
</Step>
<Step>
Wait for the analysis to finish. You can close the window while it runs. Analysis continues, and you can reopen it from the **Adoption history** tab.
</Step>
<Step>
Review the results, as described below, then click **Continue**.
</Step>
<Step>
Under **Group details**, enter a name (at least 3 characters) and an optional description. C1 prefills both from the source entitlement. Click **Create group**.
</Step>
<Step>
When C1 shows **Group created**, click **View group** to open the new group.
</Step>
</Steps>

### Start from an entitlement

To start from the entitlement itself, open the entitlement's details page, click the **...** (more actions) menu, and choose **Create group from entitlement**. The **Create group** window opens at the **Source** step with that entitlement already selected. Continue from the **Analyze** step above.

### Review the analysis

The **Review** step shows what C1 found in the source and how it proposes to rebuild that membership.

- **Recommendation.** C1 recommends either **Rule-based membership**, where a rule adds and removes members as user attributes change, or **Individual membership**, where C1 adds the listed users and later changes to the source don't update the group.
- **Rule expression.** The proposed membership rule, written as a [CEL expression](/product/admin/expressions).
- **Rule coverage.** How many of the eligible people the rule covers, such as "Rule coverage: 480 of 500 eligible people."
- **Inclusions.** People the rule doesn't match who still held the source entitlement. C1 adds them to the group individually.
- **Exclusions.** People the rule would match who didn't hold the source entitlement. C1 adds them to the group's exclusion list so the rule doesn't add them. This tab also lists source members who can't be adopted, with the reason for each.

#### Source members who can't be adopted

C1 doesn't create users or accounts, so a source member can be left out of the new group. Reasons include an account that isn't linked to a C1 user, a linked user who is missing, deleted, disabled, or not a person, an app account whose invitation hasn't been accepted, and a principal type that adoption doesn't support.

When any source members can't be adopted, the **Review** step warns you, and you must select **I understand these source members will not be added to the group.** before you can continue. Open **Exclusions** first to see who is affected and why.

If the source has no eligible users, C1 asks you to choose another entitlement or start from scratch.

### Manage adoption jobs

Each analysis is saved as a job. The **Adoption history** tab on the **Dynamic groups** page lists every job with its source entitlement, app, status, created group, and last update. Select a job to reopen it.

| Status | What it means |
|---|---|
| **Analyzing** | C1 is reading the source and building the recommendation. |
| **Requires review** | The analysis is ready. Reopen the job to review it and create the group. |
| **Creating group** | C1 is creating and configuring the group. Status updates automatically. |
| **Completed** | The group exists. Use **View group** to open it. |
| **Failed** | The job can't continue. |

A failed job can't be resumed. If no group was created, click **Start a new analysis** to analyze the source's current membership. If C1 had already created the group, click **Manage group** and finish setting it up there. If you leave while the group is being created, creation continues. Check **Adoption history** for its status.

If C1 can't confirm that an analysis started, check **Adoption history** before starting another one. Each analysis creates a separate job.

### What adoption does and doesn't do

- **It's a one-time setup.** The new group is an ordinary C1 group. Later changes to the source entitlement, or to who holds it, don't update the group. The rule keeps evaluating user attributes like any other group rule, and you can edit the rule, inclusions, and exclusions afterward.
- **It never changes the source.** C1 doesn't write to your identity provider or app, and it doesn't change the source entitlement or role assignments.
- **It doesn't create users or accounts.** Only existing, enabled C1 users become members.

## Duplicate a C1 group

Need a group that's similar to one that already exists? To save time, you can duplicate an existing group and then make adjustments as needed. 

<Steps>
<Step>
On the **Dynamic groups** page, find the group you want to duplicate. 
</Step>
<Step>
Click the **...** (more actions) menu, then choose **Duplicate**.
</Step>
</Steps> 

The new group will be pre-filled with the same name, description, and membership rule as the original, which you can then edit.

## Manually add users to a group 

If you need to manually add users to the access profile who do not match the membership automation condition, click **Add users**.

The users you add will be shown in the list of members, with a notation that they were added manually, rather than by membership automation. 

## Review group membership in an access review campaign

You can include C1 group memberships in an [access review campaign](/product/admin/campaigns), including memberships in groups that C1 fills automatically from a membership rule. Reviewers then certify or deny each member the same way they review access in any other app.

C1 groups are resources in the C1 app, so you select them the way you select any other entitlements. In step 3 of campaign setup, choose the C1 app and select group membership entitlements with **Entitlements**, **Entitlements by type**, or a **Custom selector**. See [Choose what to review](/product/admin/campaigns#step-3-choose-what-to-review). One-time campaigns and recurring campaign templates both support group memberships.

When a reviewer decides on a member:

- **Certify** keeps the member in the group, including a member that the membership rule added.
- **Deny** removes the member from the group. If the membership rule added the member, C1 also adds them to the group's exclusion list so the rule doesn't add them back the next time it runs. A member who was added manually, or through a request, is simply removed.

Ownership entitlements and a group's exclusion entitlement can't be added to a campaign.

## Frequently asked questions about C1 groups

<AccordionGroup>
<Accordion title="How often does the membership rule sync?">

A new sync is kicked off each hour. 

</Accordion>
<Accordion title="Can users request access to a C1 group?">

Yes. Add the group's entitlement to an app's [requestable entitlements](/product/admin/access-requests#set-the-standard-audience-for-an-app-and-select-requestable-entitlements) or to an [access profile](/product/admin/profiles) like any other entitlement, and users can request group membership with the same approvals, durations, and revocation as other requestable access.

Members added through a request aren't removed by the group's membership automation rule — the same protection that already applies to users you add manually.

</Accordion>
<Accordion title="How do I fetch C1 groups with the API?">

There is no dedicated groups endpoint in the C1 API. C1 groups are resources of the group resource type in the C1 app, so you fetch them with the app resource endpoints:

1. Find the group resource type for the C1 app: `GET /api/v1/apps/{app_id}/resource_types`
2. List the group resources of that type: `GET /api/v1/apps/{app_id}/resource_types/{app_resource_type_id}/resources`
3. To get a group's entitlements (such as its member entitlement), list the entitlements associated with that resource: `GET /api/v1/apps/{app_id}/entitlements/resource_types/{app_resource_type_id}/resources/{app_resource_id}`

In each request, `app_id` is the ID of the built-in C1 app.

</Accordion>
</AccordionGroup>
