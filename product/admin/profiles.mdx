## What's an access profile?

Everyone in your organization needs access to the software your whole team uses to stay in touch and get work done. But an employee in the Accounting department probably doesn't need access to the specialized tools the Product Design team uses, or vice versa. For both simplicity and security, limit the list of resources each employee at your company can request by creating _access profiles_.

Access profiles are groups of resources and entitlements. You determine the contents of each profile and who the profile is visible to. You'll likely want to create two kinds of access profiles:

- General access profiles with the tools and access used by everyone in your company, which are visible to everyone

- Access profiles scoped to certain departments, job types, or access levels, which are only visible to the folks in those groups

When [requesting access](/product/how-to/create-requests/) in C1 or through Slack, each employee can see and request the contents of the access profiles they have access to, but nothing more.

You also have the option to allow employees to ask for _all_ the resources and entitlements in an access profile. This is called a _profile request_, and is especially useful for onboarding or times when employees will need access to several interrelated entitlements. 

Profiles available to an employee for profile requests are shown on the **Profiles** tab of the **New request** form and the **Requests** page. Need instructions for requesting a profile? See [Request an access profile](/product/how-to/create-requests#request-an-access-profile). 

Not all access works by request, though. Some of it should simply show up when someone starts a job or joins a team, and access profiles can handle that, too. That's what [access profile types](#access-profile-types) are for. 

## Access profile types

Each access profile has a type, which decides how it grants access:

- **Catalog:** Access people request, such as a design tool or a data visualization license. Catalogs don't track members.
- **Role:** Access that arrives with the job. A membership condition such as `department == "Sales"` gives every new Sales hire the CRM and the team's shared drive, with no request.
- **Hybrid:** A mix of both automatically granted and requestable access. An Engineering profile might grant source control automatically and let people request production database access when they need it.

The type also decides which settings a profile has, so you only see the ones that apply:

| | **Catalog** | **Role** | **Hybrid** |
|---|:---:|:---:|:---:|
| Users can request the profile's entitlements | ✓ | | ✓ |
| Users can request membership in the profile | | ✓ (through a catalog) | ✓ |
| Members are tracked | | ✓ | ✓ |
| Membership is granted automatically from a condition | | ✓ | ✓ |
| Joiner and leaver behavior (JML) | | ✓ | ✓ |

On the **Access profiles** page, each access profile's type appears as a label next to its name, and you can filter the list by **Type**.

<Note>
Access profile types aren't the same as [profile types](/product/admin/profile-types), which segment your users and decide which attributes appear on their profiles.
</Note>

<Tip>
**Want to automatically add users to access profiles as part of onboarding?** 

Check out [Automate onboarding & offboarding access changes](/product/admin/dynamic-access-control) to learn more about setting up automatic membership for people who join, leave, or change roles. 
</Tip>

## Create a new access profile
{/* header name used in links, change with caution */}

Each access profile type is created and set up a little differently. Follow the instructions for the type you want to create:

- [Create a catalog](#create-a-catalog)
- [Create a role](#create-a-role)
- [Create a hybrid access profile](#create-a-hybrid-access-profile)

Not sure which to choose? See [Access profile types](#access-profile-types).

### Create a catalog

A catalog is a collection of entitlements that people request. Catalogs don't track who has been granted what. 

<Steps>
<Step>
Navigate to **Governance** > **Access profiles** and click **New profile**.
</Step>
<Step>
On the **Access profile type** step, choose **Catalog**, enter a name and an optional description, then click **Next**.
</Step>
<Step>
On the **Request audience** step, choose who can request entitlements in this catalog: **Everyone**, or **Users with entitlements**, which limits requests to people who already hold the entitlements you select. 

   Use the **Create catalog with requests enabled** toggle to turn requests on now, or leave it off until you're ready to launch.
</Step>
<Step>
On the **Access** step, select the apps and entitlements people can request. (You can also add apps and entitlements later.)
</Step>
<Step>
Click **Create**. (If you don't select any entitlements now, the button reads **Create without access**.)

   Your new access profile is created. Next we'll fine-tune the settings and assign an owner. You can always come back to the **Apps** and **Settings** tabs to make changes later. 
</Step>
<Step>
Assign the access profile an owner. On the catalog's **Settings** tab, click **Owners** at the top of the page (a pencil icon appears when you hover over it) and select one or more owners. 

   Because an access profile is a resource within [the C1 application](/product/admin/c1-for-c1), naming an owner or owners makes it possible to set up review, request, and revoke [policies](/product/admin/policies) that assign these tasks to the owner of the access profile.
</Step>
<Step>
To change the access profile's name, description, or annotations, click the catalog's name or any of those labels to open the **Edit access profile** drawer.
</Step>
<Step>
**Optional.** To change which entitlements the catalog offers, navigate to the **Apps** tab and click **Manage**. Select the apps you want to include, the entitlements within each app, and review what you're adding or removing, then click **Save changes**. 

   See [Add an entitlement to an existing access profile](#add-an-entitlement-to-an-existing-access-profile) for tips.
</Step>
<Step>
**Optional.** To change who can request from the catalog, navigate to the **Settings** tab and click **Edit** in the **Allow requests** area. Turn **Allow requests** on or off, and under **Profile is visible to**, choose **Everyone** or **Users with entitlements**. 

   If you choose **Users with entitlements**, use the dropdown to find and add the entitlements. Only users who currently hold them can view and request the catalog's contents. 
</Step>
</Steps>

**Done.** The catalog appears in the **Access profiles** page list with its type next to its name. Once requests are turned on, the contents are visible to the employees you selected on the **New request** form, the **Requests** page, and in Slack or Teams (if enabled).

### Create a role

A role grants its entitlements automatically to people who meet a membership condition. Roles track their members, and people can also request membership through a catalog.

<Steps>
<Step>
Navigate to **Governance** > **Access profiles** and click **New profile**.
</Step>
<Step>
On the **Access profile type** step, choose **Role**, enter a name and an optional description, then click **Next**.
</Step>
<Step>
On the **Birthright membership** step, decide who gets the role automatically. Under **Add and remove users based on**, choose **Users with entitlements** and select the entitlements people must hold to be members, or choose **Expression** and write a [CEL expression](/product/admin/expressions), or have C1AI draft one from a plain-language description.

   Turn on **Create role with automation enabled** if you want the condition to start granting membership as soon as the role is created.
</Step>
<Step>
On the **Self-service membership** step, choose the catalogs to add this role to. Users in those catalogs can then request the role.
</Step>
<Step>
On the **Access** step, select the apps and entitlements members receive. (You can also add apps and entitlements later.)
</Step>
<Step>
Click **Create**. (If you don't select any entitlements now, the button reads **Create without access**.)

   Your new access profile is created. Next we'll fine-tune the settings and assign an owner. You can always come back to the **Apps** and **Settings** tabs to make changes later.
</Step>
<Step>
Assign the access profile an owner. On the role's **Settings** tab, click **Owners** at the top of the page (a pencil icon appears when you hover over it) and select one or more owners.

   Because an access profile is a resource within [the C1 application](/product/admin/c1-for-c1), naming an owner or owners makes it possible to set up review, request, and revoke [policies](/product/admin/policies) that assign these tasks to the owner of the access profile.
</Step>
<Step>
To change the access profile's name, description, or annotations, click the role's name or any of those labels to open the **Edit access profile** drawer.
</Step>
<Step>
**Optional.** To change which entitlements members receive, navigate to the **Apps** tab and click **Manage**. Select the apps you want to include, the entitlements within each app, and review what you're adding or removing, then click **Save changes**.

   See [Add an entitlement to an existing access profile](#add-an-entitlement-to-an-existing-access-profile) for tips.
</Step>
<Step>
**Optional.** To fine-tune the role, navigate to the **Settings** tab:

   - **Birthright membership** grants membership automatically from a condition. Click **Sync now** to run the condition right away instead of waiting for the next hourly sync. The **Advanced** line below it holds excluded users, what happens to access when membership changes, and anomaly detection.
   - **Self-service membership** lists the catalogs users can request the role from, and the longest a person can be a member (**Max membership duration**).
   - **Approval policies** sets the membership grant and revoke policies, and whether each entitlement's own grant and revoke policies are enforced or bypassed.

   See [Automate onboarding & offboarding access changes](/product/admin/dynamic-access-control#set-up-membership-automation-on-a-role) for how membership conditions work, and [Grant duration and expiration in access profiles](#grant-duration-and-expiration-in-access-profiles) for what happens to access when membership ends.
</Step>
</Steps>

**Done.** The role appears in the **Access profiles** page list with its type next to its name. People who meet the membership condition become members and receive the role's entitlements.

The **Members** tab shows how many members the role has, how many are pending, and how many are expiring. The table lists each member's **Date added**, how they were added (**Added via**), and when their membership **Expires**. To add someone yourself, click **Add users**, select one or more users, and click **Save**. This starts the access changes for those users.

### Create a hybrid access profile

A hybrid access profile combines both behaviors. People can request its entitlements one at a time or request membership in the whole profile, and it can also grant its entitlements automatically to anyone who meets a membership condition. Hybrid access profiles track who their members are. Hybrid is labeled **Advanced** in the type picker because it has the most settings to configure.

<Steps>
<Step>
Navigate to **Governance** > **Access profiles** and click **New profile**.
</Step>
<Step>
On the **Access profile type** step, choose **Hybrid**, enter a name and an optional description, then click **Create**.

   Your new access profile is created. Next we'll assign an owner, add entitlements, and fine-tune the settings. You can always come back to the **Apps** and **Settings** tabs to make changes later.
</Step>
<Step>
Assign the access profile an owner. On the access profile's **Settings** tab, click **Owners** at the top of the page (a pencil icon appears when you hover over it) and select one or more owners.

   Because an access profile is a resource within [the C1 application](/product/admin/c1-for-c1), naming an owner or owners makes it possible to set up review, request, and revoke [policies](/product/admin/policies) that assign these tasks to the owner of the access profile.
</Step>
<Step>
To change the access profile's name, description, or annotations, click the access profile's name or any of those labels to open the **Edit access profile** drawer.
</Step>
<Step>
Add apps and entitlements. Navigate to the **Apps** tab and click **Manage**. Select the apps you want to include, the entitlements within each app, and review what you're adding or removing, then click **Save changes**. (You can also add apps and entitlements later.)

   See [Add an entitlement to an existing access profile](#add-an-entitlement-to-an-existing-access-profile) for tips.
</Step>
<Step>
Set who can view and request from the access profile. Navigate to the **Settings** tab, click **Edit** in the **Allow requests** area, and turn on **Allow requests**. You can leave this off until you're ready to launch.
</Step>
<Step>
Under **Profile is visible to**, choose whether the access profile can be viewed and requested by everyone in your organization, or only by users who currently hold specific entitlements.

   If you choose **Users with entitlements**, use the dropdown to find and add the entitlements. Only users who currently hold them can view and request the access profile's contents.
</Step>
<Step>
Under **Allow requests for**, choose **Entitlements only** or **Entitlements and profile membership**. This sets whether employees can request only the entitlements in the profile, or the entire access profile (membership) as well.

   Membership in the access profile means that changes to the profile are automatically applied to its members' access. When someone requests membership, C1 creates individual request tickets for each entitlement in the access profile not yet granted to the employee.
</Step>
<Step>
Click **Save**.
</Step>
<Step>
**Optional.** To grant membership automatically, click **Edit** in the **Membership automation** area and set the membership condition.

   See [Set up membership automation on a hybrid profile](/product/admin/dynamic-access-control#set-up-membership-automation-on-a-hybrid-profile).
</Step>
<Step>
**Optional.** Click **Edit** in the **Joiner** area to set what happens when someone joins:

   - **Approval policy:** the policy used for the profile's membership entitlement.
   - **Entitlement provisioning:** whether each entitlement's own grant policy is enforced or bypassed.
   - **Max membership duration:** the longest a person can be a member.
</Step>
<Step>
**Optional.** Click **Edit** in the **Leaver** area to set what happens when someone leaves:

   - **Leaving policy:** the policy used when membership is revoked.
   - **Access change behavior:** whether access is left as-is, or all or only unjustified entitlements are revoked.
   - **Entitlement deprovisioning:** whether each entitlement's own revoke policy is enforced or bypassed.

   See [Grant duration and expiration in access profiles](#grant-duration-and-expiration-in-access-profiles) for what each **Access change behavior** option does.
</Step>
</Steps>

**Done.** The access profile appears in the **Access profiles** page list with its type next to its name. Its contents are visible to the employees you selected on the **New request** form, the **Requests** page, and in Slack or Teams (if enabled). If you allowed profile membership requests, your selected users can request membership from the **Profiles** tab on the **New request** form and the **Requests** page.

The **Members** tab shows how many members the access profile has, how many are pending, and how many are expiring. The table lists each member's **Date added**, how they were added (**Added via**), and when their membership **Expires**. To add someone yourself, click **Add users**, select one or more users, and click **Save**. This starts the access changes for those users.

## Change an access profile's type

Needs change. If a hybrid profile turns out to be doing only one job, you can change its type after you create it, for example from hybrid to catalog or role.

<Steps>
<Step>
Open the access profile's details page.
</Step>
<Step>
Click the **...** (more actions) menu and select **Change type...**.
</Step>
<Step>
Choose the new type. C1 reviews the profile and lists what will change, in up to three groups:

   - **Required changes.** Things you must fix before the type can change. For example, you need to turn off requests before changing to a role, turn off membership automation before changing to a catalog, remove any roles from a catalog before changing its type, and remove a role from every catalog it belongs to before changing its type.
   - **Behavior unavailable for this type.** Settings that stop applying after the change.
   - **Additional information.** What stays the same. Existing members and the grants they already have are not changed.
</Step>
<Step>
Click **Change type**.
</Step>
</Steps>

## Add an entitlement to an existing access profile

There are two ways to add an entitlement to an access profile.

<Tip>
**Tips for adding entitlements to access profiles:**

**1. Make sure you're adding the right access entitlements.** If you have applications that are sourced through your identity provider (IdP), be sure to add the access entitlement for the app itself, and not the access entitlement for the app via IdP, which only grants the ability to SSO into the app.

Here's an example: When Docusign is sourced through Okta, you'll see two Docusign access credentials. To add Docusign access to your access profile, choose the **Docusign credential** entitlement, not the **Okta app** entitlement.

<Frame>
<img src="/images/product/assets/catalogs-entitlement-clarification.png" alt="A screenshot showing the Apps tab of an access profile with entitlements grouped by app."/>

</Frame>
**2. Make sure every entitlement you add has a request policy set.** Make sure that each entitlement you add to an access profile has a request policy set on either [the application](/product/admin/access-requests#set-app-level-access-request-rules) or [the entitlement](/product/admin/access-requests#configure-access-request-settings-on-an-individual-entitlement). If no request policy is set, users attempting to request the entitlement will see an error message. This is a known issue and will be corrected.

**3. Take advantage of role mining recommendations.** Once your access profile begins to take shape, C1 can suggest entitlements to add, with a confidence score for each: 80% or higher is a great fit, 50%–79% might be a good fit, and 49% or lower likely isn't. Suggestions get more accurate as the profile's list of members grows, and a profile with no members has none. For org-wide suggestions and custom cohort analysis, see [Use role mining](/product/admin/role-mining).
</Tip>

### Manage entitlements from the access profile's Apps tab

On the **Apps** tab of an access profile's details page, entitlements are organized by app. You have two options:

- **To add a new app (and select its entitlements)**: Click **Manage**. Select the apps you want to add (step 1), then select the specific entitlements within those apps (step 2), and click **Save changes**.
- **To change which entitlements from an existing app are in the profile**: Click the pencil icon next to the app. Check or uncheck entitlements in the drawer, then click **Save changes**.

<Tip>
**For hybrid profiles, current members are not automatically granted new entitlements added to the access profile.** 

If you want all current members to receive the entitlements you've added to the access profile, check the **Create requests for currently enrolled users** box on the review step before saving your changes. For roles, this box is checked by default. C1 will automatically create access request tasks for each new entitlement for each member. Alternatively, you can leave the box unchecked and follow the process in [Update a current access profile holder's grant](/product/admin/profiles#update-a-current-access-profile-holders-grant).
</Tip>

### Add an entitlement on the entitlement's details page

Alternatively, you can add an entitlement to an existing access profile from the entitlement's own details page. This method is ideal for times when you want to add a single entitlement to multiple access profiles. 

<Steps>
<Step>
Navigate to the **Apps** page.

</Step>
<Step>
On the **Managed apps** tab, navigate to the entitlement you want to add to an access profile:

   - Click the application's name
   - Click the **Entitlements** tab
   - Locate the entitlement you want and click its name

</Step>
<Step>
In the **Access requests** section of the entitlement's details page, click **Edit**.
</Step>
<Step>
In the **Access profiles** field, search for and select one or more access profiles you want to add the entitlement to.

</Step>
<Step>
Click **Save**.
</Step>
</Steps>

The entitlement is now included in the access profile. Users who have access to the access profile will see the entitlement as an option on the **New request** form, the **Requests** page, and in Slack or Teams (if enabled). 

### Update a current access profile holder's grant

If profile requests are allowed, any newly added entitlement will be included in future grants of the full access profile, but the entitlement will not be automatically granted retroactively to users who were previously granted the access profile. To manually add the new entitlement to a current profile holder's access: 

<Steps>
<Step>
Navigate to the access profile's **Apps** tab. 
</Step>

<Step>
Locate the newly added entitlement in the list of entitlements included in the access profile and click the **...** (more actions) menu. 
</Step>

<Step>
Select **Manage provisioning**. 
</Step>

<Step>
Any users who have been granted the full access profile but do not currently have access to the entitlement display **Not granted** in the **Status** column. Click **Request** for the users who you want to receive access to the new entitlement. 

   You can also click **Request for all** to request access for all profile holders who do not have the entitlement. 
</Step>
</Steps>

**Done.** C1 automatically creates an access request for the entitlement for each user. You can track the progress of the access requests at any time by returning to the **Manage provisioning** drawer.

## Grant duration and expiration in access profiles

Access profiles control how long a user can be a *member*, but they don't control how long the underlying grants last. When a user becomes a member of a profile, C1 creates individual grants for each entitlement in the profile — and each grant follows the duration configured on that entitlement, not the profile's membership duration. If different entitlements in the same profile have different durations configured, their grants will expire at different times, independently of each other and independently of when the membership itself ends.

What happens to those grants when a profile membership ends depends on the profile's **Access change behavior** setting. Depending on how this is configured, grants may be left in place, revoked, or revoked unless the user has another active membership justifying them.

### Profile expiration settings

Roles and hybrid profiles have two settings that control membership duration and what happens when it ends. You can find and set these on the access profile's **Settings** tab. On a hybrid profile, **Max membership duration** is in the **Joiner** area and **Access change behavior** is in the **Leaver** area. On a role, **Max membership duration** is in the **Self-service membership** area, and the same setting is called **Revoke behavior** and is under the **Advanced** line of **Birthright membership**. 

- **Max membership duration** — the longest a user can be a member. If a user requests a duration longer than the maximum, it's capped. If they don't specify a duration, the maximum is used as the default.
- **Access change behavior** (**Revoke behavior** on a role) — what C1 does to a user's entitlement grants when their profile membership ends. There are three options:
  - **Leave access as-is** — grants are not touched when membership ends. Access continues until grants expire on their own schedule or are revoked manually.
  - **Revoke all entitlements** — all grants created by this membership are revoked when membership ends, regardless of any other access the user holds.
  - **Revoke unjustified entitlements** — grants are revoked when membership ends, unless the user is still a member of another active profile that includes the same entitlement. A direct grant to the same entitlement does not count as justification.

### When a user has both a profile membership and a direct grant

A user may hold the same entitlement from two sources at once: a profile membership and a direct grant. In that case, both the individual grant durations and the profile's **Access change behavior** setting affect what happens to access over time.

| When does access end? | Access change behavior setting | What happens |
|---|---|---|
| The direct grant expires before the profile membership ends | Any | Access is revoked when the direct grant expires, even though the membership is still active |
| The profile membership ends; the direct grant is still active | Leave access as-is | Access continues. The direct grant remains active. |
| The profile membership ends; the direct grant is still active | Revoke all entitlements | Access is revoked, regardless of the direct grant |
| The profile membership ends; the direct grant is still active | Revoke unjustified entitlements | Access is revoked. A direct grant does not count as justification. |

## Frequently asked questions about creating access profiles

<AccordionGroup>
<Accordion title="How do I let people request a role?">
Add the role to a catalog from the role's **Self-service membership** settings. Users who can see that catalog can then request the role. See [Create a role](#create-a-role).
</Accordion>
<Accordion title='What does the "This profile needs configuration" banner mean?'>
On a catalog or role, this banner on the **Settings** tab tells you what's still missing, and a warning icon appears next to the tab. A catalog needs requests turned on, at least one entitlement, and an audience. A role needs birthright membership or self-service membership turned on.
</Accordion>
<Accordion title="What happens if part of the setup fails when I create an access profile?">
C1 still creates the access profile and lists the steps that didn't finish. Click **View profile settings** to finish them from the profile's **Settings** tab.
</Accordion>
</AccordionGroup>
