## What's an access profile?

Everyone in your organization needs access to the software your whole team uses to stay in touch and get work done. But an employee in the Accounting department probably doesn't need access to the specialized tools the Product Design team uses, or vice versa. For both simplicity and security, limit the list of resources each employee at your company can request by creating _access profiles_.

Access profiles are groups of resources and entitlements. You determine the contents of each profile and who the profile is visible to. You'll likely want to create two kinds of access profiles:

- An access profile with the tools and access used by everyone in your company, which is visible to everyone

- Access profiles scoped to certain departments, job types, or access levels, which are only visible to the folks in those groups

When [requesting access](/product/how-to/create-requests/) in C1 or through Slack, each employee can see and request the contents of all the access profiles they have access to, but nothing more.

You also have the option to allow employees to ask for _all_ the resources and entitlements in an access profile. This is called a _profile request_, and is especially useful for onboarding or times when employees will need access to several interrelated entitlements. 

Profiles available to an employee for profile requests are shown on the **Profiles** tab of the **New request** form and the **Requests** page. 

Not all access works by request, though. Some of it should simply show up when someone starts a job or joins a team, and access profiles can handle that, too. That's what access profile types are for. See [Access profile types](#access-profile-types).

<Tip>
**Want to automatically add users to access profiles as part of onboarding?** 

Check out [Automate onboarding & offboarding access changes](/product/admin/dynamic-access-control) to learn more about setting up automatic membership for people who join, leave, or change roles. 
</Tip>

## Access profile types

Not everything people need at work is something they should have to ask for. A designer who occasionally needs a data visualization license should request it. A new Sales hire who needs the CRM on day one shouldn't have to. Each access profile has a type, so it behaves the way you intend.

- **Catalog.** Use a catalog for access people should request. Anyone in your company might need a design tool, a data visualization license, or read access to an analytics dashboard now and then, but not everyone does, so employees pick the specific items they need.
- **Role.** Use a role for access that arrives with someone's job. Every new Sales hire needs the CRM, the sales engagement tool, and the team's shared drive, so you can put them in a role with a membership condition such as `department == "Sales"`. People get the access automatically when they match the condition, and nobody has to file a request.
- **Hybrid.** Use a hybrid profile for a mix of both. An Engineering profile might grant source control and the team chat automatically, while letting people request production database access only when they need it.

Here's how the three types compare:

| Type | What it does |
|---|---|
| **Catalog** | A collection of entitlements that a group of users can self-service request. Catalogs don't track members. |
| **Role** | Grants entitlements automatically based on a membership condition. A role explicitly tracks who is a member, and membership can be granted, revoked, and requested just like other entitlements. |
| **Hybrid** | A collection of entitlements that people can request, either one at a time or by requesting membership in the profile. It can also grant its entitlements automatically to anyone who meets a membership condition. Members are tracked, so you can see who belongs to the profile. |

If you created access profiles before access profile types existed, they're all hybrid profiles, and nothing about how they work changes. You'll see each access profile's type as a label next to its name, and you can filter the **Access profiles** list by **Type**.

<Note>
Access profile types are not the same as [profile types](/product/admin/profile-types). Profile types segment your users and decide which attributes appear on their profiles. Access profile types decide how an access profile grants access.
</Note>

The type also decides which settings a profile has, so you only see the ones that apply:

| | **Catalog** | **Role** | **Hybrid** |
|---|:---:|:---:|:---:|
| Users can request the profile's entitlements | ✓ | | ✓ |
| Users can request membership in the profile | | ✓ (through a catalog) | ✓ |
| Members are tracked | | ✓ | ✓ |
| Membership is granted automatically from a condition | | ✓ | ✓ |
| Joiner and leaver behavior (JML) | | ✓ | ✓ |

<Note>
Settings for roles, such as membership automation, require JML to be enabled for your tenant.
</Note>

## Create a new access profile
{/* header name used in links, change with caution */}

Creating an access profile starts with choosing its type, because the type decides what else you'll set up.

<Steps>
<Step>
Navigate to **Governance** > **Access profiles** and click **New profile**.
</Step>
<Step>
On the **Access profile type** step, choose the access profile type (**Catalog**, **Role**, or **Hybrid**), then enter a name and an optional description.

   Most people should start with a **Catalog** or a **Role**. **Hybrid** is labeled **Advanced** because it combines both behaviors, so it has the most settings to configure. If you choose **Hybrid**, click **Create**, then finish setting it up as described in [Configure owners, entitlements, and requests](#configure-owners-entitlements-and-requests). For **Catalog** and **Role**, click **Next**.
</Step>
<Step>
Complete the remaining steps for your type. You can click **Skip** on a step to configure it later.

   **For a catalog:**

   - **Request audience.** Choose who can request entitlements in this profile: **Everyone**, or **Users with entitlements**, which limits requests to people who already hold the entitlements you select. Use the **Create catalog with requests enabled** toggle to turn requests on now or leave them off until you're ready to launch.
   - **Access.** Select the apps and entitlements people can request.

   **For a role:**

   - **Membership automation.** Decide who gets the role automatically. Under **Add and remove users based on**, choose **Users with entitlements** and select the entitlements people must hold to be members, or choose **Expression** and write a [CEL expression](/product/admin/expressions), or have C1AI draft one from a plain-language description. Turn on **Create role with automation enabled** if you want the condition to start granting membership as soon as the role is created.
   - **Self-service membership.** Choose the catalogs to add this role to. Users in those catalogs can then request the role.
   - **Access.** Select the apps and entitlements members receive.
</Step>
<Step>
Click **Create**. If you didn't select any entitlements, the button reads **Create without access**.
</Step>
</Steps>

**Done.** The new profile appears in the **Access profiles** list with its type next to its name. If part of the setup fails, C1 still creates the profile and lists the steps that didn't finish. Click **View profile settings** to finish them from the profile's **Settings** tab.

### Configure owners, entitlements, and requests

Finish setting up a profile from its details page. Which steps you need depends on the access profile's type and on what you configured in the wizard.

<Steps>
<Step>
Open the access profile's details page.
</Step>
<Step>
Assign an owner to the access profile. Click **Owners** at the top of the page (a pencil icon appears when you hover over it) and select one or more owners. To change the name, description, or annotations, click the access profile's name or any of those labels to open the **Edit access profile** drawer.  

   Because an access profile is a resource within [the C1 application](/product/admin/c1-for-c1), naming an owner or owners makes it possible to set up review, request, and revoke [policies](/product/admin/policies) that assign these tasks to the owner of the access profile. 
</Step>
<Step>
Add apps and entitlements to the profile. On the **Apps** tab, click **Manage**, then select the apps you want to include in the profile (step 1), the entitlements within each app (step 2), and review what you're adding or removing (step 3).

<Tip>
   **Tips for adding entitlements to access profiles:**

   **1. Make sure you're adding the right access entitlements.** If you have applications that are sourced through your identity provider (IdP), be sure to add the access entitlement for the app itself, and not the access entitlement for the app via IdP, which only grants the ability to SSO into the app.

   Here's an example: When Docusign is sourced through Okta, you'll see two Docusign access credentials. To add Docusign access to your access profile, choose the **Docusign credential** entitlement, not the **Okta app** entitlement.

   <Frame>
   <img src="/images/product/assets/catalogs-entitlement-clarification.png" alt="A screenshot showing the Apps tab of an access profile with entitlements grouped by app."/>

   </Frame>
   **2. Make sure every entitlement you add has a request policy set.** Make sure that each entitlement you add to an access profile has a request policy set on either [the application](/product/admin/access-requests#set-app-level-access-request-rules) or [the entitlement](/product/admin/access-requests#configure-access-request-settings-on-an-individual-entitlement). If no request policy is set, users attempting to request the entitlement will see an error message. This is a known issue and will be corrected.

   **3. Take advantage of role mining recommendations.** Once your access profile begins to take shape, C1 can offer data-driven recommendations for which entitlements to add to the access profile. [Read more about role mining.](/product/admin/profiles#use-role-mining-recommendations) 
</Tip>
</Step>
<Step>
When you've selected the entitlements you want to add to the access profile (don't worry, you can always adjust this list later), click **Save changes**.
</Step>
<Step>
Set who can view and request items from this access profile. On the **Settings** tab, in the **Allow requests** area of the screen, click **Edit**.
</Step>

<Step>
Click to turn on **Allow requests**. This makes the access profile's contents available to the selected requesters. You can leave this toggle disabled until you're ready to launch the access profile.
</Step>
<Step>
Under **Profile is visible to**, set whether this access profile can be viewed and requested by everyone in your organization, or just users who are currently granted specific entitlements. 

   If you choose the **Users with entitlements** option, use the dropdown to find and add the entitlements. Only users who are currently assigned the entitlements you choose can view and request this access profile's contents.
</Step>
<Step>
If you're setting up a hybrid profile, under **Allow requests for**, choose **Entitlements only** or **Entitlements and profile membership** to set whether employees can request only the entitlements in the profile, or the entire access profile (membership) as well. Catalogs don't have this option, because they don't track members. Membership in the access profile means that changes to the profile will be automatically applied to its members' access.

   C1 will automatically create individual request tickets for each entitlement in the access profile not yet granted to the employee.
</Step>
<Step>
Click **Save**.
</Step>
</Steps>

**Done.** The access profile is shown in the list of access profiles, and is requestable. Its contents are visible to the employees you selected on the **New request** form, the **Requests** page, and in Slack or Teams (if enabled). If you allowed profile membership requests, your selected users can request membership from the **Profiles** tab on the **New request** form and the **Requests** page. 

### Use role mining recommendations

Role mining analyzes access patterns across your organization to suggest entitlements for access profiles. C1 assigns a confidence score to each entitlement suggestion:

* 80% or higher — This entitlement is a great fit for this access profile
* 50%–79% — This entitlement might be a good fit for this access profile
* 49% or lower — This entitlement likely isn't a good fit for this access profile

Role mining becomes more accurate as your access profile grows and your list of members is established. If an access profile has no members yet, no recommendations are shown.

For org-wide suggestions and custom cohort analysis, see [Use role mining](/product/admin/role-mining).

### Configure a catalog or role

An access profile's **Settings** tab replaces the **Overview**, **Requests**, and **JML** tabs. It shows only the settings that apply to the access profile's type:

- **Catalog:** the **Allow requests** setting, which controls whether requests are on and who can request the profile's entitlements.
- **Role:**
  - **Membership automation** grants membership automatically from a condition. Click **Sync now** to run the condition right away instead of waiting for the next hourly sync. The **Advanced** line below it holds excluded users, what happens to access when membership changes, and anomaly detection.
  - **Self-service membership** lists the catalogs users can request the role from, and the longest a person can be a member (**Max membership duration**).
  - **Approval policies** sets the membership grant and revoke policies, and whether each entitlement's own grant and revoke policies are enforced or bypassed.
- **Hybrid:** **Allow requests**, **Membership automation**, **Joiner**, and **Leaver**. See [Grant duration and expiration in access profiles](#grant-duration-and-expiration-in-access-profiles) for the **Joiner** and **Leaver** settings.

If a catalog or role isn't set up to do anything yet, a **This profile needs configuration** banner on the **Settings** tab tells you what's missing, and a warning icon appears next to the tab. For example, a catalog needs requests turned on, at least one entitlement, and an audience. A role needs membership automation or self-service membership turned on. See [Automate onboarding & offboarding access changes](/product/admin/dynamic-access-control) for how membership conditions work.

### Track members

Roles and hybrid profiles have a **Members** tab, which shows how many members the profile has, how many are pending, and how many are expiring. The table lists each member's **Date added**, how they were added (**Added via**), and when their membership **Expires**. To add someone yourself, click **Add users**, select one or more users, and click **Save**. This starts the access changes for those users.

Catalogs don't track members, so they don't have a **Members** tab.

### Change an access profile's type

Needs change. If a hybrid profile turns out to be doing only one job, you can change its type after you create it, for example from hybrid to catalog or role.

<Steps>
<Step>
Open the access profile's details page.
</Step>
<Step>
Click the **...** (more actions) menu and select **Change type...**.
</Step>
<Step>
Choose the new type. C1 reviews the profile and lists what will change, in up to three groups:

   - **Required changes.** Things you must fix before the type can change. For example, you need to turn off requests before changing to a role, turn off membership automation before changing to a catalog, remove any roles from a catalog before changing its type, and remove a role from every catalog it belongs to before changing its type.
   - **Behavior unavailable for this type.** Settings that stop applying after the change.
   - **Additional information.** What stays the same. Existing members and the grants they already have are not changed.
</Step>
<Step>
Click **Change type**.
</Step>
</Steps>

## Add an entitlement to an existing access profile

There are two ways to add an entitlement to an access profile.

### Manage entitlements from the access profile's Apps tab

On the **Apps** tab of an access profile's details page, entitlements are organized by app. You have two options:

- **To add a new app (and select its entitlements)**: Click **Manage**. Select the apps you want to add (step 1), then select the specific entitlements within those apps (step 2), and click **Save changes**.
- **To change which entitlements from an existing app are in the profile**: Click the pencil icon next to the app. Check or uncheck entitlements in the drawer, then click **Save changes**.

<Tip>
**For hybrid profiles, current members are not automatically granted new entitlements added to the access profile.** 

If you want all current members to receive the entitlements you've added to the access profile, check the **Create requests for currently enrolled users** box on the review step before saving your changes. For roles, this box is checked by default. C1 will automatically create access request tasks for each new entitlement for each member. Alternatively, you can leave the box unchecked and follow the process in [Update a current access profile holder's grant](/product/admin/profiles#update-a-current-access-profile-holders-grant).
</Tip>

### Add an entitlement on the entitlement's details page

Alternatively, you can add an entitlement to an existing access profile from the entitlement's own details page. This method is ideal for times when you want to add a single entitlement to multiple access profiles. 

<Steps>
<Step>
Navigate to the **Apps** page.

</Step>
<Step>
On the **Managed apps** tab, navigate to the entitlement you want to add to an access profile:

   - Click the application's name
   - Click the **Entitlements** tab
   - Locate the entitlement you want and click its name

</Step>
<Step>
In the **Access requests** section of the entitlement's details page, click **Edit**.
</Step>
<Step>
In the **Access profiles** field, search for and select one or more access profiles you want to add the entitlement to.

</Step>
<Step>
Click **Save**.
</Step>
</Steps>

The entitlement is now included in the access profile. Users who have access to the access profile will see the entitlement as an option on the **New request** form, the **Requests** page, and in Slack or Teams (if enabled). 

### Update a current access profile holder's grant

If profile requests are allowed, any newly added entitlement will be included in future grants of the full access profile, but the entitlement will not be automatically granted retroactively to users who were previously granted the access profile. To manually add the new entitlement to a current profile holder's access: 

<Steps>
<Step>
Navigate to the access profile's **Apps** tab. 
</Step>

<Step>
Locate the newly added entitlement in the list of entitlements included in the access profile and click the **...** (more actions) menu. 
</Step>

<Step>
Select **Manage provisioning**. 
</Step>

<Step>
Any users who have been granted the full access profile but do not currently have access to the entitlement display **Not granted** in the **Status** column. Click **Request** for the users who you want to receive access to the new entitlement. 

   You can also click **Request for all** to request access for all profile holders who do not have the entitlement. 
</Step>
</Steps>

**Done.** C1 automatically creates an access request for the entitlement for each user. You can track the progress of the access requests at any time by returning to the **Manage provisioning** drawer.

## Grant duration and expiration in access profiles

Access profiles control how long a user can be a *member*, but they don't control how long the underlying grants last. When a user becomes a member of a profile, C1 creates individual grants for each entitlement in the profile — and each grant follows the duration configured on that entitlement, not the profile's membership duration. If different entitlements in the same profile have different durations configured, their grants will expire at different times, independently of each other and independently of when the membership itself ends.

What happens to those grants when a profile membership ends depends on the profile's **Access change behavior** setting. Depending on how this is configured, grants may be left in place, revoked, or revoked unless the user has another active membership justifying them.

### Profile expiration settings

Roles and hybrid profiles have two settings that control membership duration and what happens when it ends. You can find and set these on the access profile's **Settings** tab, where **Max membership duration** is in the **Joiner** area and **Access change behavior** is in the **Leaver** area. 

- **Max membership duration** — the longest a user can be a member. If a user requests a duration longer than the maximum, it's capped. If they don't specify a duration, the maximum is used as the default.
- **Access change behavior** — what C1 does to a user's entitlement grants when their profile membership ends. There are three options:
  - **Leave access as-is** — grants are not touched when membership ends. Access continues until grants expire on their own schedule or are revoked manually.
  - **Revoke unjustified entitlements** — grants are revoked when membership ends, unless the user is still a member of another active profile that includes the same entitlement. A direct grant to the same entitlement does not count as justification.
  - **Revoke all entitlements** — all grants created by this membership are revoked when membership ends, regardless of any other access the user holds.

### When a user has both a profile membership and a direct grant

A user may hold the same entitlement from two sources at once: a profile membership and a direct grant. In that case, both the individual grant durations and the profile's **Access change behavior** setting affect what happens to access over time.

| When does access end? | Access change behavior setting | What happens |
|---|---|---|
| The direct grant expires before the profile membership ends | Any | Access is revoked when the direct grant expires, even though the membership is still active |
| The profile membership ends; the direct grant is still active | Leave access as-is | Access continues. The direct grant remains active. |
| The profile membership ends; the direct grant is still active | Revoke all entitlements | Access is revoked, regardless of the direct grant |
| The profile membership ends; the direct grant is still active | Revoke unjustified entitlements | Access is revoked. A direct grant does not count as justification. |
