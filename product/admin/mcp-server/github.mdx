Let your AI clients work with repositories, pull requests, issues, Actions, and security alerts in GitHub through MCP tools that C1 governs. C1 offers two GitHub options. They appear as separate entries in your MCP server catalog:

- **GitHub** (GitHub MCP) — C1 connects to GitHub's own hosted MCP server at `api.githubcopilot.com` and passes each tool call through. The tools are the ones GitHub publishes, so the set follows GitHub's own releases.
- **GitHub API** — C1 hosts an MCP server that turns GitHub's REST API into tools for developer workflows. C1 defines the tool set and sets default approval levels for risky actions.

Both options support per-user OAuth through a GitHub OAuth app that you register, or a shared personal access token.

| | GitHub (GitHub MCP) | GitHub API |
| :--- | :--- | :--- |
| **Who hosts the MCP server** | GitHub | C1 |
| **Tool set** | GitHub's own tools: repositories, issues, pull requests, Actions, discussions, security alerts, projects, gists, notifications, and more | About 350 tools, about 45 of them hidden by default, for developer workflows: code, pull request review, CI, deployments, issues, security alert triage, organization and team reads, projects, gists, and notifications |
| **Authentication** | Per-user OAuth through a GitHub OAuth app, or a personal access token | Per-user OAuth through a GitHub OAuth app, or a personal access token |
| **Scopes C1 requests** | `repo`, `read:org`, `read:user`, `user:email`, `read:packages`, `write:packages`, `read:project`, `project`, `gist`, `notifications`, `offline_access` | `repo`, `user`, `read:org`, `project`, `gist` |
| **Approval defaults** | Your tenant's default tool settings | High-risk actions such as merges, pushes, and workflow dispatch require approval by default |

### Choose between the two options

Choose **GitHub** if you want the tool set GitHub itself publishes, including discussions, Copilot features, and package-related scopes, and you want new GitHub tools to appear as GitHub releases them.

Choose **GitHub API** if you want a developer-workflow tool set with C1's default approval levels already applied to risky actions. It also includes tools that GitHub's hosted server doesn't offer as separate tools, such as reviewing pending deployments for a workflow run and listing a pull request's requested reviewers separately for users and teams.

<Tab title="GitHub MCP">

C1 registers as a client of [GitHub's hosted MCP server](https://github.com/github/github-mcp-server) rather than translating GitHub's API itself. Your users' AI clients only see C1-governed MCP tools. C1 passes each tool call to `https://api.githubcopilot.com/mcp/` under the connected user's session, then returns the result. - AI access management must be enabled for your tenant. See [Enable AI access management](/product/admin/enable-ai-access-management).
- GitHub doesn't support dynamic client registration for this server, so for per-user OAuth you first register a GitHub OAuth app and give C1 its client ID and client secret. If you'd rather not, use a personal access token.
- If your GitHub organization or enterprise is on a Copilot Business or Copilot Enterprise plan, GitHub's **MCP servers in Copilot** policy may need to be enabled for users to reach the hosted server. Organization policies can also limit which OAuth apps and scopes are allowed. See GitHub's [guide to setting up the GitHub MCP server](https://docs.github.com/en/copilot/how-tos/provide-context/use-mcp/set-up-the-github-mcp-server).

<Note>
In your MCP server catalog, this option is listed as **GitHub**, distinct from the **GitHub API** entry. If you don't see either, [contact the C1 support team](mailto:support@c1.ai) to enable it for your tenant.
</Note>

## Set up per-user OAuth

Per-user OAuth is the recommended way to connect. Each user authorizes individually, and every tool call runs under their own GitHub identity and permissions. Create the GitHub OAuth app first.

<Steps>
<Step>
In GitHub, go to **Settings** > **Developer settings** > **OAuth Apps** and select **New OAuth App** (or **Register a new application** if this is your first one). See GitHub's [guide to creating an OAuth app](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app).
</Step>
<Step>
Fill in the registration form:

- **Application name** — a recognizable name such as `C1`.
- **Homepage URL** — your C1 tenant URL, or `https://www.c1.ai`.
- **Authorization callback URL** — set this exactly to whichever matches your C1 tenant's domain. GitHub OAuth apps allow only one callback URL.
  - Default instance: `https://accounts.conductor.one/auth/callback`
  - EU data residency instance: `https://accounts.c1eu.ai/auth/callback`
</Step>
<Step>
Select **Register application**, then copy the **Client ID**.
</Step>
<Step>
Select **Generate a new client secret** and copy the secret. GitHub shows it only once. Store it securely. If it's ever exposed, generate a new one, update C1, then delete the old one ([best practices for creating an OAuth app](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/best-practices-for-creating-an-oauth-app)).
</Step>
</Steps>

With your OAuth app ready, register the server in C1.

<Steps>
<Step>
Follow [Register an MCP server](/product/admin/mcp-servers#register-an-mcp-server) and select **GitHub** from the catalog.
</Step>
<Step>
When you [configure authentication](/product/admin/mcp-servers#configure-authentication), choose **OAuth2 — per-user passthrough** and enter your OAuth app's **client ID** and **client secret**.
</Step>
<Step>
Save your changes.
</Step>
</Steps>

The first time a user calls a GitHub tool from their AI client, C1 redirects them to GitHub to sign in and approve the requested scopes, then returns them to C1 ([authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)).

### GitHub OAuth endpoints and scopes

Users authorize through GitHub's standard OAuth web application flow with PKCE (S256). These are GitHub's OAuth endpoints for your OAuth app, and you don't enter them in C1:

- **Authorization URL:** `https://github.com/login/oauth/authorize`
- **Token URL:** `https://github.com/login/oauth/access_token`

GitHub OAuth apps don't have scopes configured in advance. C1 requests these scopes on GitHub's consent screen ([scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)). All of them are requested by default, and there are no optional scopes to add:

- `repo` — full access to public and private repositories, including code, commit statuses, invitations, collaborators, deployment statuses, and webhooks.
- `read:org` — read-only access to organization membership, organization projects, and team membership.
- `read:user` — read access to the user's profile data.
- `user:email` — read access to the user's email addresses.
- `read:packages` — download and install packages from GitHub Packages.
- `write:packages` — upload and publish packages to GitHub Packages.
- `read:project` — read-only access to user and organization projects.
- `project` — read and write access to user and organization projects.
- `gist` — write access to gists.
- `notifications` — read notifications, mark threads as read, and manage watch and thread subscriptions.
- `offline_access` — lets GitHub issue a refresh token so users stay connected without reauthorizing each time the access token expires.

Tool calls run with the connected user's own GitHub permissions, so a user who can't publish a package in GitHub can't do it through a tool either. Scope changes take effect the next time a user authorizes.

If your organization enforces SAML single sign-on, each user needs an active SAML session for the organization when they authorize the app. If the app can't reach the organization afterward, the user revokes the app in GitHub, signs in to the organization, and authorizes again ([authorizing OAuth apps](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/authorizing-oauth-apps)).

## Use a personal access token instead

GitHub's hosted MCP server also accepts a personal access token, either fine-grained or classic, as a shared bearer credential. Every user then acts as one GitHub identity. Generate the token first.

<Steps>
<Step>
In GitHub, go to **Settings** > **Developer settings** > **Personal access tokens**. GitHub recommends **Fine-grained tokens**, which you can limit to specific repositories and permissions. A classic token reaches every repository its owner can access, and it's the option that works across several organizations ([managing personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)).
</Step>
<Step>
Select **Generate new token**, set a name, an expiration, and the permissions or scopes you need, then select **Generate token**.
</Step>
<Step>
Copy the token. GitHub shows it only once.
</Step>
</Steps>

If your organization uses SAML single sign-on, authorize the token for it after you create it. If the organization requires approval of fine-grained tokens, an organization owner must approve the token before it can reach the organization's resources. For a fine-grained token, the resource owner must be the organization for the token to reach its repositories. Enterprise Managed Users can't use personal access tokens unless an enterprise administrator enables them. Then register the server in C1 with the token.

<Steps>
<Step>
Follow [Register an MCP server](/product/admin/mcp-servers#register-an-mcp-server) and select **GitHub** from the catalog.
</Step>
<Step>
When you [configure authentication](/product/admin/mcp-servers#configure-authentication), choose **Bearer token** and paste the token. C1 sends it as `Authorization: Bearer <token>` on every request.
</Step>
</Steps>

## How GitHub MCP credentials are shared

- **Per-user OAuth.** Each user authorizes with their own GitHub account, so tool calls run under that user's GitHub identity and GitHub attributes each action to them.
- **Personal access token.** Every user's tool calls use the one token you provided, so GitHub sees a single shared identity. C1 still attributes each call to the individual user in the [AI tool usage audit log](/product/admin/audit-ai-tool-usage).

## Tool coverage

The tools are the ones GitHub's hosted server publishes, grouped by GitHub into toolsets such as repositories, issues, pull requests, Actions, code security, secret protection, Dependabot, security advisories, discussions, projects, gists, notifications, organizations, users, labels, Git data, Copilot, and stargazers. Because GitHub controls the list, tool names and coverage can change when GitHub updates its server. See [GitHub's toolset documentation](https://github.com/github/github-mcp-server#available-toolsets) for the current list.

## Discover and govern tools

After you register the server, C1 runs tool discovery against GitHub's hosted MCP server. Discovered tools appear on the server's **Tools** tab.

Each tool starts as either **Pending review** or automatically **Approved**, depending on the option chosen when the server was set up or your tenant's default tool settings in **AI** > **MCPs** > **Settings**. See [Require tool approval](/product/admin/enable-ai-access-management#require-tool-approval) and [Default tool classification](/product/admin/enable-ai-access-management#default-tool-classification). C1 doesn't set special approval levels for GitHub's tools, so review the tools that merge, push, trigger workflows, or change repository settings before approving them.

Before anyone can call a GitHub tool, it must be approved, added to a toolset, and bound to an access profile. Continue to [Govern tools and toolsets](/product/admin/tools-and-toolsets) to set this up.

<Note>
Tool discovery runs even if authentication isn't complete yet, so seeing discovered tools doesn't confirm a user has authorized. You confirm access when an approved user successfully calls a GitHub tool from their AI client.
</Note>

## Manage access to GitHub MCP

- **Rotate the OAuth client secret** on your OAuth app's settings page in GitHub (**Settings** > **Developer settings** > **OAuth Apps**), then update the secret on the server's authentication settings in C1.
- **Rotate a personal access token** by generating a new one in GitHub and updating it in C1. Set an expiration on the token so it rotates on a schedule.
- **An individual user can revoke their own authorization at any time.** In GitHub, go to **Settings** > **Applications** > **Authorized OAuth Apps**, then select **Revoke** next to C1 ([reviewing your authorized OAuth apps](https://docs.github.com/en/apps/oauth-apps/using-oauth-apps/reviewing-your-authorized-oauth-apps)).
- **An organization owner can restrict or revoke OAuth app access org-wide** if the organization has third-party application access restrictions enabled ([about OAuth app access restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions)).

## Troubleshooting GitHub access errors

If a tool call fails with a 403 error or returns empty results, check these causes:

- **SAML enforcement.** If GitHub reports that the resource is protected by organization SAML enforcement, authorize the personal access token for single sign-on, or have the user sign in to the organization and authorize the OAuth app again.
- **OAuth app access restrictions.** If the organization restricts third-party OAuth apps, an organization owner must approve the app ([about OAuth app access restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions)).

## How GitHub API credentials are shared

How GitHub sees your users' activity depends on the method you chose:

- **Per-user OAuth.** Each user authorizes with their own GitHub account, so tool calls run under that user's GitHub identity and inherit only the access they already have. GitHub attributes each action to the individual user.
- **Personal access token.** Every user's tool calls use the one token you provided, so GitHub sees a single shared identity. C1 still attributes each call to the individual user in the [AI tool usage audit log](/product/admin/audit-ai-tool-usage).

For how shared and per-user credentials work across MCP servers, see [Configure authentication](/product/admin/mcp-servers#configure-authentication).

## Tool coverage

The GitHub API server exposes about 350 tools for developer workflows:

- **Repositories and code** — repositories, branches, commits, files, Git references and trees, releases, comparisons, and search across code, commits, issues, repositories, and users.
- **Pull requests** — pull requests, changed files, commits, reviews, review comments, requested reviewers, merges, and branch updates.
- **Issues** — issues, comments, labels, milestones, assignees, sub-issues, dependencies, and timeline events.
- **Actions and CI** — workflows, runs, jobs, artifacts, check runs, and commit statuses, plus re-running, canceling, and dispatching workflows.
- **Deployments** — deployments, environments, and reviewing pending deployments for a workflow run.
- **Security triage** — code scanning, Dependabot, and secret scanning alerts, security advisories, and dependency review.
- **Identity and organizations** — users, organizations, teams, members, collaborators, and organization roles.
- **Projects, gists, notifications, and stars.**

Administration of organizations, enterprises, and repositories (settings, policies, runners, secrets, webhooks, membership changes) and credential management aren't exposed.

### Reviewing pending deployments

The GitHub API server can list the deployments a workflow run is waiting on and approve or reject them with a comment, the same review a person gives in GitHub. GitHub enforces who can do this:

- The run must be waiting on an environment that has required reviewers, and the connected GitHub identity must be one of them. Each pending deployment shows whether the connected user can approve it.
- If the environment prevents self-review, a user can't approve a run they started.
- On GitHub Free, Pro, and Team plans, required reviewers are only available for public repositories ([deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)).
- With a fine-grained personal access token, grant read access to **Contents** and **Deployments** on the repositories involved.

### Approval defaults

C1 sets default approval levels for GitHub API tools. Reads run without confirmation. The tools that carry the highest risk require approval by default:

- Merging pull requests and branches, syncing forks, and updating a pull request branch.
- Committing files, updating Git references, and creating commit statuses.
- Dispatching workflows, sending repository dispatch events, and re-running, canceling, or disabling workflows.
- Creating deployments and releases, and reviewing pending deployments or custom deployment gates.
- Creating, submitting, and dismissing pull request reviews.
- Dismissing code scanning, Dependabot, and secret scanning alerts, and committing code scanning autofixes.

Most other writes ask for confirmation. Only a few low-risk actions, such as marking notifications as read, subscribing to a thread, and starring a repository, run without confirmation. You can change any default when you [govern tools and toolsets](/product/admin/tools-and-toolsets).

About 45 tools are hidden by default, including downloads of archives and artifacts, log retrieval, and irreversible deletes.

### Known limits

- Writes that touch `.github/workflows/` files fail because C1 doesn't request the `workflow` scope.
- Some organization reads, such as outside collaborators and organization roles, return an error unless the connected user is an organization owner or admin.
- Each list call returns one page of results. Tools that support paging take a `page` parameter, with up to 100 results per page.
- The tools that remove assignees, requested reviewers, and sub-issues, and the tool that deletes a file, can't currently be enabled.

## Troubleshooting GitHub access errors

If a tool call fails with a 403 error or returns empty results, check these causes:

- **SAML enforcement.** If GitHub reports that the resource is protected by organization SAML enforcement, authorize the personal access token for single sign-on, or have the user sign in to the organization and authorize the OAuth app again.
- **OAuth app access restrictions.** If the organization restricts third-party OAuth apps, an organization owner must approve the app ([about OAuth app access restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions)).
- **Workflow files.** Writes to files under `.github/workflows/` fail because C1 doesn't request the `workflow` scope.
- **Owner-only reads.** Reads such as outside collaborators and organization roles return a 403 or 404 error unless the connected user is an organization owner.
- **Missing scopes after a scope change.** If organization, team, project, or gist tools fail for a user who authorized earlier, have the user reconnect their GitHub account so GitHub grants the scopes C1 currently requests.
- **Review requests.** GitHub rejects a review request for the pull request's own author with a 422 error. Request a different user or a team.
