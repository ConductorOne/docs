The Looker MCP server lets you govern access to Looker — dashboards, looks, queries, explores, content, and users — as tools your AI clients can call through C1.

You choose how users connect when you register the server:

- **Per-user OAuth**. Each person authorizes with their own Looker account, so every tool call runs under that user's Looker identity and permissions.
- **API credentials**. A client ID and client secret that C1 exchanges for a short-lived access token. A single set of credentials authenticates everyone, so all tool calls reach Looker as one shared identity.

For a deeper comparison of shared versus per-user credentials, see [Configure authentication](/product/admin/mcp-servers#configure-authentication).

## How C1 connects to Looker

C1 hosts the Looker MCP server, so your users' AI clients only ever see MCP tools — they never call Looker directly. When an AI client calls one of these tools, C1 makes the matching request to the Looker API using the credentials you configure here, then returns the result to the AI client.

The credentials you set up below are what C1 uses to call Looker on your users' behalf.

## Before you begin

- AI access management must be enabled for your tenant. See [Enable AI access management](/product/admin/enable-ai-access-management).
- For per-user OAuth, a Looker administrator who can register an OAuth client application through the Looker API.
- For API credentials, a Looker account with API credentials. API credentials inherit the permissions and content access of the user they belong to, so use a user that has the access you want this integration to have.

<Note>
If you don't see **Looker** in your MCP server catalog, [contact the C1 support team](mailto:support@c1.ai) to enable it for your tenant.
</Note>

## Option 1: Set up per-user OAuth

With per-user OAuth, you register one OAuth client application in Looker and each user authorizes individually. This keeps every action attributable to the user who took it, with only the access that user already has in Looker.

### Register a Looker OAuth client application

Looker requires an OAuth client application to be registered through its API before users can authenticate. For the full procedure, see Looker's [OAuth client application](https://docs.cloud.google.com/looker/docs/api-cors) documentation.

<Steps>
<Step>
In the Looker API Explorer, choose **4.0 - stable** and open **Register OAuth App** under **Auth**.
</Step>
<Step>
Enter a **client_guid** such as `c1`, a **display_name** and **description**, and set the **redirect_uri** exactly to whichever matches your C1 tenant's domain. Looker denies authentication if the values don't match exactly.

- Default instance: `https://accounts.conductor.one/auth/callback`
- EU data residency instance: `https://accounts.c1eu.ai/auth/callback`
</Step>
<Step>
Run the request. The **client_guid** is the client ID you give C1.
</Step>
</Steps>

### Looker scopes

C1 requests this scope automatically. It's the scope Looker uses for OAuth access to its API:

`cors_api`

### Register the server with OAuth

With your OAuth client application registered, register the server and provide its client ID to C1.

<Steps>
<Step>
Follow [Register an MCP server](/product/admin/mcp-servers#register-an-mcp-server) and select **Looker** from the catalog.
</Step>
<Step>
Enter your Looker instance URL when prompted.
</Step>
<Step>
When you [configure authentication](/product/admin/mcp-servers#configure-authentication), choose per-user OAuth and enter the application's **client_guid** as the client ID. The scopes field is pre-filled with `cors_api`.
</Step>
<Step>
Save your changes. The first time a user calls a Looker tool from their AI client, they're prompted to connect their Looker account.
</Step>
</Steps>

## Option 2: Use API credentials

Create API credentials for the user whose Looker access this integration should carry. For more information, see Looker's [API authentication](https://cloud.google.com/looker/docs/api-auth) documentation.

<Steps>
<Step>
Sign in to your Looker instance and open the user whose access the credentials should carry. 
</Step>
<Step>
On that user's page, find the **API Keys** section and generate a new key.
</Step>
<Step>
Copy both the **Client ID** and the **Client Secret**. Looker shows the client secret only once.
</Step>
</Steps>

For a shared production setup, create the credentials under a dedicated service-account user so activity is attributable to C1 rather than a person, and grant that user only the roles and content access you want to govern.

### Register the server with API credentials

With your credentials ready, register the server and provide them to C1.

<Steps>
<Step>
Follow [Register an MCP server](/product/admin/mcp-servers#register-an-mcp-server) and select **Looker** from the catalog.
</Step>
<Step>
Enter your Looker instance URL when prompted.
</Step>
<Step>
When you [configure authentication](/product/admin/mcp-servers#configure-authentication), choose **Client credentials** and enter your Looker **client ID** and **client secret**.
</Step>
<Step>
Save your changes. C1 starts a sync that discovers the tools the Looker server exposes.
</Step>
</Steps>

## How Looker credentials are shared

How Looker sees your users' activity depends on the method you chose:

- **Per-user OAuth.** Each user authorizes with their own Looker account, so tool calls run under that user's Looker identity and inherit only the access they already have. Looker attributes each action to the individual user.
- **API credentials.** Every user's tool calls use the one set of API credentials you provided, so Looker sees a single shared identity. C1 still attributes each call to the individual user in the [AI tool usage audit log](/product/admin/audit-ai-tool-usage). For a shared setup, create the credentials under a dedicated service-account user so activity is attributable to C1 rather than a person.

For how shared and per-user credentials work across MCP servers, see [Configure authentication](/product/admin/mcp-servers#configure-authentication).

## Discover and govern tools

After you register the server, C1 runs tool discovery against Looker. Discovered tools appear on the server's **Tools** tab.

Each tool starts as either **Pending review** or automatically **Approved**, depending on the option chosen when the server was set up or your tenant's default tool settings in **AI** > **MCPs** > **Settings**. See [Require tool approval](/product/admin/enable-ai-access-management#require-tool-approval) and [Default tool classification](/product/admin/enable-ai-access-management#default-tool-classification).

Before anyone can call a Looker tool, it must be approved, added to a toolset, and bound to an access profile. Continue to [Govern tools and toolsets](/product/admin/tools-and-toolsets) to set this up.

<Note>
Tool discovery runs even if your credentials are incorrect, so seeing discovered tools doesn't confirm that authentication is working. You confirm your Looker credentials when an approved user successfully calls a Looker tool from their AI client.
</Note>

## Manage your Looker credentials

- **Re-register the OAuth client application** in the Looker API Explorer if you need to change its redirect URI or details, then update the client ID in C1 if it changed.
- **Rotate the API credentials** by generating a new key for the user in Looker, updating the client ID and client secret in C1, then deleting the old key.
- **Adjust access** by editing the roles and content access of the user the credentials belong to in Looker.
