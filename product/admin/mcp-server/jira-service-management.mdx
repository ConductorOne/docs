The Jira Service Management MCP server lets you govern access to Jira Service Management — service desks, requests, queues, customers, organizations, knowledge base content, and SLAs — as tools your AI clients can call through C1.

Jira Service Management supports two ways to authenticate, and you choose one when you register the server:

- **Per-user OAuth** (recommended). Each person authorizes with their own Atlassian account, so every tool call runs under that user's identity and permissions.
- **Atlassian API token** (scoped). A single API token, created for a person or a service account, authenticates everyone as one shared identity. C1 sends it as a Bearer token.

For a deeper comparison of shared versus per-user credentials, see [Configure authentication](/product/admin/mcp-servers#configure-authentication).

## How C1 connects to Jira Service Management

C1 hosts the Jira Service Management MCP server, so your users' AI clients only ever see MCP tools — they never call Jira Service Management directly. When an AI client calls one of these tools, C1 makes the matching request to the Jira Service Management API using the credentials you configure here, then returns the result to the AI client.

The credentials you set up below are what C1 uses to call Jira Service Management on your users' behalf.

## Before you begin

- AI access management must be enabled for your tenant. See [Enable AI access management](/product/admin/enable-ai-access-management).
- For per-user OAuth, an Atlassian account that can create an OAuth 2.0 integration. See Atlassian's [OAuth 2.0 (3LO) apps guide](https://developer.atlassian.com/cloud/jira/service-desk/oauth-2-authorization-code-grants-3lo-for-apps/).
- For an API token, an Atlassian account or service account that can create API tokens with scopes, with access to Jira Service Management.
- Your Atlassian site's Cloud ID. To find it, open `https://your-site.atlassian.net/_edge/tenant_info` in a browser, replacing `your-site` with your site's name, and copy the `cloudId` value.

<Note>
If you don't see **Jira Service Management** in your MCP server catalog, [contact the C1 support team](mailto:support@c1.ai) to enable it for your tenant.
</Note>

## Option 1: Create an Atlassian OAuth 2.0 integration

With per-user OAuth, you register one Atlassian OAuth 2.0 (3LO) integration and each user authorizes individually. This keeps every action attributable to the user who took it, with only the access that user already has in Jira Service Management.

<Steps>
<Step>
Sign in to the Atlassian Developer Console with your Atlassian account. For the full walkthrough, see Atlassian's [OAuth 2.0 (3LO) apps guide](https://developer.atlassian.com/cloud/jira/service-desk/oauth-2-authorization-code-grants-3lo-for-apps/).
</Step>
<Step>
Select **Create** > **OAuth 2.0 integration**, enter a recognizable name such as `C1`, and if prompted for an **Access type**, choose **Resource-level**. Then select **Create**.
</Step>
<Step>
Open the **Permissions** tab. Add and configure both **Jira API** and **Jira Service Management API**, then add the scopes from [Jira Service Management scopes](#jira-service-management-scopes) below — the default scopes, plus any optional write or admin scopes you need. Each scope lives under the API shown in the table.
</Step>
<Step>
Open the **Authorization** tab. Next to **OAuth 2.0 (3LO)**, select **Configure** and set the **Callback URL** exactly to whichever matches your C1 tenant's domain:

- Default instance: `https://accounts.conductor.one/auth/callback`
- EU data residency instance: `https://accounts.c1eu.ai/auth/callback`

Select **Save changes**.
</Step>
<Step>
Open the **Settings** tab. Under **Authentication details**, copy the **Client ID** and the **Secret**. Reveal the secret to copy it, and treat it as a high-value credential.
</Step>
</Steps>

## Jira Service Management scopes

C1 requests the default scopes automatically. To enable write or admin tools, add the optional scopes below in the Developer Console (**Permissions** > the API listed for each scope > **Configure**) and in C1's scopes field when configuring authentication. Grant only what you need.

The scopes span two APIs in the Developer Console, so add both **Jira API** and **Jira Service Management API**.

**Default scopes** (enable all of them) read requests, customers, knowledge base content, and user profiles, plus `offline_access` for token refresh. `manage:servicedesk-customer` is the only scope Atlassian offers for customer and organization access, so it also authorizes the customer and organization write tools:

| Scope | API in the Developer Console | Scope type |
| :--- | :--- | :--- |
| `read:servicedesk-request` | Jira Service Management API | Classic |
| `manage:servicedesk-customer` | Jira Service Management API | Classic |
| `read:knowledgebase:jira-service-management` | Jira Service Management API | Granular |
| `read:requesttype:jira-service-management` | Jira Service Management API | Granular |
| `read:request.attachment:jira-service-management` | Jira Service Management API | Granular |
| `read:request.comment:jira-service-management` | Jira Service Management API | Granular |
| `read:jira-user` | Jira API | Classic |
| `read:jira-work` | Jira API | Classic |
| `read:user:jira` | Jira API | Granular |
| `offline_access` | None (C1 requests it; nothing to enable) | Not applicable |

<Warning>
Every default scope must be enabled on your integration. If C1 requests a scope the integration doesn't have, authorization fails and Atlassian shows only "Something went wrong."
</Warning>

**Optional scopes** enable the write and admin tools. Add only the ones you need:

| Scope | API in the Developer Console | Scope type | Enables |
| :--- | :--- | :--- | :--- |
| `write:servicedesk-request` | Jira Service Management API | Classic | Create and update requests, add comments |
| `write:requesttype:jira-service-management` | Jira Service Management API | Granular | Create and edit request types |
| `write:jira-work` | Jira API | Classic | Not used by the current tools |
| `manage:jira-project` | Jira API | Classic | Delete request types, and set or delete request type properties |
| `manage:jira-configuration` | Jira API | Classic | Not used by the current tools |
| `manage:jira-webhook` | Jira API | Classic | Not used by the current tools |

<Note>
Atlassian recommends keeping an app under 50 scopes. Scope changes take effect the next time a user connects — adding an optional scope after users have connected requires each user to reconnect their Atlassian account.
</Note>

## Register the Jira Service Management MCP server with OAuth

With your integration ready, register the server and provide your credentials.

<Steps>
<Step>
Follow [Register an MCP server](/product/admin/mcp-servers#register-an-mcp-server) and select **Jira Service Management** from the catalog.
</Step>
<Step>
Enter your Atlassian site's **Cloud ID**.
</Step>
<Step>
When you [configure authentication](/product/admin/mcp-servers#configure-authentication), choose per-user OAuth and enter your integration's **client ID** and **client secret**.
</Step>
<Step>
Save your changes. The first time a user calls a Jira Service Management tool from their AI client, they're prompted to connect their Atlassian account.
</Step>
</Steps>

## Option 2: Set up an Atlassian API token

An Atlassian API token authenticates every user as one shared identity: the Atlassian account that owns the token. Use it when per-user attribution in Jira Service Management isn't required, or when you want a service account to own the connection. C1 sends the token as a Bearer token.

### Create an API token

Create an API token with scopes, either for a person or for a service account, so C1 can authenticate to the Jira Service Management API. The token's scopes are fixed when you create it, so select every scope below. To change them later, create a new token.

<Steps>
<Step>
Open [Atlassian API tokens](https://id.atlassian.com/manage-profile/security/api-tokens) and select **Create API token with scopes**. For details, see Atlassian's [Manage API tokens for your Atlassian account](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/) documentation.
</Step>
<Step>
Enter a name such as `C1`, choose an expiration between 1 and 365 days, then select **Next**.
</Step>
<Step>
Select **Jira** as the app, then select **Next**. Atlassian lists the Jira Service Management scopes under the **Jira** app, so there is no separate app to choose.
</Step>
<Step>
Select these scopes, then select **Next**:

- `read:servicedesk-request`
- `manage:servicedesk-customer`
- `read:jira-user`
- `read:jira-work`
- `read:knowledgebase:jira-service-management`
- `read:requesttype:jira-service-management`
- `read:request.attachment:jira-service-management`
- `read:request.comment:jira-service-management`
- `read:user:jira`

To enable write or admin tools, also select the matching optional scopes from [Jira Service Management scopes](#jira-service-management-scopes).
</Step>
<Step>
Review the token, select **Create**, then copy it. Atlassian shows it only once.
</Step>
</Steps>

To own the token with a service account instead of a person, create it from the service account in Atlassian Administration under **Directory** > **Service accounts**, and select the same app and scopes. Give the service account access to Jira Service Management and to the service desks C1 should read. For the full procedure, see Atlassian's [Manage API tokens for service accounts](https://support.atlassian.com/user-management/docs/manage-api-tokens-for-service-accounts/) documentation. A dedicated service account keeps activity attributable to C1 rather than a person.

The token expires on the date you chose, so rotate it before then.

### Register the Jira Service Management MCP server with an API token

With your API token ready, register the server and provide it.

<Steps>
<Step>
Follow [Register an MCP server](/product/admin/mcp-servers#register-an-mcp-server) and select **Jira Service Management** from the catalog.
</Step>
<Step>
Enter your Atlassian site's **Cloud ID**.
</Step>
<Step>
When you [configure authentication](/product/admin/mcp-servers#configure-authentication), choose **Bearer token** and paste your API token.
</Step>
<Step>
Save your changes. C1 runs tool discovery against Jira Service Management.
</Step>
</Steps>

## How Jira Service Management credentials are shared

With per-user OAuth, each user authorizes with their own Atlassian account, so tool calls run under that user's Jira Service Management identity and inherit only the access they already have. Atlassian attributes each action to the individual user.

With an API token, every user's tool calls use the one credential you provided, so Jira Service Management sees a single shared identity: the account that owns the token. C1 still attributes each call to the individual user in the [AI tool usage audit log](/product/admin/audit-ai-tool-usage).

For how shared and per-user credentials work across MCP servers, see [Configure authentication](/product/admin/mcp-servers#configure-authentication).

## Discover and govern tools

After you register the server, C1 runs tool discovery against Jira Service Management. Discovered tools appear on the server's **Tools** tab.

Each tool starts as either **Pending review** or automatically **Approved**, depending on the option chosen when the server was set up or your tenant's default tool settings in **AI** > **MCPs** > **Settings**. See [Require tool approval](/product/admin/enable-ai-access-management#require-tool-approval) and [Default tool classification](/product/admin/enable-ai-access-management#default-tool-classification).

Before anyone can call a Jira Service Management tool, it must be approved, added to a toolset, and bound to an access profile. Continue to [Govern tools and toolsets](/product/admin/tools-and-toolsets) to set this up.

<Note>
Tool discovery runs even if your credentials are incorrect, so seeing discovered tools doesn't confirm that authentication is working. You confirm your Jira Service Management credentials when an approved user successfully calls a Jira Service Management tool from their AI client.
</Note>

## Manage your Jira Service Management credentials

- **Rotate the OAuth client secret** in the Atlassian Developer Console under your integration's **Settings** tab, then update the secret on the server's authentication settings in C1.
- **Rotate an API token** by creating a new token in Atlassian with the same scopes and updating it in C1, then revoking the old one. Create the new token before the current one expires.
- **Adjust access** by editing the integration's scopes on the **Permissions** tab in the Atlassian Developer Console. For an API token, create a replacement token with different scopes.
