Tool call hooks are interception points that run on every governed MCP tool call. They can observe a call, modify its inputs or outputs, or deny it outright. Use them to redact sensitive data, cap risky parameters, or enforce conditional access rules that see beyond the entitlement grant model.

## How hooks work

Each hook fires on one of two events:

| Event | When it runs | What it can do |
| :--- | :--- | :--- |
| **Pre-tool use** | Before C1 forwards the call to the MCP server | Inspect or rewrite the input, or deny the call |
| **Post-tool use** | After the MCP server returns | Inspect or rewrite the output, or deny the response from reaching the client |

Hooks run in **priority order** (lower priority numbers run first). Each hook is independently enabled or disabled and can be scoped to specific tools with a [CEL](/product/admin/expressions) filter expression. Multiple hooks can stack on the same call — input or output modifications from earlier hooks are passed to later ones, and any hook can short-circuit the chain by denying.

Hooks are **fail-closed**. If a hook errors, times out, or its filter expression fails to evaluate, the call is denied. Custom function hooks have a 60-second invocation timeout.

Every hook execution is recorded in the [audit log](/product/admin/audit-ai-tool-usage) with one of these statuses: `ALLOWED`, `MUTATED`, `DENIED`, `ERROR`, `TIMEOUT`, or `FILTER_ERROR`.

## Configure a hook

<Steps>
<Step>
Go to **AI > C1 Gateway > Settings** and find the **Hooks** section.
</Step>
<Step>
Click **New hook**.
</Step>
<Step>
Fill out the form:

| Field | Notes |
| :--- | :--- |
| **Name** | Required. 1–100 characters. |
| **Description** | Optional. Up to 2048 characters. |
| **Hook type** | **Built-in pattern** for one of the patterns below, **Patch tool input** to rewrite the call's input fields directly, or **Custom function** to invoke a [function](/product/admin/functions). |
| **Event** | **Pre-tool use** or **Post-tool use**. Some built-in patterns only support one event, and **Patch tool input** hooks are always pre-tool use. |
| **Filter** | Optional [CEL](/product/admin/expressions) expression. Empty matches all tools. Example: `ctx.tool_name.startsWith("github_")`. See [Filter variables](#filter-variables). |
| **Priority** | 0–1000. Lower runs first. |
| **Enabled** | Toggle on to activate the hook immediately on save. |
</Step>
<Step>
Configure the hook type: for **Built-in pattern**, choose the pattern and set its options; for **Patch tool input**, define the patch; for **Custom function**, pick the function from the dropdown.
</Step>
<Step>
Click **Save**.
</Step>
</Steps>

### Filter variables

Filter expressions read from a single `ctx` variable:

- `ctx.tool_name` — the name of the tool being called, for example `github_create_issue`. Always available.
- `ctx.surface` — the chat surface the call came from, either `slack` or `web`.
- `ctx.channel_id` — the ID of the Slack channel the call came from, for example `C0123456789`.

`ctx.surface` and `ctx.channel_id` are only available for calls that originate in a chat channel. When a call comes from somewhere else — an AI client connected directly over MCP, for example — the variables are absent rather than empty, and reading an absent variable fails the expression. Because hooks are fail-closed, that failure denies the call, so guard with `has()` before reading either one:

```cel
has(ctx.channel_id) && ctx.channel_id == "C0123456789"
```

## Built-in patterns

C1 ships five pre-built hook patterns. Each one is a self-contained handler with its own configuration; no function code is required.

| Pattern | Event | What it does |
| :--- | :--- | :--- |
| **PII field redaction** | Post | Replaces values in JSON output fields whose names match a configurable list (defaults: `ssn`, `social_security_number`, `date_of_birth`, `salary`, `bank_account`) with a placeholder string. |
| **Credit card blocking** | Post | Scans tool output for Luhn-valid credit card numbers and denies the response if any are found. |
| **Query scope limit** | Pre | Caps numeric input fields (defaults: `limit`, `page_size`, `count`, `max_results`) at a configured maximum to prevent oversized queries. |
| **Write authorization** | Pre | Denies tool calls whose classification is in a blocked list, optionally only outside a configured business-hours window (timezone, start/end times, days of the week). |
| **Sensitive file guard** | Pre | Denies tool calls that reference sensitive file paths or directories (defaults: `.env`, `*.pem`, `*.key`, `id_rsa`, `.ssh/`, `.aws/`, and similar). |

## Patch tool input hooks

A **Patch tool input** hook rewrites the input of a tool call before C1 forwards it to the MCP server — adding, overwriting, or removing fields without invoking a function. Use it to force a parameter to a safe value, stamp a scope onto every call, or strip a field the AI client shouldn't be able to set.

These hooks only run on **pre-tool use**, since the other event has no tool input left to patch.

Define the patch one of two ways:

| Option | Notes |
| :--- | :--- |
| **Static fields** | A fixed JSON object applied to every matching call. Use it when the values never change, for example always sending `{"environment": "development"}`. |
| **CEL expression** | A [CEL](/product/admin/expressions) expression that returns a JSON object, evaluated per call. Use it when the patch depends on who is calling or where the call came from. |

A hook uses one or the other, not both.

### Expression variables

A patch expression reads from three variables:

- `ctx` — the same call context available to [filters](#filter-variables): `ctx.tool_name`, plus `ctx.surface` and `ctx.channel_id` when the call comes from a chat channel. Guard the chat-channel variables with `has()`.
- `input` — the tool call's own input arguments, so you can derive one field from another.
- `caller` — identity information about the caller, including `caller.id`.

<Warning>
Never treat `caller` as an authorization input. C1 has already made the access decision by the time a hook runs, so use these values to shape a call — not to decide whether it's allowed.
</Warning>

### How the patch is applied

The resulting object is merged onto the tool's input field by field:

- A field in the patch that isn't in the input is **added**.
- A field in both is **overwritten** with the patch's value.
- A field set to `null` in the patch is **removed** from the input.
- Every other field in the input is left untouched.

This follows [JSON Merge Patch (RFC 7396)](https://datatracker.ietf.org/doc/html/rfc7396) at the top level of the input, including its convention that `null` deletes a field. The merge is not recursive: a nested object in the patch replaces the input's object of the same name outright rather than merging into it, so include every field you want to keep.

A call whose input was changed is recorded as `MUTATED` in the [audit log](/product/admin/audit-ai-tool-usage).

### Example: stamp a Slack channel's scope onto DataDog calls

To make every DataDog tool call from one Slack channel query only that team's tenant, filter to the channel and patch the tenant field.

Filter:

```cel
ctx.tool_name.startsWith("datadog_") && has(ctx.channel_id) && ctx.channel_id == "C0123456789"
```

Patch expression:

```cel
{"tenant_id": ctx.channel_id}
```

Matching calls arrive at the MCP server with `tenant_id` set to the originating channel, whatever the AI client asked for. Calls to other tools, or from anywhere other than that channel, pass through unchanged.

## Custom function hooks

When the built-in patterns and input patching don't fit, write a [function](/product/admin/functions) and attach it to a hook. C1 invokes the function with a JSON payload describing the call and uses the return value to decide whether to allow, modify, or deny.

See the [Functions overview](/product/admin/functions) and [Create a function](/product/admin/functions-create) for how to author and deploy a function.

### Pre-tool-use payload

The function receives:

```json
{
  "tool_name": "github_create_issue",
  "input": { /* the tool's input arguments */ },
  "context": {
    "tool_source": "connector",
    "classification": "WRITE",
    "surface": "slack",
    "channel_id": "C0123456789"
  }
}
```

`tool_source` is either `builtin` or `connector`. `classification` is the tool's configured action class (`READ`, `WRITE`, `DESTRUCTIVE`, `SENSITIVE`, or `DANGEROUS`). `surface` and `channel_id` identify the chat channel the call came from and are omitted entirely for calls that didn't originate in one.

### Post-tool-use payload

The function receives the same fields plus the call result:

```json
{
  "tool_name": "github_create_issue",
  "input": { /* original input */ },
  "output": { /* whatever the tool returned */ },
  "error": "",
  "context": { /* same as pre */ }
}
```

### Return value

In both events the function returns an object with any subset of these fields:

```json
{
  "deny": false,
  "reason": "explanation shown in audit log",
  "input":  { /* pre only: replacement input */ },
  "output": { /* post only: replacement output */ }
}
```

- Set `deny: true` to block the call. The `reason` is recorded in the audit log and surfaced to the AI client as a denial.
- Omit `input` (pre) or `output` (post) when you don't need to modify the payload.
- Returning an empty object `{}` is equivalent to allowing the call unchanged.

If the function throws, exceeds the 60-second timeout, or returns invalid JSON, the call is denied and the failure is recorded as `ERROR` or `TIMEOUT` in the audit log.
