Something broke? Start here. Most connector issues fall into recognizable patterns. For the exact text of errors that the SDK produces, see [Error codes reference](/developer/error-codes).

## Debugging workflow

When a connector fails, follow this sequence:

1. **Check the logs.** What's the error message?
2. **Inspect the output.** Did the sync produce a `.c1z` file?
3. **Verify the configuration.** Are the credentials valid?
4. **Test API access.** Can you reach the target API directly?
5. **Isolate the issue.** Which resource type fails?

### Enable debug logging

```bash
./baton-yourservice --log-level debug --log-format json
```

Log levels are `debug`, `info`, `warn`, and `error`. The default is `info`. `--log-format` is `json` or `console`, and the default depends on whether the output is a terminal. Add `--log-path <file>` to write logs to a file. Every flag also works as an environment variable, such as `BATON_LOG_LEVEL=debug`.

At the debug level, `uhttp` logs every HTTP request. Search the logs for these messages:

| Message | Level | When |
|---------|-------|------|
| `HTTP request complete` | Debug | A successful request |
| `HTTP request client error` | Debug | A 4xx response |
| `HTTP request server error` | Warn | A 5xx response |
| `HTTP request failed` | Error | A transport failure, such as a refused connection |

Each message includes `http.method`, `http.status_code`, `duration`, and the URL host and path. To print response bodies as well, set `BATON_DEBUG_PRINT_RESPONSE_BODY` to any non-empty value. Be careful: bodies can contain sensitive data.

### Inspect sync output

Use the `baton` CLI to inspect what a sync produced:

```bash
baton resource-types -f sync.c1z  # List resource types
baton resources -f sync.c1z       # List resources
baton entitlements -f sync.c1z    # List entitlements
baton grants -f sync.c1z          # List grants
baton stats -f sync.c1z           # Show counts by resource type
```

The CLI has more commands for debugging:

- `baton syncs -f sync.c1z` lists the syncs stored in a file.
- `baton diff -f sync.c1z` compares the latest full sync in a file with the one before it.
- `baton explorer -f sync.c1z` opens a local browser interface for exploring a sync.
- `baton sanitize` makes a copy of a sync file with identifying data removed, which is useful when you need to share a file for a bug report.

Add `-o json` for machine-readable output.

## Common errors

### Pagination loop detected

**Error:** `listing resources failed: next page token unchanged ... - likely a connector bug`. Entitlements and grants have matching messages.

**Cause:** Your `List`, `Entitlements`, or `Grants` method returned the same non-empty token it received.

```go
// BAD: returns the token it was given.
func (u *userBuilder) List(ctx context.Context, parentID *v2.ResourceId, opts resource.SyncOpAttrs) ([]*v2.Resource, *resource.SyncOpResults, error) {
    users, _, err := u.client.GetUsers(ctx, opts.PageToken.Token)
    // ...
    return resources, &resource.SyncOpResults{NextPageToken: opts.PageToken.Token}, nil // Wrong
}

// GOOD: returns the next token from the API, or an empty token when done.
func (u *userBuilder) List(ctx context.Context, parentID *v2.ResourceId, opts resource.SyncOpAttrs) ([]*v2.Resource, *resource.SyncOpResults, error) {
    users, nextPage, err := u.client.GetUsers(ctx, opts.PageToken.Token)
    // ...
    return resources, &resource.SyncOpResults{NextPageToken: nextPage}, nil // Correct
}
```

The SDK stops the sync when it sees this. It doesn't catch a token that alternates between two values. See [Pagination patterns](/developer/pagination).

### Authentication failed

**Error:** An HTTP 401 or 403 from the target API. Through `uhttp`, these arrive as gRPC `Unauthenticated` and `PermissionDenied` errors, and the SDK doesn't retry them.

**Causes:**
- Invalid or expired credentials
- Missing required scopes or permissions
- Wrong API endpoint

**Diagnostic steps:**

```bash
# Test the credentials directly.
curl -H "Authorization: Bearer $TOKEN" https://api.example.com/v1/users

# For JWT tokens, decode the token and check the 'exp' claim.

# Check the required scopes in the target API's documentation.
```

| Issue | Fix |
|-------|-----|
| Expired token | Refresh or regenerate the credentials |
| Missing scope | Request additional API permissions |
| Wrong endpoint | Check the connector's endpoint setting. Many connectors have a base URL or domain flag, so run `--help` to find it. |

### Rate limited

**Error:** HTTP `429 Too Many Requests`, or a slow sync

**Solutions:**

1. **Reduce the page size.** Smaller requests are less likely to trip a limit. Use the page size the SDK passes in `opts.PageToken.Size` where your API accepts one.

2. **Use `uhttp`.** It turns a 429 into a gRPC `Unavailable` error. The SDK then waits and retries, using the API's rate limit headers when the request passed `uhttp.WithRatelimitData`, and an increasing delay otherwise. The delay grows linearly, not exponentially.

   ```go
   httpClient, err := uhttp.NewClient(ctx)
   if err != nil {
       return nil, err
   }
   base, err := uhttp.NewBaseHttpClientWithContext(ctx, httpClient)
   ```

3. **Limit your request rate.** Pass `uhttp.WithRateLimiter(rate, per)` when you create the client, instead of calling `time.Sleep` in your builder.

### Resource type mismatch

**Error:** Grants reference principals that don't exist

**Cause:** The `ResourceId` in a grant doesn't match any synced resource.

```go
// BAD: the type ID doesn't match.
g := grant.NewGrant(res, "member",
    &v2.ResourceId{ResourceType: "User", Resource: member.ID}) // "User" vs "user"

// GOOD: the type ID matches the declared resource type exactly.
g := grant.NewGrant(res, "member",
    &v2.ResourceId{ResourceType: userResourceType.Id, Resource: member.ID})
```

**Debug:**

```bash
baton resource-types -f sync.c1z
baton grants -f sync.c1z
```

Compare the resource type IDs in the two outputs.

### Empty sync results

**Error:** The sync finishes but produces no resources

**Causes:**
- The API returns empty results, often because of a permissions issue
- Pagination starts past the end of the data
- A filter, such as `--sync-resource-types`, is too restrictive

```bash
baton stats -f sync.c1z
./baton-yourservice --log-level debug 2>&1 | grep "HTTP request"
```

The second command shows each request and its status code.

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| 0 users | Missing read permission | Check the credential scopes |
| 0 grants | No memberships exist, or the resource type skips grants | Verify the data exists, and check for the `SkipEntitlementsAndGrants` annotation |
| Partial data | Pagination bug | Check token handling |

### Connection refused

**Error:** `connection refused` or `no such host`

```bash
curl -v https://api.example.com/health  # Test connectivity
nslookup api.example.com                # Check DNS
```

If your connector has a base URL setting, point it at the right host. Run `--help` to see whether it does.

### TLS certificate errors

**Error:** `x509: certificate signed by unknown authority`

**For testing only:** The SDK has no flag that skips TLS verification. If your connector adds one, it builds the HTTP client with `uhttp.WithTLSClientConfig`. See [Insecure TLS for local testing](/developer/recipes-testing#insecure-tls-for-local-testing).

<Warning>
Never skip TLS verification in production.
</Warning>

**For production:** Add the certificate authority to the system's trust store. On Linux, Go also reads a CA bundle from the `SSL_CERT_FILE` environment variable:

```bash
export SSL_CERT_FILE=/path/to/ca-bundle.crt
```

## Performance issues

### Slow sync

| Cause | Diagnosis | Fix |
|-------|-----------|-----|
| Too many API calls | Debug logs show thousands of requests | Batch where possible |
| No pagination | A single huge request | Implement paging |
| N+1 queries | Fetching details one at a time | Use bulk endpoints |
| Rate limiting | 429 responses in the logs | Reduce the request rate |
| Sequential sync | Large installations take hours | Try `--workers` to sync in parallel |

```go
// BAD: N+1 pattern (one API call per user).
for _, user := range users {
    details, _ := client.GetUserDetails(ctx, user.ID)
}

// GOOD: Bulk fetch.
details, _ := client.GetUsersWithDetails(ctx, userIDs)
```

If requests time out, `--http-timeout-seconds` raises the HTTP timeout. The default is 300 seconds, and the maximum is 1800.

### Memory issues

| Cause | Fix |
|-------|-----|
| Loading all data into memory | Use pagination and stream the results |
| Large responses not garbage collected | Process in batches |
| Caching too much | Limit the cache size, or use the session store |
| Large c1z files | See [c1z: max decoded size exceeded](/developer/error-codes#c1z-max-decoded-size-exceeded). `--c1z-temp-dir` or `BATON_TMPDIR` moves temporary files to a larger disk. |

## Daemon mode issues

In daemon mode, a connector polls C1 for tasks. It needs both `--client-id` and `--client-secret`.

### Task polling failures

**Errors:** `failed to get token: <status>`, `invalid client id`, `runner: error getting next task`, or `c1_api_task_manager: startup Hello failed`

```bash
./baton-yourservice \
    --client-id $CLIENT_ID \
    --client-secret $CLIENT_SECRET \
    --log-level debug
```

| Message | What to check |
|---------|---------------|
| `invalid client id` | A client ID has the form `name@host/...`. Copy it again from C1. |
| `failed to get token: 401 Unauthorized` | The client secret doesn't match the client ID, or the credential was revoked |
| `startup Hello failed; will retry` | A temporary failure. The connector retries with a growing delay, so look at the error in the same log line. |
| `startup Hello failed with non-retryable error; giving up` | The credentials or the target host are wrong, and retrying can't help |
| `runner: error getting next task` | Polling failed. The connector waits longer after each consecutive failure, up to a minute. |

The connector connects to C1 over TLS. To point it at a different C1 host, set `BATON_C1_API_HOST`.

### Connector not receiving tasks

**Symptom:** The daemon runs but never processes anything.

Check:
- The connector is registered in C1, and the client ID matches it.
- A sync is scheduled.
- `--skip-full-sync` isn't set. It makes the connector ignore sync tasks.
- The connector isn't already busy. It runs up to `--task-concurrency` tasks at once, and the default is 3.
- The process is alive. Run it with `--health-check` and request `/health`, `/ready`, or `/live` on `--health-check-port` (default 8081).

### Tasks that start and then stop

While a task runs, the connector reports progress to C1 at an interval that C1 sets. If it can't report progress ten times in a row, it stops the task and logs `heartbeat: failed after 10 attempts`. If C1 cancels the task, the connector logs `heartbeat: task was cancelled by server`. Check the connector's network path to C1.

### Debug logs requested by C1

C1 can ask a connector to capture debug logs for a task. The connector writes them to a `debug.log` file in its temporary directory and uploads that file with the sync.

## Provisioning issues

### Grant and revoke failures

**Error:** `resource type <type> does not have provisioner configured`

**Cause:** C1 sent a grant or revoke for a resource type whose builder doesn't implement provisioning.

```go
// Implement these methods on the resource builder.
func (g *groupBuilder) Grant(ctx context.Context,
    principal *v2.Resource, entitlement *v2.Entitlement) (
    []*v2.Grant, annotations.Annotations, error) {
    // Implementation
}

func (g *groupBuilder) Revoke(ctx context.Context,
    grant *v2.Grant) (annotations.Annotations, error) {
    // Implementation
}
```

Verify which resource types declare provisioning:

```bash
./baton-yourservice capabilities | jq '.resourceTypeCapabilities[] | select(.capabilities | contains(["CAPABILITY_PROVISION"]))'
```

If the capability is present but provisioning still fails in daemon mode, check that the connector runs with `--provisioning`. See [Implementing provisioning](/developer/provisioning).

## Duplicate objects after sync

### Symptom

After a sync, you see duplicate resources in C1: one created through Terraform or the API and a separate one discovered by the connector.

### Causes

1. **RawId not set.** The connector doesn't include the `RawId` annotation.
2. **ID format mismatch.** The connector uses a different ID format than you expected.
3. **Incorrect `match_baton_id` value.** The Terraform resource has the wrong ID value.
4. **Case sensitivity.** IDs may be case-sensitive.

### Resolution

**Step 1:** Confirm in your code that the connector builds the resource with the `RawId` annotation. See [ID correlation recipes](/developer/recipes-id#setting-rawid-annotation).

**Step 2:** Check what ID the connector uses:

| Connector | ID field | Example |
|-----------|----------|---------|
| Okta | `app.Id` | `0oa1xyz789abcdef0h7` |
| Azure AD | Object ID | `12345678-1234-...` |
| GCP | Resource path | `projects/my-project` |
| AWS | Full ARN | `arn:aws:iam::123...` |
| Databricks (group) | `account/<account-id>/group/<group-id>` | `account/8c6f99ec-.../group/79416186968854` |
| Databricks (workspace) | Deployment name | `dbc-dd4d071e-0b85` |

Some connectors don't use the native ID for every resource type. For example, a Databricks group's ID is a compound path, not the bare Databricks group ID. See [per-connector ID formats](/developer/recipes-id#per-connector-id-formats) for the full list.

**Step 3:** Update Terraform to use the exact match:

```hcl
resource "conductorone_app" "example" {
  display_name   = "My App"
  match_baton_id = "0oa1xyz789abcdef0h7"  # Exact value from the connector
}
```

**Step 4:** Delete the duplicate and sync again.

## Diagnostic commands

```bash
# Quick check
make build && ./dist/*/baton-yourservice \
    --log-level debug \
    --log-format json \
    2>&1 | head -100

# Inspect a .c1z file
baton stats -f sync.c1z
baton resources -f sync.c1z --resource-type user
baton resources -f sync.c1z --output-format json > resources.json

# Compare the latest sync with the previous one in the same file
baton syncs -f sync.c1z
baton diff -f sync.c1z

# Check connector health in daemon mode
./baton-yourservice health-check --endpoint health
```

## Getting help

If you've tried these steps and still have issues:

1. **Search existing issues** on the connector's GitHub repo.
2. **Check SDK issues** at [baton-sdk issues](https://github.com/conductorone/baton-sdk/issues).
3. **Open a new issue** with:
   - The connector name and version
   - The full error message
   - Debug logs, with credentials removed
   - Steps to reproduce

## Quick reference

### Debug flags

| Flag | Purpose |
|------|---------|
| `--log-level debug` | Verbose logging |
| `--log-format json` | Structured logs for parsing |
| `--log-path` | Write logs to a file |
| `--sync-resource-types` | Limit a sync to some resource types |
| `--workers` | Sync in parallel |
| `--http-timeout-seconds` | Raise the HTTP client timeout |
| `--health-check` | Enable the health check endpoint in daemon mode |

Many connectors also have an endpoint or base URL flag. Run `--help` to find out.

### Diagnostic tools

| Tool | Command | Purpose |
|------|---------|---------|
| baton | `baton resources -f sync.c1z` | Inspect sync output |
| baton | `baton stats -f sync.c1z` | Summary statistics |
| baton | `baton diff -f sync.c1z` | Compare the latest two full syncs |
| curl | `curl -v $API_URL` | Test API connectivity |
| jq | `baton resources -f sync.c1z -o json \| jq '.'` | Parse JSON output |
