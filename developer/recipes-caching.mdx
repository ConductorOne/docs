## When to cache

**Problem:** You need data from one resource type when processing another, such as resolving user IDs to emails when you emit grants.

| Scenario | Cache? | Why |
|----------|--------|-----|
| `Grants()` needs user details from `List()` | Yes | Avoids N+1 API calls |
| `Entitlements()` needs role definitions | Yes | Role metadata is stable |
| `List()` needs parent context | Usually not | The SDK passes the parent ID |
| Any data across syncs | No | Stale data causes drift |

**When not to cache:**
- Across syncs. In daemon mode, the same connector process runs many syncs.
- Large datasets that don't fit in memory.
- Data that changes frequently during a sync.

## What the SDK guarantees

A cache is only useful if you know when it's filled. These facts decide how you design one:

- **In a full sync, every `List` call finishes before any `Grants` call.** Registration order doesn't matter.
- **That isn't true everywhere.** A targeted sync fetches specific resources without listing the rest. A sync can also resume from a checkpoint in a new process, where nothing from the earlier run is in memory. `Grants` must work when the cache is empty.
- **Builders can run concurrently.** With `--workers N` (N greater than 0), the SDK syncs in parallel. The default is sequential.
- **The connector lives as long as the process.** The SDK builds your connector once, and in daemon mode the same instance serves every sync.

## Use the session store

**Problem:** Share data between `List()` and `Grants()` without managing a cache yourself.

**Solution:** V2 syncers receive a session store in `opts.Session`. The SDK clears it at the end of each sync, so nothing leaks into the next one.

First enable the store when you run the connector:

```go
config.RunConnector(ctx, "baton-example", version, cfg.Config, connector.New,
    connectorrunner.WithSessionStoreEnabled(),
)
```

Then write to it in `List` and read from it in `Grants`:

```go
// Populate during List.
func (u *userBuilder) List(ctx context.Context, _ *v2.ResourceId, opts resource.SyncOpAttrs) ([]*v2.Resource, *resource.SyncOpResults, error) {
    users, next, err := u.client.ListUsers(ctx, opts.PageToken.Token)
    if err != nil {
        return nil, nil, err
    }

    var resources []*v2.Resource
    items := make(map[string]User, len(users))
    for _, user := range users {
        items[user.ID] = user

        r, err := resource.NewUserResource(user.Name, userResourceType, user.ID,
            []resource.UserTraitOption{resource.WithEmail(user.Email, true)})
        if err != nil {
            return nil, nil, err
        }
        resources = append(resources, r)
    }

    if err := session.SetManyJSON(ctx, opts.Session, items); err != nil {
        return nil, nil, err
    }

    return resources, &resource.SyncOpResults{NextPageToken: next}, nil
}

// Read during Grants, and fall back to the API on a miss.
func (g *groupBuilder) Grants(ctx context.Context, res *v2.Resource, opts resource.SyncOpAttrs) ([]*v2.Grant, *resource.SyncOpResults, error) {
    memberIDs, next, err := g.client.GetGroupMemberIDs(ctx, res.Id.Resource, opts.PageToken.Token)
    if err != nil {
        return nil, nil, err
    }

    cached, err := session.GetManyJSON[User](ctx, opts.Session, memberIDs)
    if err != nil {
        return nil, nil, err
    }

    var grants []*v2.Grant
    for _, memberID := range memberIDs {
        if _, ok := cached[memberID]; !ok {
            // Not cached, so check the API instead of dropping the member.
            if _, err := g.client.GetUser(ctx, memberID); err != nil {
                return nil, nil, err
            }
        }
        grants = append(grants, grant.NewGrant(res, "member",
            &v2.ResourceId{ResourceType: userResourceType.Id, Resource: memberID}))
    }

    return grants, &resource.SyncOpResults{NextPageToken: next}, nil
}
```

`session` is `github.com/conductorone/baton-sdk/pkg/session`.

**Why:** The session store survives a resume and is scoped to one sync. It has limits you should plan for:

- **Treat it as a remote service, not a map.** Batch your reads and writes with the `Many` helpers, and tolerate misses.
- **Calls have a size limit of about 4 MB.** Cache IDs and small records, not whole API responses.
- **It's available only to V2 syncers**, and only when you enable it. Without it, calls return `session.ErrSessionStoreDisabled`.

## Cache in memory

**Problem:** Cache data in the connector itself, for a connector that doesn't use the session store.

**Solution:** Keep the cache on the connector struct, guard it, and key it by the sync ID so each sync starts empty:

```go
type Connector struct {
    client *client.Client

    mu    sync.Mutex
    cache *syncCache
}

type syncCache struct {
    syncID string
    users  sync.Map // map[userID]User
}

// cacheFor returns the cache for this sync, and replaces it when a new sync starts.
func (c *Connector) cacheFor(syncID string) *syncCache {
    c.mu.Lock()
    defer c.mu.Unlock()

    if c.cache == nil || c.cache.syncID != syncID {
        c.cache = &syncCache{syncID: syncID}
    }
    return c.cache
}
```

Builders call `c.cacheFor(opts.SyncID)` and treat a missing entry as a miss, not an error:

```go
cache := g.connector.cacheFor(opts.SyncID)

for _, memberID := range memberIDs {
    if _, ok := cache.users.Load(memberID); !ok {
        // Cache miss. List might not have run in this process.
        user, err := g.client.GetUser(ctx, memberID)
        if err != nil {
            return nil, nil, err
        }
        cache.users.Store(memberID, user)
    }
    // ...
}
```

**Why:** `sync.Map` is safe when builders run concurrently. Keying by `SyncID` means a new sync never sees data from the previous one. Falling back to the API on a miss keeps targeted syncs and resumed syncs correct.

## Cross-resource lookups

**Problem:** When you emit grants, you have member IDs but need to know whether each is a user or a group.

**Solution:** Record each ID's type while you list, and look it up when you emit grants:

```go
// In the user builder's List, mark IDs as users.
cache.knownUsers.Store(user.ID, true)

// In Grants, resolve the principal type.
func (c *syncCache) principalType(id string) string {
    if _, ok := c.knownGroups.Load(id); ok {
        return "group"
    }
    return "user" // Default
}
```

**Why:** Many APIs return member IDs without a type. Recording the type during `List` avoids a lookup for each member during `Grants`. Because the cache can be empty in a targeted or resumed sync, choose a default that's safe, or look the ID up in the API.

## Package-level caches

<Warning>
**Avoid package-level caches.** A package-level `sync.Map` persists for the life of the process, so in daemon mode it carries data from one sync into the next.
</Warning>

```go
// ANTI-PATTERN: do not copy.
var userCache sync.Map // Package-level. Persists across syncs.
```

**What goes wrong:**

1. Sync 1 runs and caches users A, B, and C.
2. User B is deleted from the target system.
3. Sync 2 runs in the same daemon process.
4. The cache still contains user B.
5. Grants for user B look valid but point at a deleted user.
6. Access reviews show access that doesn't exist.

A cache on the connector struct has the same problem, because the SDK builds the connector once per process. A struct field isn't fresh per sync. Use the session store, or key the cache by sync ID as shown above.

To check your connector for package-level caches:

```bash
grep -r "^var.*sync\.Map" pkg/
```

## Built-in HTTP cache

The `uhttp` package caches successful GET responses in memory. It keeps them for one hour by default, within a 5 MB limit. The SDK clears these caches at the end of every sync.

**Problem:** A cached response is stale, or you're testing and want every request to reach the API.

**Solution:** Opt out for one request, or turn the cache off for the whole process:

```go
// One request.
req, err := c.http.NewRequest(ctx, http.MethodGet, u, uhttp.WithNoCache())
```

```bash
# The whole process.
export BATON_DISABLE_HTTP_CACHE=true
```

You can also tune the cache with `BATON_HTTP_CACHE_TTL` (seconds) and `BATON_HTTP_CACHE_MAX_SIZE` (megabytes).

## Memory-bounded caching

**Problem:** Caching all users exhausts memory in a large organization.

**Solution:** For large datasets, use a bounded cache, or skip caching:

```go
import lru "github.com/hashicorp/golang-lru/v2"

type syncCache struct {
    syncID string
    users  *lru.Cache[string, User] // Holds at most 10,000 entries
}

func newSyncCache(syncID string) (*syncCache, error) {
    users, err := lru.New[string, User](10000)
    if err != nil {
        return nil, err
    }
    return &syncCache{syncID: syncID, users: users}, nil
}
```

**Alternative:** Batch your lookups instead of caching everything:

```go
// One API call for a batch of IDs.
func (c *Connector) lookupUsers(ctx context.Context, ids []string) (map[string]User, error) {
    return c.client.GetUsersByIDs(ctx, ids)
}
```

**Why:** Memory is finite. A connector that runs out of memory is worse than one that makes extra API calls.
